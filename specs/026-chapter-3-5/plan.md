# Implementation Plan: Tutorial Chapter 3.5 — Webhooks That Survive the Customer

**Branch**: `026-chapter-3-5` (no branch cut; work proceeds on `main` per the series' practice) | **Date**: 2026-08-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/026-chapter-3-5/spec.md`

## Summary

Write and publish chapter 3.5 in English and Vietnamese, and advance the platform
to the state it documents: webhook endpoints with rotatable signing secrets, and a
**new deployable service** that consumes the event stream, signs, posts, retries on
a durable widening schedule, and dead-letters what never succeeds.

The chapter's spine is that chapter 3.4's pattern stops applying, twice over. The
effect is an HTTP request to a machine the platform does not own, so it cannot be
rolled back. And the claim cannot join it in a transaction anyway, because the
dispatcher is a separate service and constitution IV reserves PostgreSQL writes to
the API service. What replaces the pattern is not a cleverer protocol: it is
choosing which way to be wrong, documenting it, and handing the customer the
identifier that makes the choice survivable.

Phase 0 settled the design, and **R1 was re-planned on 2026-08-10 after its
measurement**. The retry unit is `(event, endpoint)` rather than the event, because
one event can match several endpoints and retrying the event would re-deliver to
endpoints that already succeeded (R2). Where a pending retry *lives* was measured
rather than assumed: a broker-held delay survives a restart to the millisecond but
holds an acknowledgement slot while it waits, so a handful of dead endpoints starve
deliveries to healthy ones. The schedule is therefore a `next_attempt_at` column
drained by a relay in the api — chapter 3.3's outbox with one more predicate (R1,
R13). The signing secret cannot be hashed the way chapter
3.2 hashed API keys, because the platform must *use* it rather than verify it, so
NFR-SEC-02's other branch — envelope encryption — is the one that applies (R3).
The dispatcher is the first caller of the internal seam that is neither a tenant's
application nor an end user, which the credential model does not currently have a
shape for (R6). And the whole feature is reachable with **zero new dependencies**
(R10).

## Technical Context

**Language/Version**: TypeScript 5.9 on Node 22.12+. The api compiles as CommonJS
under NestJS 11 (ADR-15); everything else in the workspace is ESM.

**Primary Dependencies**: **none added.** The dispatcher needs an HTTP client
(Node 22's global `fetch`), HMAC and AES-GCM (`node:crypto`), and a NATS client
(`nats@2.29.3`, already present since 3.3). A chapter that adds a deployable and
no dependency is worth the sentence it costs to say so (R10).

**Framework**: the dispatcher is **frameworkless**, following the gateway's shape.
ADR-15 binds NestJS to the API service *only*; a second Nest application would be
adopting a framework by momentum rather than by decision.

**Storage**: PostgreSQL via the API service and never directly (constitution IV).
**Three** new tenant-scoped tables and one forward-only migration, generated by
drizzle-kit and reviewed before it is applied. NATS JetStream gains a second stream
which carries only work that is **already due** — the waiting happens in a row, not
in the broker (R1).

**Testing**: vitest in two lanes (Docker-free unit; `*.itest.ts` against compose
stores) plus the `@relay/e2e` journey suite. **New**: a controllable HTTP endpoint
that fails, hangs, or succeeds on command — the chapter's hostile customer, and the
same artifact a reader points their own endpoint at.

**Target Platform**: Linux server (services), static site (tutorial).

**Project Type**: Documentation-first tutorial plus the canonical monorepo it
teaches. The chapter is the deliverable; the code is its answer key.

**Performance Goals**: none claimed. A per-attempt timeout and a per-endpoint
concurrency bound are chosen for the reasons in R7 — one slow customer must not
starve the others — not against a latency budget. FR-WHK-05's requirement is an
isolation property, not a speed one, and it is tested as such.

**Constraints**: the dispatcher never writes PostgreSQL; the unit lane stays
Docker-free; no signing secret and no tenant message body in any log line; the API
service must serve writes with the dispatcher absent; every existing suite keeps
passing; fences byte-match the tag with hunked-diff amendments, and every file the
prose asserts is fenced (spec FR-029); both locales ship together.

**Scale/Scope**: one published chapter in two locales, **one new deployable**,
three new tables, one migration, one new stream, a second relay loop in the api, one
new internal contract, sixteen invariants — and, by the author's decision on
2026-08-10, **the containerisation of all three services**, which the repository has
never had. Fence budget **37–41** (R11) — by a wide margin the largest in the
series, and costed before rather than after.

## Constitution Check

*GATE: evaluated before Phase 0 and re-evaluated after Phase 1 design.*

| Principle | Gate | Verdict |
|---|---|---|
| **I — Tenant isolation is a correctness property** | Two new tables that, unlike the last two chapters', **are** tenant data. | **PASS, and the exception ends.** `outbox` (3.3) and `consumed_events` (3.4) were both exempted from tenant scoping as platform bookkeeping. Webhook endpoints belong to an environment and dead letters hold tenant-visible payloads, so both carry `environment_id` and both go through the scoped repository. The plan states the distinguishing rule explicitly (data-model §The rule the last two chapters were exceptions to) rather than leaving the next chapter to judge by resemblance. Endpoints join the 3.7 gauntlet's target list. |
| **II — No acknowledged message is ever lost** | A delivery path that can duplicate, and a schedule that must not be lost. | **PASS, with the trade stated in the chapter's own words.** A pending retry is a committed row, not process or broker memory, so neither a dispatcher restart nor an api restart can drop one (R1). Nothing about message durability changes; the event spine is 3.3's and 3.4's, unaltered. What is new is that the terminal hop is at-least-once *and visible to a customer*, so the obligation is documentary as well as technical: FR-003 requires the guarantee be stated, the accepted failure named, and the deduplication identifier handed over. An at-least-once webhook a customer believes is exactly-once is worse than one they know to deduplicate. |
| **III — Two data paths, never crossed** | A new service consuming the spine. | **PASS.** The dispatcher reads JetStream and talks to the API service. It never touches ClickHouse and never reads PostgreSQL. The 30-day analytical attempt log that FR-WHK-06 wants is explicitly Part 4's, which keeps this chapter on one path. |
| **IV — Single writer, single source of truth** | **The gate this chapter turns on.** | **PASS by construction.** "Only the API service writes to PostgreSQL… Other services obtain writes and backfill reads via the API service's internal endpoints." The dispatcher owns no database: endpoint configuration, delivery state and dead letters are all reached over the internal seam the gateway has used since 2.5. This is not a constraint the chapter works around — it is the reason the chapter's central pattern breaks, and therefore the reason the chapter exists. |
| **V — API-first, developer-first** | The first thing the platform sends *to* a customer's own code. | **PASS.** `contracts/webhooks.md` specifies the delivery as carefully as a REST endpoint: headers, signature construction, verification steps, retry schedule, and what is not promised. A webhook is an API whose consumer cannot read your source, so anything unstated becomes a support ticket. |
| **VI — Requirement-driven, test-verified** | Sixteen invariants, and a new service to measure. | **PASS, with new wiring required.** Every invariant has a named test and a requirement to cite (contracts §Invariants). Feature 024's coverage instrument and CI must be extended to the new service in the same change that creates it — a deployable outside the measurement is how a ratchet quietly stops meaning anything. |
| **VII — Boring by design — scope is a commitment** | A new deployable is the largest scope act since Part 1. | **PASS, and the scope was cut to pay for it.** Zero new dependencies. The attempt log (FR-WHK-06) and auto-disable (FR-WHK-07) move to the follow-on chapter by the author's decision, because they are one piece of work and this chapter is already the series' largest. Named and not built: mail, a dashboard, per-endpoint rate limits, a delivery-log query surface. |

**Post-Phase-1 re-evaluation**: unchanged. The design adds no dependency, two
tenant-scoped tables, one stream and one service, and changes no existing public
route. One item moved from "design" to "must be decided by measurement" — see R1
and Complexity Tracking.

**Structure Decision**: the management surface lives in the **api** and the
delivery machinery lives in the **dispatcher**, and the split is the constitution's
rather than a preference. Creating an endpoint writes tenant rows, so it belongs
behind the repository layer in the only service permitted to write. Posting to a
customer is neither a write nor a read of tenant state, so it belongs in a service
that can be starved by a slow customer without taking the write path with it. The
`webhooks/` module in the api and the `dispatcher/` service are two halves of one
feature separated along the line ADR-04 already drew.

The dispatcher mirrors `services/gateway`'s shape — frameworkless, ESM, an
`api-client.ts` that is its only road to state, and request/response schemas that
live in `@relay/protocol` so the two sides cannot drift. That is not novelty; it is
the second instance of a pattern chapter 2.5 established, which is the point at
which a pattern is worth naming.

## Phase 2 preview — how tasks will be shaped

`/speckit-tasks` will sequence: **the retry-durability measurement first** (R1 — if
a delayed redelivery does not survive a consumer restart, the whole scheduling
design changes, and discovering that after the service is built would be 2.6's
`ioredis` lesson a third time) → the endpoint and dead-letter schema, migration and
review → envelope encryption for the secret, with the "why not a hash" test written
first → the management surface, tenant-scoped, with the cross-tenant cases before
the happy path → the signature construction and an **independent verifier** in the
test (a verifier that reuses the signing code proves nothing) → the internal
dispatch contract in `@relay/protocol` → the dispatcher skeleton, provably startable
and stoppable with the api absent → expansion to per-endpoint deliveries → the
delivery attempt with its timeout → the six-tier schedule and its restart-survival
test → the dead-letter path and replay → the hostile endpoint and the walk script →
wire coverage and CI for the new service → prove every existing suite green →
capture output → write the chapter → translate → publish → amend `docs/07` → gates
plus traceability.

Chapter prose comes after the code, as always.

## Complexity Tracking

No constitution violations to justify. Four decisions a reviewer may reasonably
question, recorded with their alternatives:

| Decision | Why | What was rejected |
|---|---|---|
| A new deployable service | SAD §4.1 specifies it, and constitution IV makes the split meaningful rather than cosmetic: a service that cannot write the database is forced into the internal seam, which is the chapter's subject | keeping it in the api, which defers SAD §4.1 a fourth time and lets a customer-controlled URL be fetched from inside the process that owns the database |
| The signing secret is encrypted, not hashed | the platform must *use* it to sign; a hash cannot be used, only compared (R3). NFR-SEC-02 permits both and this is the branch that applies | hashing it as 3.2 hashed API keys, which would make signing impossible — worth stating because the resemblance is the trap |
| The retry unit is `(event, endpoint)`, not the event | one event can match several endpoints; retrying the event re-delivers to endpoints that already succeeded (R2) | per-event retry with a per-endpoint success set, which is the same state in a shape that makes the duplicate-delivery bug easy to reintroduce |
| The retry schedule is a `next_attempt_at` column, drained by a relay in the api | **measured**: a broker-held delay holds an acknowledgement slot, so dead endpoints starve healthy ones (R1). A row waits for free, and the loop already exists from 3.3 | nak-with-delay on one consumer (measured to starve); one consumer per tier (confines starvation to a tier, at the price of six budgets nobody can size from first principles) |
| Containerising **all three** services, not just the new one | the author's decision, 2026-08-10. The repository has never had a Dockerfile; compose ran only the four stores and the api and gateway ran from `dist/` on the host. Adding one container for the dispatcher alone would read to a reader as arbitrary — the deployable that happens to be newest is not a reason to package it differently | leaving the dispatcher uncontainerised and demonstrating its separability with `kill` instead of `docker compose stop` (smaller, and rejected); containerising only the dispatcher (inconsistent) |
| Endpoint deletion is soft | a hard delete must cascade, and cascading erases the customer's dead letters — which FR-WHK-04 says to retain for seven days. Chapter 3.2 reached the same conclusion for `api_keys.revoked_at`, and the foreign keys are `ON DELETE NO ACTION` to make the wrong choice impossible rather than merely discouraged | hard delete with `ON DELETE CASCADE`, which trades a customer's failure record for a tidier table |

**The item left open until measurement (R1) is now closed — and it changed the
design.** Both behaviours were exercised against the compose broker on 2026-08-10.
A delayed redelivery survives a restart to within 3 ms, and messages waiting out a
delay hold acknowledgement slots the whole time: with `max_ack_pending=3`, three
messages nak'd for five minutes made two available messages unfetchable. Scaled up
that is dead customer endpoints starving healthy ones, which is precisely what
FR-WHK-05 forbids and precisely what no amount of code review would have caught.

The plan's instruction was to stop and re-plan rather than adapt in place, and that
is what happened: the schedule moved out of the broker and into a column, the api
gained a second relay (R13), and expansion became N rows in one transaction instead
of N publishes after a claim — which removed a dual write the original plan had
accepted. SAD §4.1's "JetStream redelivery + a scheduled-retry stream" named both
candidates; the measurement is what turned the sketch into a choice.

**The cost is honest**: three more fences and a bigger chapter. The benefit is an
isolation property that holds structurally rather than by tuning.

**Constitution VI, and the thing that would quietly break it.** Feature 024's
coverage instrument and CI job cover the packages and services that existed when it
was written. A new deployable that is not added to both would sit outside the
measurement while every existing ratchet stayed green — the failure mode where an
instrument reports comfortably about the wrong thing. Wiring the dispatcher into
`vitest.coverage.config.mts` and `ci.yml` is therefore part of creating it, not a
follow-up.
