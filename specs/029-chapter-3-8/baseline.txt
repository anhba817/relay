T002a — a global drain, through a door chapter 3.7 did not check
-----------------------------------------------------------------

  FAIL  dispatcher.itest.ts > the dispatcher >
        invariant 7: delivers an event the endpoint subscribes to
        AssertionError: expected 0 to be greater than 0

  FAIL  dispatcher.itest.ts > the dispatcher >
        JSON that is not an envelope is terminated too, not retried
        Error: Test timed out in 60000ms

NOT this chapter's work, and separated before starting — T005's rule, and chapter
3.7's four-hour lesson about a lane that cannot report its own faults.

MEASURED, not inferred:

  dispatcher suite alone                          16 passed, exit 0
  integration lane, three runs                    3 clean, 188-190 s each
  coverage lane, run 1                            2 failed
  coverage lane, run 2                            380 passed
  due deliveries after a coverage run             0 (drained by the run itself)
  pending deliveries after a coverage run         98

ROOT CAUSE. The suite's `publishDue()` helper builds a delivery relay and calls
`drainOnce()` with **no batch size**, so it takes `BATCH_SIZE = 50` — the fifty
oldest due deliveries in the platform, `ORDER BY next_attempt_at`, oldest first.
This suite's own delivery is the newest. Every earlier suite in the run leaves due
deliveries behind, and once more than fifty accumulate the batch fills before
reaching the one under test. `pollUntil` then times out at eight seconds and the
endpoint has received nothing.

WHY ONLY THE COVERAGE LANE. `vitest.coverage.config.mts` sets
`fileParallelism: false` — every suite in one process against one database — so
the dispatcher suite runs after everything else has filled the queue. The
integration lane runs packages separately and its dispatcher suite starts clean.
Three integration runs found nothing; one coverage run in two did.

WHY IT READS AS A FLAKE AND IS NOT. The failing run **drains the backlog itself**,
so the next run passes. One-in-two today, and it returns whenever the backlog
rebuilds past fifty.

THE SIXTH INSTANCE OF ONE SHAPE. Chapter 3.7's baseline found four tests asserting
a local fact about a global operation, and fixed `drainDueDeliveries` in
`deliveries.itest.ts` twice — an explicit limit for the sweep, and a settle loop
for the drain. It never looked at `dispatcher.itest.ts`, which reaches the same
global drain through a different door. Analysis pass 10 found a fifth instance in
this chapter's own plan. This is the sixth.

FIXED, ahead of any chapter work: `publishDue()` now passes `batchSize: 10_000`.

  coverage after the fix                          380 passed, exit 0

HONEST LIMIT ON THAT EVIDENCE. One passing run does not prove a fix for an
intermittent failure. The confidence comes from the mechanism — a global
oldest-first batch of fifty against a newest-row assertion — not from the run. A
deterministic reproduction would mean seeding fifty-one due deliveries older than
the test's own, and it was not built.

T022 — what the `strictObject` change broke
--------------------------------------------

Making `request_id` required on `errorFrameSchema` broke **two** construction
sites, and they were found by two different mechanisms:

  services/gateway/src/session.ts    `sendError`        the compiler
  packages/protocol/src/frames.test.ts  the fixture     the test run

Research R13 predicted the first and named it as the reason the field could not
simply be added: the gateway minted no ids at all, so there was nothing to put
there. It now mints one per answered frame, and callers pass the id of the frame
they are answering.

TWO IS FEWER THAN EXPECTED, and the reason is worth noting. The error frame is
constructed in exactly one place in the gateway and nowhere else in the platform —
the REST envelope is built by `ProtocolErrorFilter` and `service-kit` separately,
and neither uses the frame schema. A shape shared by two surfaces turned out to
have three builders and one type.

T004a — FAILED AUTHENTICATIONS THE INTEGRATION LANE ALREADY PRODUCES
--------------------------------------------------------------------------------

MEASURED, not inferred. The api integration suites assert `401` or `403` 26
times, and that number turns out to have almost nothing to do with this. A 403
for a credential belonging to another environment RESOLVES its principal — it
fails authorisation, not authentication — and `AuthenticateMiddleware` counts
only the case where a Bearer credential is present and resolves to nothing. A
count of assertions is not a count of requests.

The instrument: a unique key prefix, and Redis polled once a second for the whole
lane. Polling matters because a bucket lives sixty seconds and the lane runs
three minutes, so a scan afterwards reads an almost-empty database — the first
attempt found 2 and reported it, which was wrong by a factor of twenty.

The first POLLER was also wrong, and in a way worth writing down: it ran one
`docker compose exec` per key, so a nominal five-second cycle took far longer
than five seconds and missed buckets that live for sixty. A measurement
instrument slower than the thing it measures reports zeros and looks calm.

Highest value seen per bucket, over one full green lane:

  rlauth:::1:<w>                                  8    default prefix, ::1
  rlauth:::1:<w>:signup                          13    default prefix, ::1
  rlauth:::ffff:127.0.0.1:<w>                     2    default prefix, IPv4-mapped
  rlauth-itest-<t>:::1:<w>                        4    credentials.itest.ts
  rlauth-signup-<t>:::1:<w>:signup                3    signup.itest.ts
  rlauth-fleet-<t>:198.51.100.0..9:<w>       1 each    the ten-addresses test

  15 buckets, 40 failed authentications in total.

AGAINST THE PROPOSED THRESHOLD OF 10 PER MINUTE PER ADDRESS, one bucket reaches
8 and one reaches 13. The lane is green, and the reason it is green is worth more
than the numbers.

`credentials.itest.ts` and `signup.itest.ts` both raise
`RELAY_AUTH_FAILURES_PER_MINUTE` to 10000 and NEITHER sets a key prefix. Vitest
gives each file its own worker, so the raised threshold is private to that
process — but the Redis bucket is not. Those two suites push a SHARED bucket to 8
and 13 while being personally immune to it, and any suite running in the same
minute, from the same address, at the default threshold would be refused by
traffic it did not generate.

Today nothing is, and only by accident: the polluting suites reach the api
in-process over `::1`, while the suites that spawn a child reach it over
`::ffff:127.0.0.1`, which is a different bucket. Two address formats are the
whole of the isolation.

FIXED, because it is two lines and the alternative is a lane whose isolation
depends on two address formats nobody chose. Both suites now set their own key
prefix beside the threshold they were already raising. Re-measured over another
full green lane:

  rlauth:::1:<w>                                  1    (was 8, and 13 for signup)
  rlauth:::ffff:127.0.0.1:<w>                     2    unchanged
  rlauth-credentials-<t>:::1:<w>                  7    now its own bucket
  rlauth-signup-<t>:::1:<w>:signup               13    now its own bucket
  rlauth-itest-<t>, rlauth-fleet-<t>, …    4, 1×10    unchanged

  16 buckets, 40 failed authentications — the same forty requests, and the
  default bucket now peaks at 2 against a threshold of 10.

The count of failed authentications did not change, which is the point: nothing
about the lane's traffic moved. What moved is which bucket it lands in, and
whether a suite that raises its own ceiling can quietly spend somebody else's.

THE RULE THIS SETTLES, for the suites that come after: raising the threshold and
taking your own prefix are two different protections and a suite that needs one
usually needs both. Raising it protects the suite from the lane. Taking a prefix
protects the lane from the suite.
