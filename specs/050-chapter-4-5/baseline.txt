T025/T026 — THE CAP, AND THE DIRECTION
    MAX_BUFFERED = 4_000, the meter's number, and it means the same thing only
    because of the retention rule: a buffer that emptied on every flush regardless of
    outcome could never reach a cap at all.
    TWO RECORDS PER CONNECTION here against the meter's one per (connection, period).

    DROP THE OLDEST — and the meter's ARGUMENT DOES NOT TRANSFER. The meter drops
    the oldest because under-counting is "the same direction as every other loss in
    this design": it is a bill, and billing for a socket nobody holds is the worse
    error. A connection log is not a bill; both directions lose a fact.
    Oldest anyway, for a different reason: dropping the NEWEST discards the records
    describing the outage itself, which is the window an operator opens this log to
    see.

T036 — THE UNAUTHENTICATED CASE CANNOT ARISE
    open() (session.ts:912) is the only function that builds a Connection and the only
    caller of registry.add. It takes `identity: Identity`, NOT optional. Its single
    call site is reached only after every refusal has returned:

        429 on the upgrade    over the establishment limit
        4001                  invalid or expired token
        1011                  the api could not answer
        4003                  user banned
        4008                  quota exhausted

    Three of those COMPLETE the handshake in order to close it, so an unauthenticated
    SOCKET exists and an unauthenticated CONNECTION does not. There is no record for a
    tenantless arm to carry, and 4.4's `_none` arm is unnecessary rather than declined.
    Not a decision this phase made — one the anchor choice had already made, on
    grounds (the meter's asymmetry) that nobody had connected to this question.

    AND `MAX_CONNECTIONS_PER_USER = 5` REFUSES THE SAME WAY. The sixth socket for one
    user gets close 4004 on that same path, before open(), so it produces no record
    either. T037's N has to be spread across users or the 2N assertion measures the
    cap.

T078 — A CLEAN STOP AND A KILL BOTH PRODUCE OPENS WITH NO CLOSES
================================================================================
Five connections held past two flush intervals, then the process ended two ways:

    balance-clean    5 connections -> records: opened 5 | meter billed:  5 connection-minutes
    balance-killed   5 connections -> records: opened 5 | meter billed:  0 connection-minutes

**THE ARTIFACTS PREDICTED THAT A CLEAN RUN BALANCES AND A KILLED ONE DOES NOT. NEITHER
BALANCES.** `sessions.close()` is, in full: stop the heartbeat, stop the meter, send a
final report, `releaseAll` the held slots, and `wss.close()`. **`wss.close()` stops the
server accepting and does NOT close established sockets** -- which `session.ts` already
says in the comment that put `releaseAll` there. So no per-socket `close` handler fires,
`connectionLog.closed(...)` is never called, and there are no close records on either
path.

**AND THE METERS DIVERGE IN OPPOSITE DIRECTIONS.** On the clean stop `reportOnce` walks
the registry, which still holds all five, and bills **5**. On the kill there is no
shutdown, no final report, and it bills **0**. So against the records:

    clean   meter 5, records 5 opens / 0 closes    the meter over-reports the pair
    killed  meter 0, records 5 opens / 0 closes    the RECORDS over-report the pair

**THIS IS FR-009a's WHOLE ARGUMENT, MEASURED.** Analysis pass 4 found that `reportOnce`
builds from `[...closedNow, ...open]` and therefore bills connections that have no close
record. Here that is a number, and the kill case supplies its mirror image. Scoping the
reconciliation to connections with BOTH records present -- over a window every one of
them closed inside -- is what leaves the comparison with two causes instead of four. The
three runs above agreed precisely because they were scoped that way; unscoped, run 1
would have compared 8 against 0.

    NOT A DEFECT TO FIX HERE. Leaving established sockets to the process exit is the
    deploy posture NFR-REL-03 and `releaseAll` were built around, and this chapter's
    producer follows the meter rather than changing it. It is a property a dashboard
    built on these records must tolerate, and the number a reader needs is above.
