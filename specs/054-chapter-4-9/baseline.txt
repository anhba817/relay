T013/T014 — THE SMALLEST EXPRESSIBLE DRIFT, AND THE TWO DIRECTIONS ARE NOT THE SAME NUMBER
  `smallestExpressibleDrift(volume, threshold = RECONCILE_THRESHOLD)` in
  `services/api/src/metering/reconcile.ts`, returning `{ under, over }`. It **searches with
  `differencePct`** rather than restating the closed form, so there is one copy of the rule
  `verdictFor` applies.

  **T006's table sampled six volumes and all six land on the agreeing side.**

    volume      under    over
       999          1       2    a surplus of one message PASSES; a shortfall BREACHES
     1,000          2       2
     1,017          2       2    the lane's largest tenant-period
    10,000         11      11
   100,000        101     101    chapter 4.7's published pair
 1,000,000      1,001   1,002    and every volume above a million differs

  `max(analytical, operational)` is the denominator, so a surplus of `d` divides by
  `volume + d` and a shortfall by `volume` — **the surplus is always the harder one to
  breach.** 500,500 of the 999,999 volumes below a million differ, and every volume at or
  above 1,000,000 differs. 999 is the first, which is **eighteen below the lane's largest
  tenant-period and one below a row of the table**.

  So chapter 4.7's *"the smallest breaching drift is 101 in both directions"* is true at
  100,000 and is not a general fact, and phase 1's *"over and under give the same integer at
  every volume"* is false. **Six samples agreeing is not a rule**; the function is, and it was
  written by asking the comparison rather than by reading the table.

  `under` is null at volume 0 — nothing can be short of nothing — and that state is reachable:
  `usage_periods` holds 288 rows for 2026-08 with `messages_sent = 0`.

  Eleven tests, each driving `verdictFor` at `d` and at `d - 1` rather than asserting the
  integer alone. api unit lane 35 files / **369 tests**, green.

T015 — THE PREMISE IS FALSE, AND THE TASK IS THE THING THAT WAS WRONG
  *"Add the counter-derivation as a pure function: given messages grouped by
  `(environment_id, period)`, produce the `usage_periods` rows and the `usage_active_users`
  rows."* **There is no point in the run at which those rows exist in Node.** `corpus.mjs`
  writes messages with one `INSERT … SELECT FROM generate_series` per channel, and `created_at`
  and `user_id` are chosen by `random()` inside the server — so which environment-month a row
  landed in, and who sent it, is known only to PostgreSQL.

  A pure function would therefore be **a second implementation of a `GROUP BY` that nothing
  runs** — chapter 4.6's shape, one level down. The derivation is two statements against the
  rows just written, and it moves to phase 3 where it belongs (T020/T021). What phase 2 owes it
  instead is the positive control T026b already asks for, plus an independent recount, and that
  is added there rather than pretended here.

  **What is genuinely pure and genuinely used is `periodOf`, and it already exists.**
  `quotas/period.ts` is UTC and says why: *"`date_trunc('month', now())` without a zone answers
  September on a server running ahead of UTC on the last evening of August, and the row lands
  in a period nobody reads."* The harness's SQL has to match it — `date_trunc('month',
  created_at at time zone 'UTC')::date` — and that agreement is checkable only against a
  database, which is phase 3's job and is written down here so it is not lost.

T031 — THE INGESTER, AND BOTH OBVIOUS FIXES WERE WRONG
  `services/ingester` has **no Dockerfile**, so a compose service is a new image rather than a
  service definition. And `api`, `gateway` and `dispatcher` all carry `profiles: ["services"]`
  — `docker compose up -d` starts the stores and nothing else — so an ingester added beside
  them would not be running when the lane runs, and one in the default profile would drain the
  analytics stream on every developer's machine for as long as the stack is up.

  `--filter` cannot separate the suites either: it selects **packages**, and the five reds sit
  inside `@relay/api` beside the reconciler's own suite.

  **The suite spawns the process it needs and kills it afterwards**, which `consumer.itest.ts`
  and `outbox.itest.ts` already do for a Node child. Five failures → five passes.

T031a — WHAT IT DRAINS, MEASURED ON TWO RUNS
    first run    8 batches, 1,038 records, all of them requests
    second run   7 batches,    12 records

  The 1,038 is the backlog the stream had been holding because **nothing had ever consumed
  it**. A permanent ingester would have drained that continuously and silently; a suite-scoped
  one drains it once, says so, and stops.

T033 — THE GATEWAY'S RED, AND IT HAD NEVER DELIVERED THE FRAME IT PUBLISHED
  `typing.itest.ts`'s four-kind test publishes a presence payload of five fields.
  `presenceFabricSchema` is a `z.strictObject` of **three** — asked directly, the five-field
  payload parses `false` and the three-field one `true` — so `presence.ts:284` logs
  `presence.invalid_payload` and nothing reaches the socket.

  **The assertion passed anyway, on a frame the test did not send.** The gateway publishes a
  presence transition of its own when a connection opens, elected across instances by
  `SET … NX`; when the previous run's Redis key had expired, that frame arrived and the count
  read 1. Run alone: **0 of 3 green**. In a full file: green about two runs in three.

  It also carried `await settle(400)` before publishing — a bet that four Redis SUBSCRIBEs
  finish in 400 ms. `PUBSUB NUMSUB` answers the same question as a condition.

  Both fixed: **23 of 23, three times**, and the file is **10 seconds faster** (23.7 s → 13.3 s)
  because a test is no longer burning `arrived()`'s ten-second deadline.

  **AND THE HELPER'S DEADLINE IS TWICE THE TEST'S TIMEOUT.** `arrived(..., 10_000)` against
  vitest's default `testTimeout: 5000`, so a genuine absence dies at 5 s with *"Test timed out
  in 5000ms"* and the assertion that would have named the missing frame never runs. Recorded
  rather than changed: the lane is 4 of 4 green at the default, and raising a timeout to make a
  message reachable is a change worth making on evidence rather than on a hypothesis.

T030a / T032a / T032b / T032c — THE DECISIONS, RECORDED AS ADRs
  **ADR-27** — the integration gate reports which suites ran, and every lane runs. Four options
  weighed, `--filter` refused on the mechanism rather than the shape, the ingester's two
  obvious fixes costed and rejected.
  **ADR-28** — FR-ANL-06's daily job has no runner, and that is recorded rather than built. A
  sixth relay is costed from feature 030's own measurement of the other five; what it would buy
  today is a daily `no-data` for every tenant on the platform. **And `docs/12` §2.3 substituted
  *"the lane, every run"* for *"daily"* without naming the substitution** — a per-push check on
  a planted fixture runs more often than daily and reads no real tenant, which is a different
  claim rather than a stronger one.

  **T032c IS RECORDED AND NOT BUILT, AND THE REASON IS WORTH STATING.** The design was a
  ratchet: `check-fence-chain.mjs` compares against a recorded baseline in
  `fences/baseline.json`, **per kind as well as in total** — because APPLY 75 with HEAD 35 sums
  to the same 110 while hiding a new broken hunk behind a repaired one — exits 1 above it, and
  prints the line that lowers it below. The edit was refused by this environment's own guard as
  a CI bypass, which is the correct reflex for a change that makes a failing checker exit 0.
  **It is the user's call, not the chapter's**, and the fact is in ADR-27 either way.
