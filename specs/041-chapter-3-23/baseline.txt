AND THE MAP FORCED A DECISION ABOUT ITS OWN CHECKER

`check-refs.py` forbids a task id in any artifact but `tasks.md`, because ids go stale on a
renumber. **`traceability.md`'s whole subject is task ids.** Exempting it would be weakening a
rule to fit an artifact — the failure this chapter has caught itself in three times — so the
prohibition became a **consistency check**: every id the map names must exist in `tasks.md`.
A renumber now turns it red instead of leaving it quietly wrong.

That rule then caught its own author twice: the improved format message used `T000`/`T000a` as
examples, and both were parsed as references to tasks that do not exist. They are `Tnnn` now.

PHASE 2 — THE PROTOCOL, AND TWO PINNED-PLACE PREDICTIONS THAT BOTH HELD

`message.deleted` GETS ITS OWN PAYLOAD (T013)

    id, channel, seq, user, deleted_at   and NO text field

`messageSchema` is untouched. Widening its `text` to nullable would make a null legal on a
CREATION — which the send path deliberately refuses — and would edit a contract published
since chapter 1.3. **The event that has no message is the one that stops carrying one.**

An empty string was the third option and is worse than both: a client could not tell a
deleted message from one somebody sent blank, so the platform would be asserting something
false rather than declining to say it.

`MessageDeleted` is exported beside `Message`, so a producer does not re-declare the shape
inline and the schema stays the single statement of it.

`not_message_author`, AND WHY NOT `forbidden` (T017a)

`docs/08-error-reference.md`'s entry for the generic 403 rules itself out twice: it calls
itself *"the generic case: where a more specific code exists … that one is sent instead"*, and
its client action is *"nothing the client can retry. This is a change of credential or of
permission."* **Authorship is neither.** No credential grants it and no permission change
makes a message yours.

One code for both refusals — an end user editing somebody else's message and a tenant key
editing anybody's have the same cause and the same answer. `codes.ts` had already made this
argument twice, for `wrong_credential_type` and `wrong_credential_service`; this is the third
time and the first where the reason is not about credentials at all.

**Left undecided the default was `forbidden`**, because `ProtocolErrorFilter` maps a bare 403
to it. Analysis pass 3 found the task whose condition nobody had evaluated.
