T002 — THE TWO PERFORMANCE BASELINES, TAKEN BEFORE ANY CODE CHANGE
-------------------------------------------------------------------

Taken on this lane, not quoted from `docs/11-scalability-measurement-2026-09-06.md`. Those
figures came from one gateway on a 28-core host with the load generator beside it, and a
criterion that names them is one nobody can check anywhere else.

**SC-004 — the reconnect rate.** Three runs, 10,000 connections each, nothing else running.

    run 1   10000/10000 survived · 7066 ms · 1415/s · RSS 255 MB · 11,000 subjects
    run 2   10000/10000 survived · 7046 ms · 1419/s · RSS 262 MB · 11,000 subjects
    run 3   10000/10000 survived · 7289 ms · 1372/s · RSS 263 MB · 11,000 subjects
    ----------------------------------------------------------------------------
    mean 1402/s · min 1372 · max 1419 · spread 47/s over three runs

    SC-004's band, ±10%:   1262 — 1542 connections per second

**SC-005 — what a revision costs.** Two runs of 200 edits and 200 deletes each, over HTTP,
because that is the path a customer's revision takes.

              mean      p50      p95
    edit     10.28    9.46    19.47      run 1
             11.44   11.79    20.95      run 2
    delete    4.65    4.28     8.53      run 1
              3.83    3.66     6.84      run 2

    SC-005's band, ±10% of the two-run mean:  edit 9.77 — 11.94 ms · delete 3.82 — 4.67 ms

**An edit costs roughly twice a deletion**, and that is expected rather than surprising: the
edit path writes the message row AND an immutable history row in `message_edits`, where the
deletion writes the tombstone alone. The counter this feature adds is one UPDATE on both
paths, so it should move the delete's percentage more than the edit's.

**THE BAND IS WIDE BECAUSE THE RUN-TO-RUN SPREAD IS.** Edit means differ by 1.16 ms between
two runs of the same unchanged code — 11% of the smaller. **A 10% criterion against a
measurement whose own noise is 11% cannot distinguish a regression from a Tuesday**, and the
honest thing is to say so now rather than to discover it at close-out. T032 re-measures with
more runs, and if the noise still swamps the threshold the criterion moves to the p50 or the
run count goes up — recorded as a decision, not adjusted quietly.

THE SCAN WAS RUN TWICE AND THE FIRST RUN LIED. `grep` on this machine is **ugrep
7.8.4**, not GNU grep, and under it a grouped alternation followed by two negated
character classes — `(postgres|redis)://[^:/@]+:[^@/]+@` — matched NOTHING, while the
identical pattern without the group matched. It reported the DSN pattern as 0 hits on a
corpus containing that DSN twice. A second pattern reported 0 for a different reason:
it required a closing quote after the base64 blob, and `RELAY_WEBHOOK_SECRET_KEY=…` has
none.

Two of sixteen patterns silently reported clean on material that was present. **A
credential scan that cannot fail is worse than no scan**, because it is filed as
evidence. The re-run is in Python with a positive control per pattern, and the control
is the point: a pattern that does not match its own example is reported as BROKEN rather
than as zero. That check is what turns "0 hits" into a claim about the corpus.
