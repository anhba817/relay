                   ->  Seq Scan on messages m  (cost=0.00..6837.46 rows=201253 width=32) (actual time=0.010..29.124 rows=198690.00 loops=1)

  READ THE PLAN, NOT THE CLOCK.

    ->  Bitmap Heap Scan on messages m
          Recheck Cond: (c.id = channel_id)
          Filter: (created_at >= date_trunc('month'::text, ...))

  The month predicate is a **Filter**, not an Index Cond. Every message the
  environment has ever sent is read off the heap and then discarded if it is not
  this month's. 507 rows today, and the number only goes up — there is no index on
  `messages.created_at`, and `messages` carries no `environment_id` at all.

  THE TIMING MOVED AND THE ARGUMENT DID NOT. Research R1 recorded 1.189ms with
  3.035ms of planning; this run measures **0.266ms with 0.743ms of planning**. The
  difference is a cold cache versus a warm one — R1's was the first execution of a
  query the planner had never seen. Neither number is wrong and neither is the
  point: at 507 messages both are fast, and the chapter's case is the `Filter`
  line, which does not depend on a clock.

  The chapter quotes the plan. If it quotes a duration it says which cache state
  produced it, because an unqualified 1.189ms invites a reader to check it, get
  0.266ms, and conclude the argument was inflated.

T004 / T005 — THREE LANE RUNS, AND WHAT THE THIRD FOUND
--------------------------------------------------------------------------------

  run 1  exit=0  187s  failing-files=0
  run 2  exit=0  183s  failing-files=0
  run 3  exit=1  115s  failing-files=1

  FAIL src/webhooks/deliveries.itest.ts >
       counts what is pending and stops counting it once it is delivered
  AssertionError: expected 22741 to be 22742

  **INSTANCE 12, AND IT IS THE BASELINE'S, NOT THIS CHAPTER'S.** The test read the
  global `pendingDeliveryDepth`, delivered one row, and asserted the count fell by
  exactly one. Its own comment defended the shape:

      // GLOBAL, and asserted as a delta for that reason — this is the number an
      // operator watches, so it counts every tenant's backlog, and another suite
      // seeding rows beside this one must not be able to break it.

  A delta is two reads with a gap. Another suite delivering one of its own rows in
  that gap moves the second read by one more, which is what 22741-against-22742
  is. Seeding was defended against; delivering was not.

  That makes three of the twelve occurrences whose defence was a comment saying
  why this one was fine. Feature 030's spec opens on the same observation — the
  sixth instance was written by someone who had recorded the other five.

  Fixed forward in its own commit, ahead of any chapter work: the global function
  keeps a caller and is asked only what cannot race (there is a backlog); the
  delta is asserted against this environment's own rows.

  Twenty runs of feature 030's battery passed with this in the tree, and three
  runs here found it. Nothing about the fault is rare — the lane had simply not
  been run with two suites landing in the same gap.

T018 — WHAT THE SEND PATH GAINED
--------------------------------------------------------------------------------

  FR-020 forbids a query that SCANS the message table. The transaction does gain
  two statements, and neither scans anything:

    1. the roll-up increment
       Insert on usage_periods
         Conflict Resolution: UPDATE
         Conflict Arbiter Indexes: usage_periods_pkey
         Buffers: shared hit=25
       Execution Time: 0.357 ms

    2. the distinct-user membership
       Insert on usage_active_users
         Conflict Resolution: NOTHING
         Buffers: shared hit=60
       Trigger for constraint usage_active_users_environment_id_fkey: time=0.687
       Trigger for constraint usage_active_users_user_id_fkey:        time=0.311
       Execution Time: 1.304 ms

  No `Seq Scan` in either plan. The primary key is the arbiter index, which is
  what storing the period rather than computing it buys.

  THE HONEST LINE IS THE SECOND STATEMENT'S. Two foreign-key constraint triggers
  cost 0.998ms of its 1.304ms — more than the insert itself. That is the price of
  the membership row being a real row with real references, and it is paid on
  every ATTRIBUTED send. An unattributed send skips it entirely.

  Compare against the query this design refused: 0.266ms warm for one environment
  of 507 messages, growing with the tenant's lifetime traffic. The two new
  statements are flat.
