T015  WHAT THE NEW CONSTRAINTS COST, AND ONE OF THEM WAS 21x TOO EXPENSIVE

      First measurement, 6,646 rows, heap 1,540,096 B (1,504 kB):

        media_objects_id_environment_key      352,256 B   344 kB   22.9% of heap
        media_objects_parent_rendition_key    172,032 B   168 kB   11.2%
        media_objects_parent_idx (partial)     16,384 B    16 kB    1.1%
        ---------------------------------------------------------------
        added                                 540,672 B            35.11% of heap

      **`UNIQUE (parent_id, rendition)` as a table constraint cost 168 kB to police zero
      rows.** A btree indexes NULLs, so it covered all 6,646 uploads to enforce
      uniqueness among the rows with a parent, of which there were none. Rewritten as a
      partial unique index over `parent_id IS NOT NULL`: **8,192 bytes**, a 21x
      reduction, and re-run to check that making it partial had not made it decorative —
      the duplicate is still refused by name. Added cost is now 376,832 B, 24.5%.

      **344 kB of that is constitution I's price and is not reducible.** The unique on
      `(id, environment_id)` adds no uniqueness the primary key lacks; it exists only
      because Postgres requires the referenced columns of a composite foreign key to
      carry a unique constraint. Every row can be a parent, so it cannot be partial.

      **THE FILE WAS EDITED AFTER IT HAD BEEN APPLIED**, which is the hazard 0019's own
      comment names: `schema_migrations` is `(version, applied_at)` with no checksum, so
      the runner skips an edited applied file in silence. 0020 is unreleased — written
      and applied minutes earlier in this session — so the lane was brought to match the
      edited file by hand (`DROP CONSTRAINT` then `CREATE UNIQUE INDEX`). CI and a fresh
      clone see only the edited file. Recorded because the next person to edit an applied
      migration will not have that excuse.

T017  `unreferencedMediaIn(db, environmentId, olderThan, limit)` — FR-MED-10's predicate.

      **A RENDITION IS NEVER RETURNED, AND THAT IS THE WHOLE OF FR-002.** The obvious
      reading — "a rendition is unreferenced when its parent is" — would have the reaper
      delete parent and rendition separately and depend on the order. It does not need
      to: `media_objects_parent_fk` is ON DELETE CASCADE, so the predicate asks only
      about uploads and the renditions follow. *"Its reachability is its parent's"* is
      discharged by the foreign key rather than by a second arm somebody keeps in step.

      **TWO QUERIES, NOT ONE, AND 4.12 MEASURED WHY.** The natural single statement puts
      `NOT EXISTS (… attachments @> … m.id …)` against each candidate, which builds the
      containment operand from a column on the other side of the join — a GIN index
      cannot be looked up with a value the planner does not have yet (1,042 buffers
      against 84). Candidates come back first; their ids go into the second query as
      bound values. **The first draft was THREE queries** — the middle one returned
      channels when what was needed was media ids — and was simplified before it ran.
