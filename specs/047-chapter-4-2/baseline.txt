T001 — CLICKHOUSE ANSWERS /ping AND REFUSES EVERY QUERY
-------------------------------------------------------
    $ curl -s "http://localhost:${RELAY_CLICKHOUSE_HTTP_PORT:-8123}/ping"
    Ok.

    $ curl -s "http://localhost:${RELAY_CLICKHOUSE_HTTP_PORT:-8123}/?query=SELECT+1"
    Code: 194. DB::Exception: default: Authentication failed: password is incorrect,
    or there is no user with such name. ... (REQUIRED_PASSWORD)

The premise holds, and the chapter's opening stands: the store has been in compose since
chapter 1.2, its health check has been green throughout, and nothing outside the container
could ever query it.

AND THE TWO HALVES DO NOT NAME THE SAME MECHANISM, which is worth writing down before the
prose does. The document says `default` is restricted to ::1 and 127.0.0.1 — that is a
NETWORK restriction, and T002 quotes it. What a caller from outside actually receives is an
AUTHENTICATION error naming a password. Both are true of the same refusal; only one of them
is what the reader will see in their terminal, and the chapter should show that one.

T009/T010 — THE AMENDMENT WORKS, AND THREE THINGS THE TASK DID NOT EXPECT
-------------------------------------------------------------------------
    as relay, from the host      SELECT 1  ->  1
    as default, from the host    SELECT 1  ->  Code: 194 ... (REQUIRED_PASSWORD)
    container health                          healthy

(1) `CLICKHOUSE_DB` CREATED NOTHING, AND THE LOG SAYS WHY.

    clickhouse-1 | ClickHouse Database directory appears to contain a database;
                   Skipping initialization

    SHOW DATABASES  ->  INFORMATION_SCHEMA, default, information_schema, system

The entrypoint honours `CLICKHOUSE_DB` only while INITIALISING an empty data directory.
The `clickhouse-data` volume has held a database since chapter 1.2, so the variable is
read and ignored — and it will be ignored for every reader who has followed the tutorial
in order. **`apply.mjs`'s `CREATE DATABASE IF NOT EXISTS` is therefore not a belt-and-braces
step; it is the only thing that creates the database on any stack that has ever been up.**
Analysis pass 5 reasoned its way to that bootstrap from a different direction — that the
variable does not set the SESSION default — and it turns out the variable is weaker still.

(2) THE ENTRYPOINT REWROTE THE FILE T002 QUOTES AS EVIDENCE.

`/etc/clickhouse-server/users.d/default-user.xml` now reads:

    <default remove="remove"></default>
    <relay><profile>default</profile><networks><ip>::/0</ip></networks>
           <password><![CDATA[relay]]></password> ... </relay>

So `default` is no longer network-restricted — **it is removed.** The chapter's opening
quotes a file that this chapter's own fix overwrites, and a reader who applies the
amendment and then looks will find something else. Both states have to appear in the prose,
in that order, or the evidence contradicts the page it is on.

(3) AND BOTH STATES RETURN THE SAME ERROR, WHICH MAKES T001's FALSIFICATION VACUOUS.

Before: the user exists and the network is refused. After: there is no such user. The
string a caller sees is `Code: 194 ... (REQUIRED_PASSWORD)` in both cases. T001 says *"if
the query now succeeds, the amendment is already present"* — but the amendment never makes
`default` succeed, so that clause cannot fire for the reason it names. **It is a test that
cannot fail.** The discriminator that does work is whether `relay` answers, and T001 is
amended to ask that instead.

A SIXTH DIVERGENCE FROM SAD 6.2 WAS FOUND WHILE WRITING THE DDL. `delivery_latency_ms`
is published as a non-nullable `UInt32` and nothing produces it until FR-ANL-10's chapter

T018a/T018b — THE SEEDER NOW PRODUCES WHAT THE CHAPTER IS ABOUT
----------------------------------------------------------------
Four knobs, defaulting to the lane's own proportions: CORPUS_EDITED_RATIO 0.0105,
CORPUS_DELETED_RATIO 0.0133, CORPUS_ATTACHMENT_RATIO 0.0074, CORPUS_NON_ASCII_RATIO 0.1.
Two new refusals in the file's existing idiom: edited+deleted may not both be 0 (the
rollup's event filter would exclude nothing) and attachments may not be 0 (JSONLength
could not be shown to differ from length).

A 29,333-message probe corpus, and the four findings as CLICKHOUSE sees them:

    user_id IS NULL                                301
    length(text) != lengthUTF8(text)             2,899     sample: 24 bytes vs 18 points
    length(attachments) vs JSONLength()             78 vs 2
    events that are not `created`                  745     (630 edit EVENTS, 425 deletes)
    messages edited 1 / 2 / 3 times          117 / 96 / 107
    edited and then deleted                          6

AND THE FIRST BUILD OF THAT CORPUS WAS WRONG IN A WAY THAT LOOKED RIGHT. It reported 864
edits over 288 messages — **exactly three each, every one of them**, and
`messages_edited_twice_or_more` equal to `messages_edited`, which is what gave it away.

    cross join lateral generate_series(1, 1 + floor(random() * 3)::int)

evaluates the volatile argument **once for the whole query**, not once per row. A 10-row
probe of the same shape returned 10 rows — one each. **It picks a constant at random per
query**, so it reads as random if you run it once and never compare two runs. Precomputing
`k` in a subquery makes it per-row: the same probe returns 19, and the corpus returns the
117/96/107 above. Reporting the counts rather than asserting them is what caught it.
