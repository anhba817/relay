T009/T010 — THE AMENDMENT WORKS, AND THREE THINGS THE TASK DID NOT EXPECT
-------------------------------------------------------------------------
    as relay, from the host      SELECT 1  ->  1
    as default, from the host    SELECT 1  ->  Code: 194 ... (REQUIRED_PASSWORD)
    container health                          healthy

(1) `CLICKHOUSE_DB` CREATED NOTHING, AND THE LOG SAYS WHY.

    clickhouse-1 | ClickHouse Database directory appears to contain a database;
                   Skipping initialization

    SHOW DATABASES  ->  INFORMATION_SCHEMA, default, information_schema, system

The entrypoint honours `CLICKHOUSE_DB` only while INITIALISING an empty data directory.
The `clickhouse-data` volume has held a database since chapter 1.2, so the variable is
read and ignored — and it will be ignored for every reader who has followed the tutorial
in order. **`apply.mjs`'s `CREATE DATABASE IF NOT EXISTS` is therefore not a belt-and-braces
step; it is the only thing that creates the database on any stack that has ever been up.**
Analysis pass 5 reasoned its way to that bootstrap from a different direction — that the
variable does not set the SESSION default — and it turns out the variable is weaker still.

(2) THE ENTRYPOINT REWROTE THE FILE T002 QUOTES AS EVIDENCE.

`/etc/clickhouse-server/users.d/default-user.xml` now reads:

    <default remove="remove"></default>
    <relay><profile>default</profile><networks><ip>::/0</ip></networks>
           <password><![CDATA[relay]]></password> ... </relay>

So `default` is no longer network-restricted — **it is removed.** The chapter's opening
quotes a file that this chapter's own fix overwrites, and a reader who applies the
amendment and then looks will find something else. Both states have to appear in the prose,
in that order, or the evidence contradicts the page it is on.

(3) AND BOTH STATES RETURN THE SAME ERROR, WHICH MAKES T001's FALSIFICATION VACUOUS.

Before: the user exists and the network is refused. After: there is no such user. The
string a caller sees is `Code: 194 ... (REQUIRED_PASSWORD)` in both cases. T001 says *"if
the query now succeeds, the amendment is already present"* — but the amendment never makes
`default` succeed, so that clause cannot fire for the reason it names. **It is a test that
cannot fail.** The discriminator that does work is whether `relay` answers, and T001 is
amended to ask that instead.

T018a/T018b — THE SEEDER NOW PRODUCES WHAT THE CHAPTER IS ABOUT
----------------------------------------------------------------
Four knobs, defaulting to the lane's own proportions: CORPUS_EDITED_RATIO 0.0105,
CORPUS_DELETED_RATIO 0.0133, CORPUS_ATTACHMENT_RATIO 0.0074, CORPUS_NON_ASCII_RATIO 0.1.
Two new refusals in the file's existing idiom: edited+deleted may not both be 0 (the
rollup's event filter would exclude nothing) and attachments may not be 0 (JSONLength

A 29,333-message probe corpus, and the four findings as CLICKHOUSE sees them:

    user_id IS NULL                                301
    length(text) != lengthUTF8(text)             2,899     sample: 24 bytes vs 18 points
    length(attachments) vs JSONLength()             78 vs 2

AND THE FIRST BUILD OF THAT CORPUS WAS WRONG IN A WAY THAT LOOKED RIGHT. It reported 864
edits over 288 messages — **exactly three each, every one of them**, and
`messages_edited_twice_or_more` equal to `messages_edited`, which is what gave it away.

    cross join lateral generate_series(1, 1 + floor(random() * 3)::int)

evaluates the volatile argument **once for the whole query**, not once per row. A 10-row
probe of the same shape returned 10 rows — one each. **It picks a constant at random per
query**, so it reads as random if you run it once and never compare two runs. Precomputing
`k` in a subquery makes it per-row: the same probe returns 19, and the corpus returns the
117/96/107 above. Reporting the counts rather than asserting them is what caught it.

T026 — WHERE THE SKIPPING ACTUALLY HAPPENS, AND WHERE IT CANNOT
----------------------------------------------------------------
    MinMax        Parts 4/4   Granules 154/154     skips nothing
    Partition     Parts 4/4   Granules 154/154     skips nothing
    PrimaryKey    Parts 4/4   Granules 131/154     skips 23

TWO OF THE THREE STAGES CANNOT SKIP ANYTHING HERE, AND THE REASON IS THE TTL. DR-09
expires raw events at ninety days and FR-ANL-05 asks about ninety days, so **after the
merge every row in the table already satisfies the date predicate** — there is nothing
for MinMax or the monthly partition to exclude. The date half of `ORDER BY (environment_id,
ts)` earns nothing on this query against this table; the tenant half does all the work,
and it is the half a reader would have been least sure about.

`ProfileEvents['SelectedParts']` remains the wrong instrument (R5): it reports 0 for this
query, silently. The plan is the evidence.


T027 — WHAT THE 44x DOES NOT PROVE
-----------------------------------
It does not prove ClickHouse is 44 times faster than Postgres. It is one query, one shape,
one tenant, on a machine doing nothing else, against a table built for exactly this
question and holding nothing else. The honest claim is narrower and is the chapter's:
**a question about a range of one tenant's rows, ordered by (tenant, time), costs 13 ms
where the same question over a row store ordered by neither costs 586** — and 4.1 already
showed that the index which would fix the row store buys a gap inside its own run-to-run
spread for +49% storage.

What it also does not prove is anything about writes. Nothing in this chapter writes to
ClickHouse on the send path, and the ingester that would is two chapters out.


PHASE 4 — A ROLLUP THAT NEVER SCANS RAW EVENTS
===============================================

T029 / T031 — WHAT THE ROLLUP COSTS
------------------------------------
                      best of 3      rows read        bytes read     days
    raw table          13.22 ms      1,052,655         ~33 MB         91
    rollup             10.66 ms            315          35,910        91
    runs [10.91, 13.02, 10.66]

    raw rows 1,241,029  ->  rollup rows 363          3,418 : 1
    busiest tenant: 1,034,194 raw rows -> 121 rollup rows     8,547 : 1

**IT READS 3,342 TIMES FEWER ROWS AND SAVES 19% OF THE TIME.** That is the honest pair and
the second number is the interesting one: at a million rows this query is already dominated
by something other than scanning, so the rollup's argument here is not latency. It is that
315 rows is what the cost looks like when the tenant grows — the raw side's 1,052,655 is
proportional to the corpus and the rollup's 315 is proportional to the calendar.

T030a — ONE ROW PER KEY PER INSERT, NOT PER EVENT
--------------------------------------------------
The whole corpus arrives in one INSERT, so `daily_usage` landed at **363 rows over 363
distinct keys** — one each — and a bare `SELECT messages` looks correct. Three separate
inserts of 1,000 rows into one key then measured:

    physical rows for that key     3
    bare SELECT messages        1000        <- wrong, and it is a plausible number
    sum(messages)               3000        <- right
    raw table, same key         3000

**The row count per key is the number of INSERTs, not the number of events.** A dashboard
written against a quiet demo reads one insert's worth and is wrong on a busy day. FR-005
confirmed in the same probe: the view included all three inserts with no rebuild.

T030 — DAY BY DAY, AND ONE DAY CAN NEVER AGREE
-----------------------------------------------
    days compared   91
    days agreeing   90
    days differing   1     2026-06-15: raw 6,220 · rollup 11,161 · difference 4,941

Ninety of ninety-one agree **exactly**. The one that does not is the oldest day in the
window, and it is structural rather than a defect: the TTL cuts at a TIMESTAMP and the
rollup's finest grain is a DAY. The view counted 2026-06-15 whole when it was inserted;
the merge then removed the rows whose ninety days had elapsed. As `now()` advances the
gap moves continuously through that day.

**AND THE FIRST VERSION OF THIS COMPARISON WAS WRONG IN A THIRD WAY, WHICH WAS MINE.** The
rollup side used `day >= toDate(now() - 90 DAY)` and the raw side `ts >= now() - 90 DAY` —
a whole day against a partial one. That accounted for 5 rows of the gap, not 4,941, but it
was still two windows rather than one. Both sides are day-aligned now; `rawQuery` keeps
4.1's timestamp form, because that comparison is against Postgres and has to stay 4.1's
question.

T032 / T034 — THE DISTINCT-USER RECONCILIATION AGREES, AND THAT PROVES ALMOST NOTHING
---------------------------------------------------------------------------------------
    uniqMerge(active_users_state)   5,000
    uniqExact(user_id)              5,000
    difference                          0      0.0000%

A perfect agreement, over a corpus holding exactly 5,000 users. `uniq` is exact to 65,000:

    distinct     uniq          error
      60,000     60,000        0%
      65,000     65,000        0%
      70,000     70,359        0.5129%
     100,000    100,315        0.315%
     500,000    502,646        0.5292%

**The threshold is a cardinality and this corpus is three orders under it.** The zero above
is a fact about the corpus, not about the reconciliation — which is why T034 exists and why
the table is published beside the zero rather than instead of it.
