**POSTGRES WILL NOT START WITHOUT THE PORT OVERRIDE.** Measured, first attempt:

    docker compose up -d postgres
    Error response from daemon: ... listen tcp4 0.0.0.0:5432: bind: address already in use

This machine's own Postgres holds 5432. `compose.yaml` maps `${RELAY_POSTGRES_PORT:-5432}`,
so the stack needs the documented override and only Postgres does:

    RELAY_POSTGRES_PORT=15432 docker compose up -d postgres redis nats clickhouse

Redis is on 6379 and NATS on 4222 with no override — chapter 3.18 spent fourteen analysis
passes repeating "Redis on 16379" without asking docker, and 16379 is a *conditional*
override from chapter 1.2 for a host that already runs its own Redis. This host does not.

**`docker compose --profile services down` DOES NOT DO WHAT THE TASK SAID.** Measured:

    docker compose --profile services down
    Container relay-clickhouse-1 Removing / Removed
    Network relay_default Removing / Removed

A profile **widens** the set `down` acts on; it does not restrict it. The command removed
every container and the network, stores included. Fifteen analysis passes carried that
command in T001 and none ran it. To stop only the app containers:

    docker compose stop api gateway dispatcher        # or: rm -sf api gateway dispatcher

`--profile services down` is correct only when tearing the whole stack down is intended.


THE LANE IS NOT IDEMPOTENT FROM COLD VOLUMES (T003)
---------------------------------------------------

Inherited from chapter 3.18's `gaps.md` item 3, not re-measured here. After
`docker compose down -v` the first `pnpm test:integration` fails and the second passes:
`ensureStream` (`services/api/src/outbox/jetstream.publisher.ts:84`) is reached from
`consumer/runtime.ts`, which the lane disables with `RELAY_EVENT_CONSUMER=off`, so no step
creates JetStream state on purpose — the first run creates it as a side effect. CI does not
see this: its runner has no volumes and its first run is the run.

Run it twice after a `down -v` and believe the second.

Chapter 3.18 closed at 41 files, 607 tests, mean 194.74 s. Re-measured, not copied.

**A RED RUN IS NOT A MEASUREMENT.** Runs 1 and 2 both reported 1 m 43 s, which looks like
a fast lane and is turbo stopping after the api package failed — dispatcher, gateway and
e2e never ran. Only the green run measures anything.

**THE GATEWAY POOL IS 11.20 s OF WALL CLOCK FOR 37.04 s OF TEST TIME** — research R18's
open question, answered. Files inside a package run in parallel, so the package's wall
clock is its slowest file and not the sum. `presence.itest.ts` joins that seven-file pool
as an eighth, and it is the one file this chapter writes that deliberately waits. The
number to watch at close-out is the gateway package's own wall clock, not the lane total:
44.5 s of headroom is plenty, and none of it is spent where this feature spends.


THE FAILING STATE, OBSERVED (T005)
-----------------------------------

`services/gateway/src/presence.itest.ts` — a watcher and a subject, both members of one
public channel, the watcher connected first. Red:

    FAIL  src/presence.itest.ts > presence: a member sees a co-member arrive
          > delivers presence.changed online to a connected co-member
    Error: no presence.changed frame within 5000ms

**RED FOR THE RIGHT REASON.** Both sockets reached `connection.ack` before the assertion,
so the fixture works and the frame is the thing missing. It asserts the POSITIVE — a frame
arrives — because "nothing arrived" is equally true of a broken harness.

**The first run was red for the WRONG reason** and is recorded rather than quietly fixed:

    Error: dev-token: 401     ❯ mintToken src/presence.itest.ts:156

`createApiKey` returns `{ credential }`, and the fixture read `key.plaintext`. A wrong
field name and a missing producer both produce a red test; only one of them is this
chapter's subject. Checking WHICH red is the whole value of T005.

**This test stays red until phase 3.** The phase 1 and phase 2 commits carry it failing on
purpose and say so in their bodies.

No existing gateway fixture provides two members of one channel — `seedSocketTenants` gives
one user per tenant — so this suite seeds its own environment, two users, one public
channel, and both memberships.
