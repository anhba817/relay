**POSTGRES WILL NOT START WITHOUT THE PORT OVERRIDE.** Measured, first attempt:

    docker compose up -d postgres
    Error response from daemon: ... listen tcp4 0.0.0.0:5432: bind: address already in use

This machine's own Postgres holds 5432. `compose.yaml` maps `${RELAY_POSTGRES_PORT:-5432}`,
so the stack needs the documented override and only Postgres does:

    RELAY_POSTGRES_PORT=15432 docker compose up -d postgres redis nats clickhouse

Redis is on 6379 and NATS on 4222 with no override — chapter 3.18 spent fourteen analysis
passes repeating "Redis on 16379" without asking docker, and 16379 is a *conditional*
override from chapter 1.2 for a host that already runs its own Redis. This host does not.

**`docker compose --profile services down` DOES NOT DO WHAT THE TASK SAID.** Measured:

    docker compose --profile services down
    Container relay-clickhouse-1 Removing / Removed
    Network relay_default Removing / Removed

A profile **widens** the set `down` acts on; it does not restrict it. The command removed
every container and the network, stores included. Fifteen analysis passes carried that
command in T001 and none ran it. To stop only the app containers:

    docker compose stop api gateway dispatcher        # or: rm -sf api gateway dispatcher

`--profile services down` is correct only when tearing the whole stack down is intended.

PHASE 2 — WHAT THE TOOLS FOUND THAT THE PLAN DID NOT
-----------------------------------------------------

Four corrections, three of them from a tool refusing to compile or lint something the
design documents had agreed on for fifteen analysis passes.

**1. ioredis is a RESTRICTED IMPORT, and presence is the limiter's case, not the
fan-out's.** `eslint.config.mjs` forbids `ioredis` outside a named list, because
"its keys are per environment; an unrestricted client is a cross-tenant read"
(constitution I). Chapter 3.18 added `services/api/src/fanout/**` with an explicit
justification — *"THE RULE'S REASON DOES NOT APPLY HERE… this client touches no keys:
it calls PUBLISH and nothing else, onto `chan:{channel_id}`"*.

**That justification does not transfer.** Presence's client touches keys and they are
environment-scoped: `presence:{env}:{user}` is exactly the shape the rule guards. So the
exemption is written against the limiter's standard instead — every key is composed from
the environment id on the authenticated connection's own identity, no key is read that was
not composed here, and there is no scan, `KEYS` or pattern read that could reach another
tenant's. Nothing in the plan or the contracts had noticed the rule existed.

**2. The four presence timings were on the wrong object, and eslint said so.** They were
mirrored onto `SessionServerOptions` as `presenceGraceMs` and friends, by analogy with
`meterIntervalMs`. The analogy is false: `attachSessions` **builds** the meter, so its
interval must arrive through it, while `fanout`, `limits` and `presence` are **injected
already built** and carry their own configuration. All four were declared, destructured,
and used by nothing. They now live only on `PresenceOptions`; a test wanting a
hundred-millisecond grace period constructs the module with it and injects that.

**3. `check-refs.py` could not see a completed task.** Its task pattern was `^- \[ \] `,
written before any box was ticked. The moment phase 2 marked its tasks `[X]` it reported
38 problems beginning with "ids are not sequential" — it had silently stopped counting
nine tasks. Fixed to `^- \[[ xX]\] ` and red-tested against a done task.

A residual, recorded rather than fixed: a bogus marker such as `[Q]` is still absorbed into
the description, because `( \[P\])?` simply does not match and the description regex is
permissive. The checker validates the markers it knows and ignores ones it does not.

**4. The gateway compiles against `@relay/protocol`'s `dist`, not its source.** The first
gateway typecheck after adding `presence.ts` to the protocol package failed with
`TS2305: Module '"@relay/protocol"' has no exported member 'subjectForPresence'`. The
package needs `pnpm --filter @relay/protocol build` first. Same class as `check:errors`
reading `packages/protocol/dist/codes.js`: a stale `dist` is a wrong answer, not an error.

PHASE 3 — WHAT WENT WRONG, AND IT LOOKED LIKE A FABRIC BUG
------------------------------------------------------------

**Test 1 passed and tests 2, 3 and 4 reported `expected [] to have a length of 1`.** The
one that passed put the subject on the same instance as the watcher; the failures were the
cross-instance cases. That reads exactly like a fabric that does not cross instances.

It is not. **A subject who came online in test 1 is still online in test 2** — the key
`presence:{env}:{user}` has a thirty-second TTL, so `SET … NX` correctly refuses and
nothing publishes. Correct behaviour under FR-006, and a shared fixture.

T016 asked for fresh channel **and user** ids per run for this exact reason and the first
implementation namespaced the channels only. The suite now seeds one subject per test.

**A second wrong assertion, from the same run.** The collector was unfiltered, so a
watcher's own arrival counted toward the subject's frames — `expected [ …(2) ]`. That is
FR-011 working: a subject shares every channel with themselves, so their own socket hears
them arrive. The behaviour was right and the assertion was wrong, and the fix made T025 a
real assertion instead of the placeholder it had been.

**THE FIRST VERSION OF THIS FILE COST 65.4 s ON ITS OWN.** Two changes halved it, and

The timings were not the dominant cost. Three describes each called `startApi()` — three

**SC-005's BOUND.** At the scaled window the `offline` arrives between `graceMs + marginMs`
and about 200 ms after it, so the overhead beyond the two configured numbers is a Redis
round trip and timer skew. At production defaults that is 30 s + 1 s + <0.2 s — about
**31.2 s** from the last close. Not sampled at production timings: one sample costs 31 s.


THE REGRESSION TEST WAS PROVEN AGAINST THE BUG
------------------------------------------------

A test that passes with and without the fix proves nothing, so the re-pin was removed and
the case re-run:

    × publishes no second online when the reconnect lands past the TTL
    AssertionError: expected [ { type: 'presence.changed', …(1) } ] to deeply equal []

That is R2a's defect, reproduced: with the key left on its refresh TTL it dies at
`last_refresh + ttlMs`, a reconnection in the gap wins `SET … NX`, and the watcher sees a
second `online` for a user who never left. Every other reconnect case in the suite lands
in the first part of the window where the key is still alive and the bug is invisible —
which is exactly what analysis pass 1 predicted before any of this existed.


PHASE 4 — WHAT WENT WRONG
---------------------------

**A real bug in `disconnected`, found while writing the tests rather than by them.** The
first implementation dropped the user from its refresh set unconditionally, so closing one
of two connections on one instance would have published `offline` — FR-006's exact
prohibition. The fix is the reason T017 exists: `session.ts` asks
`registry.connectionsFor(user)` AFTER the removal and only calls `disconnected` when
nothing local remains. The question "was that the last one here?" belongs to the registry,
not to a count presence keeps for itself.

**Four assertions were wrong in the same way, twice over.** In phase 3 a collector
attached before the subject arrived counted the watcher's own `online`; in phase 4 four
grace tests attached the collector before the subject arrived and counted the subject's.
Both times the implementation was right and the test was watching from too early. The
shape to remember: a presence test watches from the event it is about, not from setup.

**T047 IS NOT IMPLEMENTED AS WRITTEN, and this is the honest version.** It asks for a test
proving that swapping `registry.remove` and `presence.disconnected` fails. That cannot be
written without editing production code from a test. What guards the ordering instead is
the pair of behavioural cases: closing one of two connections publishes nothing, and
closing the last publishes one. With the calls swapped, `connectionsFor` counts the
closing connection, the `=== 0` guard never passes, and BOTH cases fail. The ordering is
therefore covered by an assertion rather than by a comment — which was T047's point — but
the swap itself is not exercised. Recorded rather than claimed.

PHASE 5 — WHAT WENT WRONG, FOR THE THIRD TIME IN THREE PHASES
---------------------------------------------------------------

**An unfiltered collector read a subject's own frame as a leak.** The cross-tenant test
asserted the stranger received nothing and it received `{user: "stranger", state:
"online"}` — its own arrival, in its own tenant, which is FR-011 working.

That is the third phase running in which a test watched more than it meant to: phase 3's
collector caught the watcher's own `online`, phase 4's four grace tests caught the
subject's, and this one caught the stranger's. **The shape is always the same** — a
subject shares every one of their channels with themselves, so any socket that is also a
subject sees itself.

The fix here is stronger than filtering, and the difference matters. Filtering to the
other tenant's subject would prove that ONE user did not leak; asserting that *everything
the stranger heard was about the stranger* catches any of them. A negative test that
names what must not appear is weaker than one that names what may.
