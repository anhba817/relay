## T003 — R4 re-run: what a request record costs on the stream

    1000 records = 315,000 bytes -> 315.0 bytes/record   (probe subject 53 chars)

    AND THAT NUMBER INCLUDES THE INSTRUMENT. Planning measured 313.0 on a subject 51 chars
    long; this probe's subject is 53 and read 315.0. Exactly one byte per subject character.
    Measured across three subject lengths against the same 1,000 records:

      p4.api.request.<uuid>          51 chars -> 313.0 bytes/record   (planning)
      p1r4.api.request.<uuid>        53 chars -> 315.0 bytes/record   (this probe)
      probeanal.api.request.<uuid>   58 chars -> 320.0 bytes/record   (length-matched)

    The real subject is `analytics.api.request.<uuid>` — 58 characters. So the honest figure
    is 320.0 bytes/record, and every number research.md R4 derived from 313.0 is 2% light.
    A probe stream cannot use `analytics.>` at all (R2: subjects overlap with an existing
    stream), so the length-matched prefix is how the real figure is reachable without
    publishing into the live stream.

    At 320.0 bytes/record:
      1 GiB holds                      3,355,443 records
      7-day retention is reached at    5.5 requests/second sustained
      the SAD's 24 h absorption holds  only to 38.8 requests/second

    Planning's 5.7 and 39.7 were both derived from the short-subject figure. The correction is
    small and in the direction that makes the problem arrive sooner.

## T038-T041 — R12 settled here, and R24's framing corrected by building it

    DECIDED: ONE consumer, one fetch loop, two row buffers.

    R24 claimed the split "makes DR-11's prohibited single-row insert the quieter table's
    routine case". Implementing it shows that overstated the novelty. 048's batch bound is
    2 seconds OR 10,000 rows, and the interval arm exists precisely because "a row count
    never flushes for a quiet tenant" -- so a quiet producer was ALREADY getting small
    inserts, split or no split. Two consumers would not have fixed that: a second durable
    on its own 2-second interval writes one row just as often.

    WHAT THE SPLIT ACTUALLY CHANGES IS THE RATE, NOT THE SIZE. A fetch returns when either
    bound is hit, so with requests plentiful the loop iterates faster than every 2 seconds,
    and the attempt table gets an insert per iteration rather than per interval. Bounded by
    max(batchMs, batchRows / request-rate): at 5,000 req/s a 10,000-row fetch takes 2 s and
    nothing changes; at 50,000 req/s it takes 0.2 s and the attempt table sees five inserts
    a second where it used to see one every two.

    The measurement that makes it matter, merges stopped:
      20 single-row inserts -> 20 parts, 20 rows
      1 batch of 20 rows    -> 1 part,   20 rows

    So the mitigation is the empty-buffer guard, and that guard was already there --
    `clickhouse.ts` has carried `if (rows.length === 0) return;` since 048. It was tidiness
    then and it is load-bearing now: most batches carry requests and no attempts at all.
    T041 is satisfied by code this chapter did not write, and saying so is the point.

    NOT TAKEN: per-table batch bounds, holding each buffer across fetches. It would cap the
    insert rate, and it costs the thing 048 spent a phase getting right -- a message cannot
    be acked until its row is written, so a buffer that spans fetches holds acknowledgements
    open across them.

## T046 — the table, asked of the database rather than read from the file

    CREATE TABLE relay_analytics.api_requests
    (
        `environment_id` Nullable(UUID),
        `ts` DateTime64(3, 'UTC'),
        `request_id` UUID,
        `endpoint` LowCardinality(Nullable(String)),
        `method` LowCardinality(String),
        `status` UInt16,
        `latency_ms` UInt32,
        `principal_kind` LowCardinality(String),
        `refused_at` LowCardinality(String),
        `limited_operation` LowCardinality(Nullable(String)),
        CONSTRAINT ts_is_real CHECK ts > toDateTime64('2020-01-01 00:00:00', 3, 'UTC')
    )
    ENGINE = ReplacingMergeTree
    PARTITION BY toYYYYMM(ts)
    ORDER BY (environment_id, ts, request_id)
    TTL toDateTime(ts) + toIntervalDay(30)
    SETTINGS allow_nullable_key = 1, index_granularity = 8192

    in T030-T035.
