## T038-T041 — R12 settled here, and R24's framing corrected by building it

    DECIDED: ONE consumer, one fetch loop, two row buffers.

    R24 claimed the split "makes DR-11's prohibited single-row insert the quieter table's
    routine case". Implementing it shows that overstated the novelty. 048's batch bound is
    2 seconds OR 10,000 rows, and the interval arm exists precisely because "a row count
    never flushes for a quiet tenant" -- so a quiet producer was ALREADY getting small
    inserts, split or no split. Two consumers would not have fixed that: a second durable
    on its own 2-second interval writes one row just as often.

    WHAT THE SPLIT ACTUALLY CHANGES IS THE RATE, NOT THE SIZE. A fetch returns when either
    bound is hit, so with requests plentiful the loop iterates faster than every 2 seconds,
    and the attempt table gets an insert per iteration rather than per interval. Bounded by
    max(batchMs, batchRows / request-rate): at 5,000 req/s a 10,000-row fetch takes 2 s and
    nothing changes; at 50,000 req/s it takes 0.2 s and the attempt table sees five inserts
    a second where it used to see one every two.

    The measurement that makes it matter, merges stopped:
      20 single-row inserts -> 20 parts, 20 rows
      1 batch of 20 rows    -> 1 part,   20 rows

    So the mitigation is the empty-buffer guard, and that guard was already there --
    `clickhouse.ts` has carried `if (rows.length === 0) return;` since 048. It was tidiness
    then and it is load-bearing now: most batches carry requests and no attempts at all.
    T041 is satisfied by code this chapter did not write, and saying so is the point.

    NOT TAKEN: per-table batch bounds, holding each buffer across fetches. It would cap the
    insert rate, and it costs the thing 048 spent a phase getting right -- a message cannot
    be acked until its row is written, so a buffer that spans fetches holds acknowledgements
    open across them.

## THE COLUMN TYPE WAS WRONG, AND ONLY A RUNNING INGESTER SAID SO

    Every gate was green -- lint, typecheck, 27 unit tests, the schema applied, the table
    verified against `data-model.md` with SHOW CREATE. Then the ingester was started against
    real traffic:

      Code: 27. DB::Exception: Cannot parse input: expected ',' before:
      '.556,"principal_kind":"none","refused_at":"handler","limited_operation":null}'

    `latency_ms` was `UInt32`. The producer measures with `process.hrtime.bigint()` and
    reports fractional milliseconds. Nothing in the type system connects a TypeScript `number`
    to an unsigned integer column, and the contract's "latency_ms | number" is true of both.

    NOTHING WAS LOST, WHICH IS 048's DESIGN WORKING. The insert threw, so nothing was
    acknowledged: `ANALYTICS 38 messages · analytics-ingester pending 0 redelivered 2`. The
    records sat on the stream until the column could take them.

    THE CHEAPER FIX WOULD HAVE BEEN THE WRONG ONE. Rounding to whole milliseconds in the
    producer keeps `UInt32` and destroys the resolution the log exists for. Measured after
    the change, on real traffic through the rebuilt stack:

      /healthz      GET  200  0.56   none  handler    ~absent
      /v1/x         GET  404  0.921  none  unmatched  ~absent
      /healthz      GET  200  0.41   none  handler    ~absent
      /v1/webhooks  GET  401  2.29   none  guard      /v1/webhooks

    Three of those four are under one millisecond. Under `UInt32` they would all read 0 and
    FR-ANL-10's percentiles would be computed over a column that had thrown its own
    resolution away. `Float32` now; `0004_api_requests.sql` was dropped and re-applied rather
    than amended, because the ledger refuses an edit to an applied file and the schema had
    not shipped.

## WHAT THE ROW SAYS ABOUT WHICH LAYER DECIDED

    401 from the guard  -> refused_at `guard`,     endpoint PRESENT   (the router ran)
    404, no match       -> refused_at `unmatched`, endpoint ABSENT    (nothing to name)
    429 from the limiter-> refused_at `middleware`, limited_operation `rest`
    200 from a handler  -> refused_at `handler`

    The 429 is the one that could not exist before. `RateLimitMiddleware` refuses with
    `res.end(); return;` and never calls `next()`, so a producer registered last never runs
    for it. Registered SECOND it does, and reads `req.principal` when the listener fires
    rather than when it attached.

## T091 — THE RESTART DID NOT RECOVER, AND 048-6's RECORDED CAUSE IS WRONG

    048-6 says an ABRUPT `docker compose down` mid-write left `EVENTS` unrecoverable. This
    was `docker compose stop` -- graceful -- and it happened again:

      healthz: {"status":"unavailable","error":"JetStream stream '$G > EVENTS' could not be recovered"}

    Then, having rebuilt EVENTS, a plain `docker compose restart nats` broke ANALYTICS
    instead. So it is not a particular stream and it is not abruptness.

    FOUR OBSERVATIONS, INCLUDING A CONTROL AND A DELIBERATE REPRODUCTION:

      1. `compose stop nats`, api writing          -> EVENTS unrecoverable
      2. `compose restart nats`, api writing       -> ANALYTICS unrecoverable
      3. `compose restart nats`, API STOPPED       -> healthz ok, clean
      4. `compose restart nats` under 500-request  -> ANALYTICS unrecoverable
         load, deliberately

    THE STREAM THAT FAILS IS THE ONE BEING WRITTEN WHEN THE BROKER GOES DOWN. Graceful or
    not makes no difference; having a writer does.

    AND THIS CHAPTER MAKES IT FAR MORE LIKELY, WHICH IS THE PART THAT BELONGS TO 4.4. Before
    this chapter the api wrote to ANALYTICS once per webhook delivery attempt -- 36 records
    in several days. Now it writes on every request, and Docker polls `/healthz` every five
    seconds. **ANALYTICS is never idle any more**, so every broker restart from here lands
    mid-write. The stream that was hardest to break is now the easiest.

    Observation 3 is the control and it is what makes the other three mean something: without
    it, "the broker sometimes fails to recover" would be the whole finding.

## AND THE STREAMS COULD NOT BE REBUILT BY THE CONTAINER THAT USES THEM

    Recreating them from inside the compose api fails:

      NatsError: replicas > 1 not supported in non-clustered mode

    `replicaCount()` returns 3 when `NODE_ENV === "production"`, and
    `services/api/Dockerfile:43` sets exactly that. So **the compose api can use a stream it
    finds and cannot create one it does not** -- on a single-node broker, which is what
    `compose.yaml` runs. 474 `request_log.publish_failed` lines accumulated while this was
    true, every one of them a record that never reached the store.

    It stayed invisible because the streams pre-existed: they were first created by something
    running outside the container, where `NODE_ENV` is unset and `replicaCount()` returns 1.
    048-6's own repair did the same thing without noticing -- it recreated EVENTS with a host
    script, which is why it worked.

    The stack was restored the same way and is healthy: EVENTS, ANALYTICS and DELIVERIES all
    present at `replicas 1`, nats container healthy, api `{"status":"ok"}`, 8 containers up.
    Filed for `gaps.md`; the fix is `RELAY_NATS_REPLICAS=1` in `compose.yaml`, and it is not
