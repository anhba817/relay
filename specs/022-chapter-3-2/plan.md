# Implementation Plan: Tutorial Chapter 3.2 — Keys and Tokens, Two Credentials and One Mistake

**Branch**: `022-chapter-3-2` (no branch cut; work proceeds on `main` per the series' practice) | **Date**: 2026-08-04 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/022-chapter-3-2/spec.md`

## Summary

Write and publish chapter 3.2 in English, and advance the platform to the state
it documents: API keys scoped to an environment (visible prefix, secret shown
once, salted hash at rest, several active at a time, immediate revocation),
end-user tokens verified against the environment's own signing secret, the
development-only endpoint that mints a token from a key, and the authorisation
split that refuses administrative work to an end-user token. Both dev-mode seams
retire here — the asserted `x-relay-environment` header and the gateway's
shared development secret — which is what every chapter since 2.2 promised.

Phase 0 settled the design: the gateway asks the api to verify tokens rather
than holding a per-environment secret, and that call replaces the memberships
call it already makes, so the connect path gains no round trip (R1). Keys are a
public lookup id plus a secret, because authentication has to happen before a
tenant scope exists (R2). Key secrets get a salted SHA-256 rather than a
password KDF, because 256 random bits cannot be guessed at any work factor (R3).
`jose` joins the api rather than hand-rolled HS256, deliberately spending a
dependency on security code (R4). And the first key comes from signup, because
with no console session nothing else can bootstrap one (R8).

## Technical Context

**Language/Version**: TypeScript 5.9 on Node 22.12+; api compiles as CommonJS
under NestJS 11 (ADR-15), the rest of the workspace is ESM.

**Primary Dependencies**: NestJS 11, Drizzle 0.45 (ADR-16), zod 4, pg 8, and
**one addition** — `jose ^6.2.7` in the api, already resolved in the lockfile for
the gateway (R4). Hashing and comparison use `node:crypto`.

**Storage**: PostgreSQL via the compose stack; one forward-only migration
(`0003_api_keys.sql`) generated by drizzle-kit and reviewed before it is applied.

**Testing**: vitest in two lanes (Docker-free unit; `*.itest.ts` against compose
stores) plus the `@relay/e2e` journey suite, which must keep passing — its
harness is one of the eight callers of the retired header.

**Target Platform**: Linux server (services), static site (tutorial).

**Project Type**: Documentation-first tutorial plus the canonical monorepo it
teaches. The chapter is the deliverable; the code is its answer key.

**Performance Goals**: one indexed key lookup per authenticated request, and one
internal call per socket connect — the same count as today, since token
verification replaces the memberships call (R1, R7). No latency claim the
chapter does not measure.

**Constraints**: the unit lane stays Docker-free; the gateway never touches
Postgres (ADR-05); no credential in any log, error body or URL (NFR-SEC-06);
every existing suite keeps passing; fences byte-match the tag with hunked-diff
amendments.

**Scale/Scope**: one published English chapter, one migration, one new table, one
new public route, one replaced internal route, and **two seam retirements with
different blast radii** — the asserted header in eight files, the shared dev
secret in seven, overlapping only at `gateway/src/auth.ts`. Plus a rewrite of 19
gateway unit tests that can no longer verify a token locally, two fix-forward
edits to chapter 3.1, and the tests that hold twelve invariants.

## Constitution Check

*GATE: evaluated before Phase 0 and re-evaluated after Phase 1 design.*

| Principle | Gate | Verdict |
|---|---|---|
| **I — Tenant isolation is a correctness property** | Authentication necessarily runs *before* a tenant scope exists — the one place the repository's mandatory `environment_id` cannot apply. Does isolation stay structural? | **PASS.** Key lookup is a single unscoped query in the same place tenant creation already lives (the admin surface, 3.1), and its *only* output is the environment id that scopes everything after it. Nothing downstream gains an unscoped path: the request-scoped repository still requires an environment, it just receives it from a verified credential instead of an asserted header — strictly stronger than today. Cross-tenant refusals are tested with a foreign key and a foreign token (spec FR-018). |
| **II — No acknowledged message is ever lost** | Untouched. | **PASS** (no change to write or delivery paths; suites re-run to prove it). |
| **III — Two data paths, never crossed** | Untouched. | **PASS.** |
| **IV — Single writer, single source of truth** | Key creation and verification are database work. | **PASS.** Both live in the repository layer; the gateway gains no database access and in fact stops asserting identity (R1). |
| **V — API-first, developer-first** | Two credentials that are famously easy to confuse. | **PASS**, and this is the chapter's subject: FR-AUT-03's visible prefix, FR-AUT-09's dev-token endpoint, and an error naming presented-versus-expected all exist to reduce the same failure the SRS names. Error shapes reuse EIR-API-04's envelope. |
| **VI — Requirement-driven, test-verified** | Twelve invariants. | **PASS.** Every one has a named test and a requirement to cite (contracts §Invariants). The 100% branch-coverage bar for isolation-relevant code is unmeasurable in this workspace and is **deferred here by explicit decision**, with the tooling-and-CI feature scheduled immediately after this chapter — see Complexity Tracking. |
| **VII — Boring by design — scope is a commitment** | The temptations: a console session, a key-management UI, a credential cache, an authorization framework. | **PASS.** One dependency, spent on crypto with the reasoning written down; no session (R11); management endpoints deferred with a named owner; no cache (R7); the authorisation model is exactly FR-AUT-10's list and no broader. |

**Post-Phase-1 re-evaluation**: unchanged. The design adds one dependency and one
table, introduces no nullable tenant column, and narrows the internal seam
rather than widening it.

**Structure Decision**: a new `auth/` module in the api, beside `messages/`,
`internal/` and `tenancy/`. No new service and no new package: authentication is

and the gateway's share of the work is one call it already makes.

## Complexity Tracking

No constitution violations to justify. Three decisions a reviewer may reasonably
question, recorded with their alternatives:

| Decision | Why | What was rejected |
|---|---|---|
| `jose` added to the api | Token verification is security code with three classic footguns; the library is already in the lockfile (R4) | Hand-rolled HS256 — thirty lines, and the chapter would be teaching the vulnerability |
| Salted SHA-256 for key secrets, not bcrypt/argon2 | A KDF's slowness only buys resistance to guessing low-entropy secrets; these are 256 random bits, and the cost lands on every request (R3) | bcrypt or argon2, plus a native dependency |
| No credential cache | Verifying per request makes FR-AUT-05's revocation bound true by construction on every instance (R7) | A cache with a Redis invalidation channel, which is machinery for a cost nobody has measured |

**Constitution VI, deferred here by an explicit decision (2026-08-08)**:
NFR-MNT-02's 100% branch coverage for isolation code cannot be measured — the
workspace has no coverage tooling, and adding `@vitest/coverage-v8` changes
`services/api/package.json`, which three published chapters fence (1.4, 2.1,
2.2). Principle VI's companion clause is equally unmet: no CI exists, so "the
quickstart MUST run unmodified, verified by automated execution in CI" has been
satisfied by hand every time.

Chapter 3.1 deferred the coverage task (021's T037) for the same reason. **This
is the second recorded deferral and the last**: the owner has scheduled one small
feature — coverage tooling, a CI workflow, and hunked-diff amendments to the
three fenced chapters — to run **immediately after 3.2 and before 3.3**.

Chapter 3.2 therefore proceeds on the stated understanding that its isolation
code is tested by name (contracts §Invariants) but its branch coverage is
unmeasured, and that the instrument arrives in the next feature rather than
never. What that feature must then verify is exactly this chapter's credential
path — `principal.environmentId` becomes the single source of tenant scope here,
which is the code NFR-MNT-02's bar was written for.
