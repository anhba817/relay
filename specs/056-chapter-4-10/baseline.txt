      `Object.prototype`:

        kindOf("constructor")            -> function Object() { … }   TRUTHY
        so the TYPE refusal                                            never fires
        KIND_CAPS[thatFunction]          -> undefined
        bytes > undefined                -> false

      types the map `Record<string, MediaKind>` and says the return is a `MediaKind`;
      the runtime disagreed, which is why no type error appeared anywhere.

      Fixed with `Object.hasOwn`. The test that found it was written to check exactly
      this and went red on its first run — 5 of 5 after.

      **And the two facts live in one file for the reason this bug shows**: a type
      allowed with no cap is measured against `undefined`, and `>` against `undefined`

T024a A PRESIGNED URL NEEDS NO CONTACT WITH THE STORE, WHICH IS WHY FR-017 NEEDED A
      ROUND TRIP BUILT FOR IT.

      Signing is five HMAC rounds over strings. The api never opens a socket, so it
      never learns the store is down, and a slot issued into an outage is
      byte-indistinguishable from a good one — the client finds out at upload time,
      holding a URL nobody can use. `docs/05-sad.md:1062` asks for the opposite, so
      `storeReachable()` exists **only to produce a refusal**.

      MEASURED BOTH WAYS, 200 SAMPLES A SIDE, THE SAME BINARY MINUTES APART:

          slot request, probe on    min 6.266  p50 7.859  p95 9.007  max 10.135 ms
          slot request, probe off   min 4.849  p50 6.335  p95 7.260  max 10.350 ms

      **+1.524 ms at p50, +24.1%.** The probe's own 1.062 ms is two thirds of that; the
      rest is the second signing. That is the price of FR-017 on the happy path and it
      is published rather than described.

      AND THE POSITION IS THE ONLY ONE THAT SATISFIES FR-009 WITHOUT A COMPENSATING
      DELETE. After type and size, before the reservation: a probe after the write would
      have to un-reserve bytes it just committed, and a probe first would spend a round
      trip on `application/x-evil`. The consequence worth naming is that a tenant over
      quota with a down store is told the store is down — retrying then produces
      `media_storage_exhausted`, so the client learns both facts in two requests. The
      opposite order tells a client to delete media when nothing could have been stored
      anyway, which is permanent advice about a transient state.

          FOR UPDATE   B blocked: yes  · B saw sum=600 · B refused  · committed   600
                                                                      against a cap of 1,000

      A TRANSACTION IS NOT A LOCK. Postgres defaults to READ COMMITTED, so wrapping a
      read and a write in BEGIN/COMMIT makes them atomic and not serialised.

T036a THE OBVIOUS PROBE FOR "DOES THE METHOD TAKE THE LOCK" MEASURED THE WRONG LOCK.

      Hold the environment row with `FOR UPDATE`, call `reserveMediaSlot`, watch it wait
      — it waits, **and it waits with the explicit lock deleted**.
      `media_objects.environment_id` is a foreign key, so the INSERT takes `FOR KEY
      SHARE` on the parent row by itself, and `FOR KEY SHARE` conflicts with
      `FOR UPDATE`. The probe was measuring the foreign key.

      `FOR NO KEY UPDATE` IS THE DISCRIMINATOR. Postgres's row-lock conflict table puts
      `FOR UPDATE` in conflict with it and `FOR KEY SHARE` not in conflict with it, so a
      holder in that mode blocks exactly the lock the method asks for and nothing the
      foreign key does. Red without the explicit lock, green with it — which the first
      version could not manage in either direction.

T032  BOTH GATES, ASKED SEPARATELY. The CHECK enumerates four dimensions and says
      nothing about a fifth, so `{"disk_inodes":{"hard":10}}` is **accepted by the
      column** and refused by `.strict()`. That is the division of labour the quota
      chapter described — *"the constraint cannot express 'and nothing else', while a
      parser can"* — and it is why a new dimension has to land in both files in one
      change: the constraint would accept a config the parser rejects, `capsFor` fails
      closed, and **the cap silently becomes no cap**.

      0016 restates TWELVE clauses where 0014 restated nine, and every earlier dimension
      is re-checked. The risk in a rebuild is the clause it drops, and a dropped clause
      is invisible from TypeScript.

T033  ABSENT, ZERO AND NULL ARE THREE STATES. An environment with no `storage_bytes`
      key uploads 18 MB across two requests; a cap of `0` refuses one byte. A parser
      that collapsed zero into absent would turn the strictest configuration into the
      loosest, silently.

T037/T038  SRS 1.17. FR-RTL-05 said *"configurable monthly quotas on messages sent,
           unique active persons, and connection-minutes"* while FR-MED-02 and FR-MED-12
