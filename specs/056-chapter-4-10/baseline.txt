## AND ONE OF THE NINE WAS PUBLISHED WRONG, FOR THE PROBE'S OWN REASON

      Planning published the tampered-signature result as **400** and the store
      answers **403 `SignatureDoesNotMatch`**. The 400 was the shell's: the probe
      rebuilt the URL as `${URL%?*}?…`, which splits on the LAST `?` rather than the
      first, so what reached the store was malformed rather than mis-signed.

      **The integration test found it by asserting the published figure and going
      red.** Confirmed two ways afterwards — a clean `curl` and a signature replaced
      with `deadbeef` both answer 403 — so the store is consistent and the outlier
      was the instrument.

      Corrected in six places: `plan.md`, `research.md`, `contracts/`, `tasks.md`,
      `quickstart.md` and `CLAUDE.md`. **Every measurement was wrong before it was
      right**, and this one had reached the project's own instruction file.

## T013 — ONE PROTOTYPE KEY DEFEATED BOTH OF FR-MED-02's FIRST TWO REFUSALS

      `ALLOWED_TYPES` is an object literal and the first `kindOf` was
      `ALLOWED_TYPES[mimeType] ?? null`. An object literal inherits from
      `Object.prototype`:

        kindOf("constructor")            -> function Object() { … }   TRUTHY
        so the TYPE refusal                                            never fires
        KIND_CAPS[thatFunction]          -> undefined
        bytes > undefined                -> false
        so the SIZE refusal                                            never fires

      **A declared MIME type of `constructor`, at any size, passed both.** TypeScript
      types the map `Record<string, MediaKind>` and says the return is a `MediaKind`;
      the runtime disagreed, which is why no type error appeared anywhere.

      Fixed with `Object.hasOwn`. The test that found it was written to check exactly
      this and went red on its first run — 5 of 5 after.

      **And the two facts live in one file for the reason this bug shows**: a type
      allowed with no cap is measured against `undefined`, and `>` against `undefined`
      is `false` rather than an error.

## T014 — THE LINT RULE REFUSED THE SERVICE, WHICH IS 4.7's FINDING ONE CHAPTER ON

      The first `media.service.ts` held the quota query and imported `drizzle-orm`:

        error  'drizzle-orm' import is restricted from being used. The query engine
               lives inside the repository layer only (constitution I, ADR-16)

      Chapter 4.7's record says why a plan walks into this: *"The plan put the job in
      the api BECAUSE the api owns the repository and never noticed the wall between
      them."* This chapter's plan did the same. The query is
      `Repository.reserveMediaSlot` now — one transaction, because the cap is a sum
      over `media_objects` and the insert adds to it — and it **returns facts rather
      than a refusal**, so the protocol decision stays in the service.

## AND THE TYPE SYSTEM SAID THE PHASE ORDER WAS WRONG

      With the route written, `tsc` refused four things, and each refusal is a guard
      this project built on purpose:

        media_type_not_allowed …    not assignable to `ErrorCode`   (three codes)
        "storage_bytes"             not assignable to `Dimension`
        NOUN: Record<Dimension,…>   missing `storage_bytes`
        RESUMES: Record<…>          missing `storage_bytes`

      **US1's route cannot compile before US2's codes and US3's dimension**, and the
      task list has it first. `protocolError` is typed `ErrorCode` precisely so an
      unregistered code stops compiling (FR-025), and `Record<Dimension, string>` is
      there because *"the compiler catches nothing"* about a missing dimension unless
      somebody makes it.

      So T021's four codes and T031's parser half were pulled forward, recorded here
      rather than reordered silently. **The dependency was real and no analysis pass
      found it; the compiler did, in one run.**

      AND THE FOURTH DIMENSION HAS NOTHING TRUE TO SAY IN ONE OF THOSE MAPS.
      `RESUMES` builds a sentence promising a date, and stored bytes resume on
      nothing — the figure falls when media is deleted and the 1st changes nothing.
      `media_storage_exhausted` exists for that reason and never reaches `QuotaError`,
      so the entry is there because the type demands one. Written down in the file.

(1)   TWO COMPOSE SERVICES CLAIMED HOST PORT 9000 AND THE STACK HAD BEEN RUNNING
      WITHOUT CLICKHOUSE FOR THIRTY-TWO HOURS.

      ClickHouse has published `${RELAY_CLICKHOUSE_NATIVE_PORT:-9000}:9000` since
      chapter 1.2; phase 1 of this feature added MinIO on `${RELAY_MINIO_PORT:-9000}`.
      They cannot both start:

          Bind for 127.0.0.1:9000 failed: port is already allocated   exit 1

      Phase 1's health check probed both ways and passed, and phase 2's five signed
      results were all real, because nothing in either phase touches ClickHouse. The
      collision only surfaced when a suite needed the analytical store — one command,
      `ECONNREFUSED 127.0.0.1:8123`.

      045's rule, third time: **a hand-maintained table cannot be checked.** Eleven
      published ports across `compose.yaml`, allocated by hand, and exactly one
      duplicate. MinIO moves to 9100 on the host and keeps 9000 in the container,
      because the host side is the hand-maintained table and chapter 1.2's claim was
      there first.

      AND A STOPPED CONTAINER CAN BE RESTARTED INTO A STATE WITH NO PUBLISHED PORTS AT
      ALL. `docker compose up -d clickhouse` printed `Started`, exited 0, reported
      `(healthy)`, and `NetworkSettings.Ports` was `{}` — not even 8123, which was free.
      The health check runs `clickhouse-client` INSIDE the container, so it cannot see
      this. `--force-recreate` fixed it. **A green health check is a claim about the
      inside of the container.**

(2)   `echo "exit=$?"` AFTER A PIPELINE READS `tail`'S STATUS. The failed compose start
      was measured as `exit=0` and was 1. 043 reproduced this three times, once in a
      task whose own text warns about it; this is the fourth.

(3)   THE TAMPERED-SIGNATURE PROBE WAS A NO-OP ONE RUN IN SIXTEEN.

      It replaced the signature's first character with `f`, which changes nothing when
      that character already IS `f`. Measured over 4,096 signings: **16 distinct first
      characters, `f` on 255 of them — 6.23%.** On those runs the probe sent a VALID
      url and the store's honest 200 read as *"the store accepted a tampered
      signature"*. It had passed three consecutive runs before it failed.

      Fixed by mapping the character to a different one and asserting the tampered url
      differs from the signed one — **a probe that may not have altered anything has to
      say so.** 20 of 20 green after.

(4)   A 20-SECOND DEADLINE INSIDE A 5-SECOND TEST, SINCE CHAPTER 4.4.

      `vitest.integration.config.mts` sets no `testTimeout`, so this lane's budget is
      vitest's default 5,000 ms. `request-log.itest.ts` polls to 20,000. The poll's
      `return null` branch was unreachable and `expect(...).not.toBeNull()` was an
      assertion that could never fail — it either got a row or the test was killed
      four times before its own deadline.

      AND THE TWIN CONFIG HAD IT RIGHT: `vitest.coverage.config.mts:102` sets
      `testTimeout: 60_000`. Two configs run `.itest.ts` files and they disagree, which
      is 4.9's finding on a different field. Both suites carry `}, 60_000` now (056-4).
