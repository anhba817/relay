# Implementation Plan: Tutorial Chapter 3.4 — JetStream and the First Consumer

**Branch**: `025-chapter-3-4` (no branch cut; work proceeds on `main` per the series' practice) | **Date**: 2026-08-09 | **Reconstructed**: 2026-08-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/025-chapter-3-4/spec.md`

> **Provenance**: reconstructed after hardware loss. See `spec.md` and
> `chapter-notes.md`.

## Summary

Write and publish chapter 3.4 in English and Vietnamese, and advance the platform
to the state it documents: an `EVENTS` stream where every setting is a decision,
a subject grammar both sides share, and the first durable pull consumer — whose
runtime deduplicates in the same transaction as the effect, so a handler cannot
forget to.

The chapter's spine is that the outbox did not remove the dual-write problem; it
moved it. Between doing the work and acknowledging it there is a window, and a
process that dies there has done work the broker will hand out again. The answer
is not a better protocol. It is a ledger row that shares a transaction with the
effect — chapter 3.3's shape, pointed the other way.

Phase 0 settled the design. Two stream settings are immutable once created and
happen to be the two 3.3 chose by hand (R1). Every other setting becomes a
decision with a reason (R2), including the one deliberately left alone: the
broker's duplicate window is not the guarantee, because the outbox can republish
hours later and no window is a safe guess (R3). Delivery attempts are bounded and
what falls out is caught by nothing, which the chapter says rather than implies
(R4). The consumer lives in the api for ADR-06's reason, and what that costs 3.5
is named now rather than discovered then (R5). The kill test uses a real
`SIGKILL` against the same walk script a reader runs (R7).

## Technical Context

**Language/Version**: TypeScript 5.9 on Node 22.12+; api compiles as CommonJS
under NestJS 11 (ADR-15), the rest of the workspace is ESM.

**Primary Dependencies**: unchanged. NestJS 11, Drizzle 0.45 (ADR-16), zod 4,
pg 8, jose 6, `nats@2.29.3`. **No new dependency** — 3.3 already chose the broker
client, and this chapter uses the JetStream manager and consumer APIs it already
carries.

**Storage**: PostgreSQL via the compose stack; one forward-only migration
(`0005_consumed_events.sql`) generated by drizzle-kit and reviewed before it is
applied. NATS JetStream with file storage, configured rather than created.

**Testing**: vitest in two lanes (Docker-free unit; `*.itest.ts` against compose
stores) plus the `@relay/e2e` journey suite. The kill test needs a child process
and a real signal, which 2.8's harness established and 3.3 used for the same
purpose one hop earlier. **New this chapter**: coverage is measurable — feature
024 landed the tooling and CI, so Principle VI's gate is a real check rather than
a deferral.

**Target Platform**: Linux server (services), static site (tutorial).

**Project Type**: Documentation-first tutorial plus the canonical monorepo it
teaches. The chapter is the deliverable; the code is its answer key.

**Performance Goals**: none claimed. The consumer's batch and acknowledgement
deadline are chosen for the reasons in R6 — a slow handler must not hold a
deadline over a batch, and a backlog of twelve thousand must drain in sensible
steps — not against a latency budget. FR-ANL-04's 60-second bound applies to the
producing side and still has orders of magnitude of headroom.

**Constraints**: the unit lane stays Docker-free; an unreachable broker must
leave the api serving writes; the durable must be safe for more than one
instance; no credential and no message text in any log line; every existing suite
keeps passing; fences byte-match the tag with hunked-diff amendments; both
locales ship together.

**Scale/Scope**: one published chapter in two locales, one migration, one new
table, one new module, two new scripts, and twelve invariants. No public route
changes and no existing response changes. Fence budget 15–18 (R12).

## Constitution Check

*GATE: evaluated before Phase 0 and re-evaluated after Phase 1 design.*

| Principle | Gate | Verdict |
|---|---|---|
| **I — Tenant isolation is a correctness property** | A second table below the boundary with no `environment_id`. | **PASS.** `consumed_events` is platform bookkeeping in the same family as `outbox`: one consumer reads every environment's events, so a scoped repository would be the wrong shape rather than a safer one. It holds no tenant data — a consumer name, an event id, a timestamp — and no event body. The exception is recorded in `data-model.md` beside 3.3's, rather than left for a reviewer to notice. |
| **II — No acknowledged message is ever lost** | The chapter's whole subject. | **PASS.** The claim and the effect share a transaction, so a handler that throws leaves no claim and the redelivery runs again. The failure this forecloses is the dangerous one: a claim written outside the transaction would wave the redelivery through as a duplicate, silently never handling the event. Proved by a real `SIGKILL`, not asserted. |
| **III — Two data paths, never crossed** | The first thing to *read* the crossing. | **PASS.** The consumer reads the broker and writes only its own ledger. Nothing on the analytical side reads Postgres; nothing here reads ClickHouse. The chapter is explicit that the ingester Part 4 builds is another consumer on this same stream, not another crossing. |
| **IV — Single writer, single source of truth** | Two places now know about delivery. | **PASS.** The broker owns the delivery count and the stream position; Postgres owns the record of handling. Neither duplicates the other, which is why the model has no `attempts` column and no consumer offset in Postgres — a cursor stored twice is a cursor that disagrees with itself after a crash. |
| **V — API-first, developer-first** | The consuming half of 3.3's promise. | **PASS.** `contracts/consumers.md` states what a consumer may assume and what the handler contract withholds. The handler's inability to acknowledge, retry or deduplicate is the contract, not a limitation of it. |
| **VI — Requirement-driven, test-verified** | Twelve invariants, and — for the first time in Part 3 — a coverage instrument. | **PASS, and the deferral ends.** Every invariant has a named test and a requirement to cite (contracts §Invariants). Feature 024 landed coverage tooling and CI after 3.3, so the measurement three chapters deferred is taken here: workspace branches 79.01%, and `repository.ts` — which holds ordering, idempotency and isolation — moves **up** to 86.30% despite this chapter adding to it (R10). NFR-MNT-02's 100% remains unmet and is now a number rather than an unknown. |
| **VII — Boring by design — scope is a commitment** | The temptations: a dead-letter table, a real handler with a real job, retry accounting, per-environment streams, pruning. | **PASS.** No new dependency. One handler that deliberately does almost nothing, with a named retirement in 3.5. No dead letter — the gap is stated instead. No `attempts` column. The stream stays one stream, because sharding is a decision with no evidence behind it yet. |

**Post-Phase-1 re-evaluation**: unchanged. The design adds no dependency, one
table and one module, introduces no tenant column, and changes no public route.

**Structure Decision**: a new `consumer/` module in the api, beside `outbox/`. It
lives there because ADR-06 put the relay there and the same reasoning applies —
and because the ledger claim needs a transaction against the database the service
owns. `handler.ts` is a separate file from `runtime.ts` on purpose: the interface
that withholds capability is the load-bearing part of SAD risk R5's mitigation,
and burying it inside the loop would make it look incidental.

## Complexity Tracking

No constitution violations to justify. Three decisions a reviewer may reasonably
question, recorded with their alternatives:

| Decision | Why | What was rejected |
|---|---|---|
| A second un-scoped table below the tenant boundary | one consumer reads every environment's events; a scoped ledger would be the wrong shape, not a safer one | an `environment_id` column that no query would ever filter on, which is worse than none — it would imply an isolation guarantee this table does not make |
| Delivery attempts bounded with nothing catching what falls out | forever is not a retry policy, and a dead-letter store is FR-WHK-04's in 3.5 | inventing a dead-letter table this chapter would have to design without the requirement that shapes it |
| The first handler does almost nothing | every consumer the SAD names belongs to a later chapter; giving this one a job means stealing 3.5's subject or inventing product (Principle VII) | a "useful" handler, which would have made the runtime's correctness look like the handler's |

**Constitution VI — the three-chapter deferral ends here.** 3.1 deferred the
branch-coverage measurement, 3.2 deferred it by explicit decision, 3.3 deferred
it a third time with the owner's agreement and moved the remedy to after it. That
remedy — feature 024 — ran. This chapter is measured: the run exits 0, the
workspace sits at 79.01% branches, and `repository.ts` improves to 86.30% despite
gaining `claimEvent` and `timesHandled`.

What that buys, stated plainly: 3.3's central claim was *no event is ever lost*
and it shipped without the instrument that keeps such a claim honest. This
chapter's claim is *no event is handled twice*, and it ships with one. NFR-MNT-02
asks for 100% branch coverage on ordering, idempotency and isolation code and we
are at 86.30% — but that is now a measured gap with named uncovered branches
rather than an unknown, which is the difference the constitution's clause exists
to create.
