## Provenance — read this first

The chapter shipped on 2026-08-09 to `relay-tutorial` (`2e5f3e3`), in both
locales. The machine holding the unpushed `relay-platform` implementation **and
this entire spec directory** failed before either was pushed. Only the tutorial
repository had been pushed.

The platform code was reconstructed on 2026-08-10 **from the chapter's own
fences**, and the reconstruction is the finding worth recording:

- **9 unified diffs applied with `git apply` cleanly — zero fuzz, no `-C1`
  fallback.** They were cut from the real repository, against a base
  (`part3-ch3` plus feature 024) that had been pushed and survived.
- **8 whole-file listings** dropped in unmodified, including `runtime.ts` (263
  lines) and `consumer.itest.ts` (482 lines).
- **The drizzle metadata was regenerated** rather than recovered, and this is the
  strongest evidence the reconstruction is faithful: running `drizzle-kit
  generate` against the reconstructed `schema.ts` produced SQL **byte-identical**
  to the chapter's `0005_consumed_events.sql`. Two independent paths — a
  hand-applied diff and a code generator — converged on the same table.
- **Both lanes then reproduced the chapter's own checkpoint exactly**: 133 unit,
  97 integration.

What this says about the format is worth more than what it says about the
accident: a chapter written to the series' fencing rule is a complete
reconstruction source for the code it teaches. The expensive artifact — 3,575
words of English prose plus a 3,535-word translation — is the one that survived,
and it was sufficient to regenerate the cheap one.

**What it could not recover** is in findings 1 and 2, and in the honesty markers
throughout `research.md`: measurements whose transcripts are gone are labelled
`MEASURED (recovered)` rather than `MEASURED`.

## Findings

### 1. The chapter asserts two files it never fences

`packages/protocol/src/internal.test.ts` and
`services/api/src/consumer/runtime.test.ts` both exist in the repository, are
both described in the prose — "Five unit cases in
`packages/protocol/src/internal.test.ts` hold the grammar", and "two are pure and
live in the unit lane" — and **neither is fenced**.

This is a real defect in a shipped chapter, and the reconstruction is what
exposed it: rebuilding the repository from the fences produced a workspace with
120 + 5 = 125 unit tests against a checkpoint promising 133. The arithmetic is
what located the gap; the prose alone would not have.

The consequences are worse than a missing listing. The fence chain cannot replay
files it does not carry, so `pnpm check:fences` can pass while the repository the
chapter describes cannot be rebuilt from it — which is the one property the
fencing rule exists to guarantee. Spec **FR-025** was added during reconstruction
to name the rule explicitly, because FR-022 only constrains fences that exist.

`internal.test.ts` was recoverable: the prose enumerates all five cases precisely
enough to write them against the real signature. `runtime.test.ts` was not — the
chapter says only that two pure invariants exist and never names them. The eight
tests now in the tree are **authored, not recovered**, and the numbering of
invariants 10 and 11 is a reconstruction decision. They were validated by
mutation (three mutations, each killed by the test that names the behaviour), and
they bring the count to exactly 133.

**Open**: fixing this is a fence-only amendment to a published chapter, in both
locales.

### 2. The chapter's opening and closing numbers cannot be reproduced

"12,930 events" in the opening transcript and "12,941" in the checkpoint came
from the author's database after a chapter's worth of running. A fresh stack
reports 14.

This is not fixable by re-running, and it is load-bearing prose rather than a
stray figure — the opening paragraph's argument is that a large backlog has sat
unread. Recommendation is to re-capture both blocks against a stack that has been
running rather than to leave historical numbers a reader cannot reproduce.
Recorded in `captured-output.md`; **open**.

### 3. A dead ternary in the runtime, faithful to the fence

```ts
return result === "duplicate" ? "acknowledge" : "acknowledge";
```

Both branches are identical. The comment above it argues that a duplicate should
still be acknowledged — the behaviour is correct and the tests pin it — but as
written the ternary decides nothing. It is present in the chapter's own listing,
so it is not a transcription slip.

Either it is deliberate pedagogy that reads as a bug, or it is a bug that reads
as pedagogy. `runtime.test.ts` pins both cases to `acknowledge`, so simplifying
it to `return "acknowledge"` would keep the suite green and the prose accurate.
**Open**, deliberately left as-is pending the author's call.

### 4. Constitution VI's three-chapter deferral ends here

3.1 deferred the branch-coverage measurement, 3.2 deferred it by explicit
decision recording that the remedy would run before 3.3, 3.3 deferred it a third
time with the owner's agreement and moved the remedy to after it. **Feature 024
ran.** This chapter is the first in Part 3 to be measured.

The result is better than the deferral history suggests: this chapter adds code
to `repository.ts`, the file carrying 024's tightest ratchet (85% branches,
deliberately below NFR-MNT-02's 100% to stop the figure sliding while the gap is
closed). Branches moved **up**, 85.91% → 86.30%. The workspace improved on both
axes. Coverage exits 0.

What is still unmet is now a number rather than an unknown, which is the whole
point of the instrument.

### 5. Two Redis environment variables, and only one of them is obvious

Found during verification, not implementation, and worth recording because it
cost an hour and produced a wrong diagnosis on the way.

`RELAY_REDIS_URL` is read by the gateway's production code (`fanout.ts`).
`RELAY_REDIS_PORT` is read by its *integration tests*, which build their own URL
from it. Setting only the first leaves the test clients dialling `localhost:6379`
where nothing listens — and because ioredis retries connection failures in the
background rather than throwing, the suite does not error. It sits there until a
5-second deadline fires, so the failure presents as seven fan-out and resume
*timeouts* rather than as a connection problem.

The wrong turn is worth recording too: the failures were first attributed to a
pre-existing environment problem on the basis that they reproduced at the base
commit. They did — but the base commit was run with the *same incomplete
environment*, so the control was broken in the same way as the experiment and
could not distinguish "machine problem" from "my own command line". Both
`*.itest.ts` files document the correct invocation in a comment four lines above
the code.

`quickstart.md` now leads with this, and `baseline.txt` repeats it.

### 6. The fence budget was right, for the first time in Part 3

R12 budgeted 15–18 and the chapter shipped **17**. Chapter 3.3 budgeted 12–15 and
shipped 19, with its notes observing that two of the four extra fences were
fix-forwards into Part 3's past rather than that chapter's own work.

The difference is structural rather than lucky: this chapter fixes forward into
no earlier chapter and touches no service beyond the api. It adds a reader to a
path that already existed. When a chapter's blast radius is genuinely one module,
a budget drawn from an enumerated file list is accurate.

## Standing debt this chapter did not create

No tags are cut for any chapter. Every SKIP AHEAD and CHECKPOINT names a state
(`part2-ch5` … `part3-ch4`) that cannot be checked out, and
`specs/019-stack-refoundation/rebase-recipe.md` now needs states for 2.2–2.8,
3.1–3.4 appended.

**This chapter is the argument for finally cutting them.** Had `part3-ch4`
existed as a tag, the lost work would have been a `git checkout` rather than a
reconstruction — and while the reconstruction succeeded, it succeeded because the
fencing discipline happened to be strong enough, not because anything guaranteed
it would be. The next chapter that loses a machine may not fence two of its test
files either.
