### THE WORD ESTIMATE MISSED BY HALF, AND THE MODEL IS THE THING TO FIX

### T081 — THE RATCHET DELETED NOTHING, AND FOUND SOMETHING ABOUT ITSELF

Four uncovered sites across the named files. **Every one has a reason, and none of them is
"nobody wrote the test":**

    messages.controller.ts:72-73   `req.requestId ?? "unknown"` and
                                   `req.principal?.environmentId ?? "unknown"`
    messages.controller.ts:311     `if (actingExternalId === undefined) throw`
    zod-validation.pipe.ts:57-64   the `issue !== undefined` guards

- The two `??` arms are **where the ratchet already acted, one chapter ago**: 3.23 added two
  publish sites each carrying its own copy, six uncovered arms where there had been two, and
  the fix was one `publishContext` function rather than a test. The fallbacks stay because

- The `throw` at 311 is a deliberate narrowing with its argument written above it: the guard

  change to the decorator invalidates it, which `!` does not.
- The pipe's guards are compiler-required. `tsconfig.base.json` sets
  `noUncheckedIndexedAccess: true`, so `result.error.issues[0]` is `$ZodIssue | undefined` and
  the `?.` is not a choice.

**AND THE INSTRUMENT ANSWERS A DIFFERENT QUESTION THAN THE ONE THE RATCHET ASKS.**
`attachments.ts` measures 100% branches. Its pair rule reads:

    const hasText = typeof value.text === "string" && value.text.length > 0;

and v8 records that line as `[7, 7]`. **Those are operand EVALUATION counts, not outcome
counts.** The `typeof` check has never once been false — every schema that calls the refinement
declares `text` as `z.string()`, so a non-string cannot reach it — and the file still reads 100.
The next line, `Array.isArray(value.attachments) && value.attachments.length > 0`, measures
`[7, 2]`: the right operand was skipped five times by short-circuit and the arm is still
"covered".

So the guard stays, for a reason that is not coverage: `refineTextAndAttachments` takes
`text?: string | null | undefined` deliberately — `exactOptionalPropertyTypes` makes
`attachments?: T[]` refuse both callers, whose own inferred type is `T[] | undefined` — and
under that signature the compiler requires the narrowing.

**The lesson is about constitution VI's 100%-branch clause.** A file at 100% branches is not a
file whose every arm has run, wherever a `&&` or a `||` is involved. Recorded in the pin's own
comment so the next reader of that number meets the caveat with it.

#### The failure rate has a confidence interval, and it does not apply

**That interval is arithmetically correct and substantively meaningless**, because
Clopper-Pearson assumes twenty independent Bernoulli trials and these twenty are
anti-correlated by construction. Read the exit column downward: from run 3 to run 17 it

anything; the number to carry is the mechanism.

#### Why the battery alternates

`node_modules/.vite/vitest/<hash>/results.json` stores `{duration, failed}` per file, and the
sequencer runs previously-failed files first, then the rest by duration descending. Three for
three in the battery:

    run  1 failed quotas    -> run  2 ordered quotas first
    run  2 failed webhooks  -> run  3 ordered webhooks first
    run 19 failed webhooks  -> run 20 ordered webhooks first

Moving the failed file to the front pushes `tuan` into the last slot, where nothing follows it
inside that run — so the run goes green, the cache reverts to duration order, and the next run
puts a suite behind `tuan` again. **The lane's failure rate is a function of a JSON file in
`node_modules`**, and the state that file was left in after run 20 predicted run A's failure
before it ran.
