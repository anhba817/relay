WHAT THE FIRST ANALYSIS PASS FOUND, AND IT WAS ONE DEFECT SEEN FROM SIX ANGLES

**Coverage read 100% before the pass and 100% after.** Every requirement had a task; the tasks

THE SOCKET DOOR DROPPED THE FIELD AT THREE NAMED POINTS

    session.ts:1512            const { channel, text, idem_key } = frame.data.payload
                               a NAMED destructure. Widening `messageSendSchema` puts the
                               field on the wire and nothing carries it further.
    internal.controller.ts:68  { text: body.text, …(idempotency_key) }
                               a NAMED construction, one hop later.
    session.ts:1534            the gateway BUILDS the outbound `message.created` payload

**A message sent over a socket would have committed with no attachments and acked normally**,
while every REST test stayed green — including the outsider test, which sends over REST. The
shape is chapter 3.21's inert module: parsed, ignored, invisible to everything that does not
exercise that exact door. T022a, T022b, T022c, T028a and T028b are what close it.

AND A STRICT RESPONSE SCHEMA MADE IT WORSE THAN A MISSING FIELD

`internalSendResponseSchema` is a `strictObject` without attachments; `api-client.ts:248`
**parses** the api's reply with it; `internal.controller.ts:84` returns `{ ...message, user }`.
The moment `sendMessage` returns an attachments key, the spread carries it and the strict parse
rejects it — **every socket send fails**, not just one carrying an attachment.

**It is latent today for a reason worth knowing.** `MessageRow` has carried `edited_at?` since
chapter 3.23 and that schema does not list it, and nothing breaks because `sendMessage`'s two
return paths never set the key. **A field on the type and never on the value is a trap that
springs the day somebody sets it**, and this chapter is the somebody.

THE PLAN'S OWN PREDICTION IS WHAT MADE THIS CHEAP

The plan listed `services/gateway/src/session.ts` with "no change expected — verify, do not
assume", because chapter 3.23 found the gateway needing a change nobody predicted. **The
prediction was wrong in both directions and verifying it took one `sed`** — at analysis time
rather than at implementation time, which is the whole difference between a note and a phase.

A prediction stated as a value is checkable; the chapter's other predictions are stated the
same way for the same reason.

TWO PRE-EXISTING DISAGREEMENTS BETWEEN THE DOORS, FOUND BY COMPARING THREE SCHEMAS

    messageSendSchema.payload.text        z.string()                  no min, no max
    internalSendRequestSchema.text        z.string().min(1).max(8000)
    sendMessageBodySchema.text            z.string().min(1).max(8000)

A socket client may send 100,000 characters and is refused one hop later by the api. **Not
fixed here**: that is FR-MSG-01's bound and this is FR-MSG-11's chapter, and narrowing a

anybody deciding to. T017a records the decision; `gaps.md` carries it with the one-line fix
named.

The second disagreement is `idem_key` against `idempotency_key`, which
`packages/outsider/src/integrate.itest.ts` already records paying for.

AND THE SWEEP CAUGHT THE SENTENCE THAT DESCRIBED THE SWEEP

Regenerating `traceability.md` after the pass fixed a stale task count. The rewritten paragraph
**quoted the sweep's own failure message**, and the sweep read the quoted figure as a fresh
claim and failed again.

**Reworded rather than exempted.** A checker cannot tell a claim from a quotation of one, and
teaching it the difference mid-pass is how a checker learns to accept the thing it was pointed
at — chapter 3.23 did exactly that once and recorded it. The blind spot is here instead: a
count inside quotation marks reads as a count.

OPTIONAL OR REQUIRED ON THE FRAME WAS UNDECIDED, AND IT DECIDES FR-007 (3.24)

The task list said "add `attachments` to `messageSchema`" and stopped. **Optional lets the wire
omit the key on the one path a client cannot re-read**; required means the compiler names every
producer that forgets. Decided as **required** (FR-022 (3.24)), and the cost is written down
rather than discovered:

    `messageCreatedSchema.shape.payload` is what `services/gateway/src/fanout.ts` parses
    arrivals with. Mid-deploy, an old instance publishes a payload with no attachments and a
    new instance DROPS THE FRAME.

That is ADR-24's own argument — a field added on one side of a rolling deploy fails loudly on
the other — and it is acceptable for the reason ADR-07 gives: a dropped fabric frame is not a
lost message, because the cursor recovers it. **The chapter says this; a deploy does not have
to teach it.**

FR-006 (3.24) SAID "EVERY PATH" AND THREE PATHS DID NOT ASSERT IT

Order was asserted at the repository and through the history route. The resume test and both
socket tests said "with attachments" and not "in order" — and a single-attachment fixture
cannot see an order at all. All three now send two.

`listMessages` IS TWO QUERIES AND BOTH WERE COVERED BY ACCIDENT

`repository.ts:5261` and `:5278` — a ternary over a `desc` page and an `asc` one, sharing a
`columns` object. T029 exercises the backward branch and T052 the forward one, **and nothing
said so**, so a change to either test would silently drop a branch.

Chapter 3.23 recorded this exact trap with the evidence: adding `isNotNull(messages.text)` to
the forward branch alone left the suite green, because the test that should have caught it
called the function with no cursor. T030a is that chapter's labelled-loop test, here.

A NEGATIVE CHECK, RECORDED BECAUSE IT WAS RUN

**No production code tests `text` for truthiness.** Fourteen places test it for null; a grep for
`if (x.text)`, `!x.text` and `x.text ||` across `services` and `packages` returns nothing.

That matters because FR-019 (3.24) makes `""` a legitimate message body and `""` is falsy — **a
single truthiness test anywhere would treat every attachments-only message as a tombstone.** It
is clean, and it is recorded as checked rather than assumed, because the next chapter to add
one will not know to look.
