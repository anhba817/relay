# Research: Reader Suggestions — Select, Right-Click, Improve

All Technical Context unknowns resolved.

> **Implementation amendment (surfaced, not silent)**: current stable turned
> out to be **Prisma 7** (7.9.1), which supersedes two assumptions below.
> (1) The client is generated *into the repo* (`lib/generated/prisma`,
> git- and docker-ignored, regenerated by postinstall) via the new
> `prisma-client` generator, configured through `prisma.config.ts` + dotenv —
> there is no schema-embedded env loading anymore. (2) There is **no Rust
> query engine**: the runtime uses the pure-JS `@prisma/adapter-pg` driver
> adapter, so R6's standalone-tracing landmine dissolves (V6 verified the
> image end to end regardless). `pnpm prisma generate` also runs explicitly
> in the Docker build stage so images never depend on a developer machine's

## R1 — Prisma wiring in this Next.js app

**Decision**: `prisma` (devDependency) + `@prisma/client` (dependency),
current stable pinned at install time. Schema at `prisma/schema.prisma` with
the single `Suggestion` model (data-model). `lib/prisma.ts` exports the
standard dev-safe singleton (`globalThis` cache so hot reload doesn't leak
connections). `prisma generate` runs via the `postinstall` script so both dev
installs and the Docker build get a client without a separate step. Migrations
via `prisma migrate dev` (development) / `prisma migrate deploy` (Dong, against
the production Neon branch) — no auto-migrate at container start.

**Rationale**: The site runs as one long-lived Node container — the plain
Prisma client over TCP is the boring, fully supported path. Auto-migrating on
boot couples deploys to schema changes and can bite with pooled connections;
an explicit `migrate deploy` step matches this repo's Dong-does-state-changes
convention.

**Alternatives considered**: `@prisma/adapter-neon` / Neon serverless HTTP
driver (built for edge/serverless functions; unnecessary here and adds a
driver-adapter preview surface); raw `pg` + SQL (loses the schema-as-artifact
and migration story the user explicitly asked for via Prisma); auto
`migrate deploy` in the entrypoint (rejected above).

## R2 — Neon connection & runtime configuration

**Decision**: One `DATABASE_URL` environment variable, read at runtime only.
Dong provisions the Neon project and uses the **pooled** connection string
(`…-pooler.…neon.tech`) for the running site; `sslmode=require` stays in the
URL. Dev uses `.env` (already gitignored via `.env*`); prod passes it through
`docker-compose.yml` `environment:` from the host. `.env.example` documents
the shape with a placeholder. The route handler is inherently dynamic
(`export const dynamic = "force-dynamic"` if needed); reading pages remain
static — a build-output check verifies no page flipped to dynamic.

**Rationale**: Neon idles compute; the pooled string keeps reconnects cheap
and survives Neon's connection churn. Runtime-only env is the lesson already
learned with `NEXT_PUBLIC_SITE_URL` — except this one is a secret, so it must
never be a build arg at all.

**Alternatives considered**: Direct (unpooled) string (fine for one container
but pooled is strictly safer with Neon's autosuspend); putting the URL in the
Docker image (a secret in an image layer — never); Neon HTTP driver (R1).

## R3 — Server-side validation & the page-path allowlist

**Decision**: `lib/suggestions.ts` exports the caps (R5) and a pure
`validateSuggestion(input)` returning either a typed payload or a coded error.
Checks: exact field set (unknown fields rejected — constitution VI), types,
trimmed non-empty suggestion, caps, locale ∈ {en, vi}, honeypot field empty,
and **pagePath ∈ the allowlist** built from the existing sources of truth:
every published chapter path from `lib/tutorial.ts` (en + `/vi`-prefixed
variants for translated ones) plus every doc page from `lib/docs.ts`. The
allowlist is computed once at module load.

**Rationale**: The manifest and docs registry already enumerate every reading
page — deriving the allowlist keeps one source of truth (a new chapter is
suggestible the moment its manifest entry flips, zero edits here). Hand-rolled
validation over zod: one endpoint, six fields, and the site takes no other
input — a schema library is a dependency for a problem this file solves in
40 lines (boring by design).

**Alternatives considered**: zod (fine choice generally; unjustified for one
endpoint); validating pagePath by regex shape only (admits garbage paths;
the registry is *right there*); referer-header checks (spoofable noise).

## R4 — The capture component (selection → menu → dialog)

**Decision**: One client component, `components/reading/suggestion-capture.tsx`,
mounted once inside `ReadingLayout` next to the article container and scoped
to it (the component finds its article root by id — `#reading-article` — which
ReadingLayout already renders). Behavior:

- **Desktop**: a `contextmenu` listener on the article root; if the current
  selection is non-collapsed and its range lies inside the article, call
  `preventDefault()` and render a small custom menu at the cursor with exactly
  one action ("Suggest an improvement" / "Góp ý cải thiện"). No selection (or
  selection outside) → no `preventDefault()`, native menu untouched (FR-001).
  Native copy remains available via Ctrl/Cmd+C and by dismissing the menu
  (Esc / click-away), which re-enables the default on the next right-click —
  the menu never traps.
- **Touch**: a `selectionchange` listener (debounced); when a non-collapsed
  selection settles inside the article, float a small "suggest" button near
  the selection's bounding rect (`range.getBoundingClientRect()`); it opens
  the same dialog (FR-002). **Coarse-pointer devices get ONLY this path**:
  Android long-press fires `contextmenu`, so on
  `matchMedia("(pointer: coarse)")` devices the custom-menu handler stands
  down entirely (no `preventDefault`) — the native selection toolbar stays
  intact and the floating button is the single affordance; the custom context
  menu is a fine-pointer feature.
- **Dialog**: an accessible modal (role="dialog", focus trap, Esc closes)
  rendered by the same component: selected text as a read-only blockquote,
  a textarea with a live length counter, cancel/submit; states for
  submitting / success (auto-dismiss with thank-you) / error (localized
  message, retry allowed). Submission `fetch`es POST `/api/suggestions`.
- **Context capture**: selection text from `selection.toString()`; context
  from the selection's enclosing block element's `textContent` — up to
  CONTEXT_MAX chars immediately before the range start and after the range
  end. Plain strings, no DOM paths (survives re-renders and small edits;
  the spec's passage-drift case).
- The component renders `null` until a selection exists — zero cost for
  non-selecting readers; strings come from the i18n dictionary via a `locale`
  prop (R7).

**Rationale**: Browsers don't allow extending the native context menu from a
page, so a conditional custom menu is the only path — restricting it to
selections inside the article is what keeps right-click sacred everywhere
else. One component owning menu+button+dialog keeps selection state coherent
(the spec's stale-selection edge case).

**Alternatives considered**: a persistent per-paragraph "suggest" affordance
(visual noise on every page for a rarely-used action); medium-style floating
toolbar on every selection (hijacks a common action — copy — with UI);
`window.prompt` (unlocalizable, ugly, blocks); a third-party annotation
library like Hypothesis (massive dependency, external service, violates
boring-by-design and privacy assumptions).

## R5 — Caps and rate limits (the numbers)

**Decision**:

| Limit | Value |
|---|---|
| Selected text | 1–1,000 chars (longer selections rejected client-side with guidance, server-enforced) |
| Context before / after | ≤ 250 chars each (client truncates; server enforces) |
| Suggestion body | 1–2,000 chars (trimmed) |
| Request body | ≤ 8 KB |
| Rate limit | 5 POSTs/min and 30/day per IP (in-memory sliding window; `x-forwarded-for` first hop behind the proxy). **Every POST counts — accepted, rejected, or honeypot** — the limiter protects CPU and the DB connection, not just storage. Restarting the process resets the windows (relevant to verification). |
| Honeypot | hidden `website` field must be empty (silent 201-shaped rejection: bots learn nothing, nothing stored) |

Rejections: HTTP 400 (validation, coded), 429 (rate), 503 (DB unreachable) —
each mapped to a localized message client-side. The limiter is per-container,
in-memory, resets on deploy — **accepted** for a single-replica site; recorded
here so a future multi-replica deployment knows to revisit.

**Rationale**: Caps bound storage per row (~4 KB max) and make the bill
predictable; 5/min tolerates an enthusiastic proofreader while stopping
floods; the honeypot is free and removes the dumbest bots without CAPTCHAs
(which would betray the 30-second promise, SC-001).

**Alternatives considered**: durable rate limiting in Postgres (a write to
stop writes — pays the cost it guards against; overkill at this traffic);
CAPTCHA (hostile to SC-001); no daily cap (a slow drip could still fill the
table).

## R6 — Prisma in the standalone Docker image

**Decision**: Keep `output: "standalone"`. The Dockerfile's build stage runs
`pnpm install` (postinstall generates the client) then `pnpm build`; the
runtime stage copies the standalone output as today. **Verification is part
of the feature**: quickstart V6 builds the image, runs it with a real
`DATABASE_URL`, and POSTs a suggestion — if Next's file tracing missed the
Prisma engine, this is where it surfaces, and the documented fix is an
explicit `outputFileTracingIncludes` for `.prisma/client` (applied only if
the replay fails; consult the bundled Next docs first per AGENTS.md).

**Rationale**: Next's output tracing generally carries Prisma's generated
client + engine, but it is the classic failure point of exactly this stack —
so the plan makes the check mandatory rather than assuming either way.

**Alternatives considered**: preemptively adding tracing config (cargo-cult if
the default works — verify first); switching off standalone (bloats the image
and changes the deployment for one dependency).

## R7 — Localized strings

**Decision**: Extend the existing `t()` dictionary in `lib/i18n.ts` with a
`suggest` namespace (menu item, dialog title, textarea placeholder + counter,
submit/cancel, thank-you, and error messages for invalid/too-long/rate/
offline). Vietnamese written at the naturalized register (settled glossary;
"Góp ý cải thiện" for the action; no calques) — self-reviewed like chapter
prose, since these strings face readers on every vi page.

**Rationale**: The dictionary is the established single home for chrome
strings (shell, badges, hints all live there); the vi register rules apply to
UI strings the same as prose.

**Alternatives considered**: hardcoding strings in the component with a
locale ternary (drifts from the established i18n pattern).

## R8 — What stays out

**Decision**: No admin/review UI (Neon SQL editor per FR-010); no auth; no
email notifications; no suggestion browsing for readers; no optimistic local
history; no analytics events; **no test-runner introduction** to the site
(the endpoint battery is curl-scripted in quickstart, matching the repo's
verification-battery convention).

**Rationale**: Spec assumptions, kept literally; every omission has a natural
follow-up feature slot if the suggestion volume earns it.
