T002a — a chapter 3.6 test that depended on a clean database
------------------------------------------------------------

  FAIL  deliveries.itest.ts > the failure run >
        invariant 12: the SWEEP disables the quiet endpoint no outcome ever revisits
        AssertionError: expected true to be false

NOT the resume duplicate this chapter is about, and worth separating immediately:
a lane with two intermittent failures cannot measure the rate of either.

ROOT CAUSE. `sweepDisabledEndpoints` is global and takes the hundred oldest
endpoints whose failure run has outrun the hour — `ORDER BY failure_run_started_at
LIMIT 100`. The test ages its own endpoint by 64 minutes and calls the sweep with
the default limit. Every earlier run of that suite leaves endpoints behind with an
open run, and those are older, so they fill the batch and the test's own endpoint
is never reached.

MEASURED, not inferred:

  endpoints with an open failure run                781
  eligible for the sweep at that moment             >100 (drained to 0 by the run)

WHICH ASSERTION CAUGHT IT is the part worth keeping. The test checks
`disabled >= 1` first, and that PASSED — the sweep had just disabled a hundred
endpoints belonging to nobody in particular. Only the assertion about THIS
endpoint could tell "the sweep works" from "the sweep did something". A count is
not a proof of effect.

FIXED, ahead of T048, because T004's measurement depends on it. The five direct
sweep calls in that suite now pass an explicit limit large enough to reach the
endpoint under test whatever else is eligible. The file is fenced by chapter 3.6
and the amendment went to `relay-tutorial/fences/post-series.md`: 3.6 teaches
auto-disable, not the batch size of a test's sweep call, and 3.7 never mentions
webhooks.

Suite after the fix: 49 passed, exit 0.

T005 — what twenty clean runs mean, and what they do to SC-001
--------------------------------------------------------------

Chapter 3.6 observed one failure in six runs and this chapter's spec repeated that
figure. Twenty runs at zero says the rate is lower than that — six runs is a thin
sample and one failure in it supports anything from 2% to 40%.

There is a better explanation than "3.6 was unlucky", and it is worth writing down
because it is about the defect rather than the statistics. The race needs a
backfill query to land inside the gap between an api commit and a Redis publish.
That gap widens under load. When 3.6 measured, the lane took about nine minutes
because the database held 4,068 pending deliveries being retried against dead
endpoints at three seconds each — the machine was saturated and the gap was wide.
That backlog was settled at the end of 3.6, the lane now takes 183 seconds, and the
gap is correspondingly narrow. The defect did not get rarer; the conditions that
exposed it went away.

**SC-001 IS NOW A CRITERION THAT CANNOT FAIL.** It asks for twenty consecutive
passes after the fix. Twenty consecutive passes happen BEFORE the fix. It can no
longer tell a fixed platform from an unfixed one, which makes it exactly the kind
of assertion this project keeps finding and removing — 3.5's "terminated, not
retried" at a 30-second ack wait, 3.6's mutation that could not compile.

Kept, not deleted, and demoted in writing: twenty post-fix runs still prove the fix
introduces no REGRESSION across the whole lane, which is worth having when the
change suppresses frames and its failure mode is a gap. What SC-001 no longer does
is provide evidence that the duplicate is gone.

**SC-002 now carries the entire proof.** The deterministic test fails every time
against today's code and passes against the fixed code, and it does so without
waiting for a race — which is why research R4 built it that way rather than
relying on the journey. The defect itself is not in doubt: R1 established the
mechanism by reading, two code paths can emit the frame and only one of them can
be the second copy.

This is the honest version of the chapter's evidence. The intermittent failure is
how the defect was FOUND; it is not how the fix is PROVEN.

T021 — twenty post-fix runs, and the three attempts it took
-----------------------------------------------------------

SC-001 asks for twenty CONSECUTIVE passes. Getting them required admitting three
times that a measurement spanning two different trees is not a measurement.

  attempt 1   7 runs    abandoned — the drain fix landed at run 7
  attempt 2  12 runs    abandoned — the consumer fix landed after run 12
  attempt 3  20 runs    SURVEY, run to completion deliberately, see below
  attempt 4  20 runs    the measurement

The survey's own numbers, kept because they are the evidence that stopping at the
first red was costing an hour per fault:

  1  pass  2  pass  3  FAIL  4  FAIL  5  pass  6  pass  7  pass
  8  pass  9  pass 10  pass 11  pass 12  pass 13  pass 14  pass
 15  pass 16  pass 17  pass 18  pass 19  pass 20  pass

Two failures, both the signup count, both before the fix for it landed between
runs 4 and 5. **Runs 5-20 are sixteen consecutive passes on the final tree** — not
SC-001's twenty, and not offered as them, but the reason attempt 4 was expected to
be clean rather than hoped to be.

A caveat on what the survey could see: turbo aborts the lane on the first package
failure, so runs 3 and 4 finished in 105s instead of 189s and never reached
gateway, dispatcher or e2e. A survey that stops early under-samples everything
downstream of `@relay/api`. Attempt 4 is the run that covers them.

**Attempt 3 was reclassified rather than abandoned.** After the second restart it
was clear the loop was: run, hit one latent flake, fix it, restart, lose an hour.
Each attempt was finding exactly one fault because it stopped at the first one.

So attempt 3 was allowed to run all twenty with the tree changing underneath it,
which makes it useless as SC-001 evidence and useful as a SURVEY: its job is to
enumerate every remaining fault in one pass instead of one per hour. It is recorded
here as a survey and is not the criterion's evidence. Attempt 4 is.

This is worth writing down because the temptation at attempt 3 was to call the
failures "unrelated flakes", record the run as passing, and move on. They are
unrelated to the resume fix. They are not unrelated to whether the lane can tell
anyone anything, which is the condition chapter 3.6 spent its baseline on and the
condition that let this chapter's own defect hide for seven chapters.


T021a — every fault the runs exposed, none of them the resume duplicate
------------------------------------------------------------------------

unscoped operation and then asserts about its own row.** Each passed alone. Each
passed in the lane too, until a shared resource grew past the budget it assumed.

  1  deliveries.itest.ts   the SWEEP takes the 100 oldest eligible endpoints;
     (T002a, baseline)     781 had accumulated an open failure run, so the test's
                           own endpoint was never in the batch.
                           FIX: an explicit limit big enough to reach it.

  2  deliveries.itest.ts   drainDueDeliveries claims FOR UPDATE SKIP LOCKED. A
     (attempt 1, run 2)    parallel suite holding the row makes one call look
                           exactly like the relay refusing to publish a due
                           delivery. FIX: drain until the row settles.

  3  consumer.itest.ts     invariant 9 called ENV() three times and ENV mints a
     (attempt 2, runs      fresh uuid, so no subject filter could cover its three
      11 AND 12)           events and the durable had to drain ~13,000 older ones
                           inside a fixed 800-poll budget.
                           NOT A FLAKE — A THRESHOLD. Ten clean runs, then two
                           failures in a row. `expected [ …(2756) ] to include`.
                           FIX: one environment, both runtimes filtered to it.

  4  signup.itest.ts       invariant 7 compared `count(*) FROM organisations`
     (attempt 3, runs      before and after one fetch — a GLOBAL count, in a lane
      3 AND 4)             
                           where every other suite signs organisations up.
                           `expected 9918 to be 9917`, twice in a row.
                           FIX: assert the property where it can be attributed to
                           this call — the route refuses, and a request refused
                           before a handler has created nothing.

The fourth is the clearest case of the disease, and it has a history.

**CHAPTER 3.3 ALREADY FIXED THIS ASSERTION, IN THIS FILE.** Its fix-forward section
says so in as many words: *"Chapter 3.1's signup suite asserted that a failed
provisioning left the global organisation count unchanged. That passed for two
chapters and failed here with `expected 884 to be 883` … The count was never the
evidence."* It removed the global count from invariant 1.

The identical assertion at invariant 7, about a hundred lines further down the
same file, was not looked for. It failed here with `expected 9918 to be 9917` —
the same sentence, four chapters and nine thousand organisations later.

That is the finding worth keeping out of all four. Fixing an instance is not
fixing a class, and the cheapest moment to grep for the other instances is while
the first one is still on the screen. A chapter that writes "the count was never
the evidence" and then leaves a second count in the same file has diagnosed the
disease and treated a symptom.

**None of these is the resume duplicate.** It did not reproduce in any of the
runs, before or after the fix, for the reason T005 gives.
