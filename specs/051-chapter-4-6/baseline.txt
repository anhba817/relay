T013 — `daily_usage` IS LEFT IN PLACE, NOT SUPERSEDED
  Four reasons, in the order they decided it:

    1. Chapter 4.2 publishes it and its readers have it. A chapter cannot delete the
       artefact an earlier chapter's reader built without telling that reader.
    2. `analytics/query.mjs` reads it. Unfenced, so the chain does not care -- but a file
       in the tree would stop working silently, and this chapter's whole argument is about
       a script nothing runs. Breaking a second one would be a poor way to make the point.
    3. The ledger refuses an edit to `0001` on its checksum (T010, run red), so
       superseding means a DROP in its own numbered file.
    4. 047 measured `DROP TABLE` on a live view's source succeeding with NO error and
       leaving an orphan answering queries with zeros. The direction that errors is the
       safe one, and here neither direction errors.

  WHAT IT COSTS, AND IT IS PAID IN PHASE 4: both rollups now fill from one
  `message_events` insert, because `0001_daily_usage.sql:19` reads the same source. The
  corpus cleanup cleans both, and a delete on the source reaches neither -- a materialised
  view does not propagate deletes.

T018 — THE `applied 2` EXPECTATION IS UNVERIFIED, AND SAYING SO IS THE POINT
  The task expects one run applying both files in sorted order. Both were applied, but in
  TWO runs, because the files were written one at a time -- so the single-run ordering was
  never exercised. The premise behind it was checked by reading the loop instead
  (`for (const f of files) { ... await run(body) }`, sequential over a sorted list), which
  is weaker than running it. A reader starting from an empty store WILL get the single
  run, and this record is what tells them their output differing from the task text is
  the task's fault rather than theirs.
