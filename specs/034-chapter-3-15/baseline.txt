## T007 — the five dead columns, generated. THE COUNT IS FOUR.

Generated with `grep -rInE` over `services` and `packages`, `--include=*.ts`, excluding
`*.itest.ts`, `*.test.ts`, `src/db/schema.ts` and `dist/`. Patterns are per column, not
per word: the first attempt used `\btype\b` and returned 332 hits, every one of them the
TypeScript keyword.

    channels.archived_at      0 references
    users.avatar_url          0 references
    users.metadata            0 references
    users.banned_at           0 references
    channels.type            11 references   ← NOT DEAD

**`channels.type` is read today.** It is declared in `ChannelRow` (`repository.ts:2204`),
selected in two queries (`repository.ts:2664`, `:2683`), and **returned by the create
route** — `channels.controller.ts:49`, `type: channel.type`. Returning a column is
reading it.

**What is true is that no decision consults it.** The only `.type ===` comparison in
non-test code is on a protocol frame in `packages/e2e/src/harness.ts:296`, not a channel.
Zero conditionals branch on `channels.type` anywhere in the platform.

So the headline is **four columns with no reader at all, and a fifth that is returned and
never decided on** — which is the distinction analysis pass fourteen had already drawn for
`members.role`, and the same one applies here. Fifteen analysis passes read "five columns
and nothing reads them" without measuring it; T007 exists because the count had to be
generated rather than typed, and generating it is what found this.

`users.display_name` measures 10 references and was already excluded from the five: it is
written by `createUser` and by `signup.controller`, and read by nothing. Written is not
read, which is the distinction FR-035 turns on.

**Consequence for the chapter**: FR-036 asks the feature to state, per column, whether it
is live or still unread. The four with zero references are the ones the chapter's number
is about; `channels.type` gets the sentence that it was already returned and is now
*decided on* for the first time, which is a sharper thing to have taught.

## T006 — two fix-forwards, neither of them this feature's work

**One: `packages/outsider` ran inside `pnpm coverage` and cannot.** The suite integrates
against a platform it does not start and throws on purpose when `RELAY_API_URL`,
`RELAY_WS_URL` and `RELAY_DEMO_CREDENTIAL` are absent, printing the five commands that
would satisfy it. `pnpm coverage` sets none. Chapter 3.12 split the lanes so
`pnpm test:integration` is `turbo run test:integration --filter=!@relay/outsider` — **and
put the exclusion in the script and not in `vitest.coverage.config.mts`.** One lane learned
it and the other did not. Now excluded there too, with the reason.

**Two: the api child's health deadline was 30 seconds and needed to be 120.**
`services/gateway/src/isolation.itest.ts` spawns an api child and waits for `/healthz`.
Measured both ways:

    the suite alone, coverage config      6 s,   19 passed
    the suite inside the full lane       90.9 s, 13 passed + 6 skipped, then
                                         afterAll timed out at 60 s

v8 instrumentation on a NestJS boot is most of that 90.9 s. The deadline was tight, not the
api broken — the same 30 s that chapter 3.12's battery blew at run 11 for a different
reason. A generous deadline costs nothing when the api is healthy: the loop polls every
100 ms and returns on the first success. It only changes how long a dead api takes to say
so.

Both fixes together took the coverage lane from **exit 1 / 399 s** to **exit 0 / 316 s** —
83 seconds faster, because the suite no longer spends 30 s timing out and 60 s in teardown.

## T003a — what this feature is predicted to do to the lane, before a test is written

The integration lane measures **407 tests in 192 s = 472 ms per test**, derived from T005's
three runs rather than from chapter 3.12's recorded mean.

`tasks.md` holds **57 tasks that write integration assertions**. At 472 ms per test:

    +60 new tests   →  467 tests,  ~220 s     inside the 240 s budget
    +90 new tests   →  497 tests,  ~234 s     inside, with 6 s to spare
    +120 new tests  →  527 tests,  ~249 s     OVER by 9 s

**So the budget breaks somewhere between 90 and 120 new tests, and 57 tasks will write more
than 90 if they average two cases each.** That is the prediction; T179b is the rule for what
to do when the measurement lands on the wrong side of it, and T180's battery is where the
real number comes from.

Two things this prediction does not get to lean on:

- **The 83 seconds T006 bought back are in the coverage lane, not this one.** Different

- **T006's deadline change does not slow the integration lane.** That suite takes 6 s there

The 240 s figure is chapter 3.12's, set in `specs/033-chapter-3-12/baseline.txt` when the

needs a task to notice.

## T022–T024 — the guard's tenth table, and a verification method that could not fail

`read_positions` is in `sentinel.sql`'s trigger array, `plant()` grows a sixth bait, and
`guard.itest.ts` drives three new cases: the refusal names the table, the message prints
the row (no `id` to interpolate), and a named exemption's write lands. **17 tests, up from
14.**

**T024 asked for the array entry to be removed and the tests to go red. They stayed green,
and the reason is a defect in the harness rather than in the tests.**

The DO block in `sentinel.sql` reads:

    DROP TRIGGER IF EXISTS __sentinel_guard_%1$s ON %1$I   -- for each table IN THE ARRAY
    CREATE TRIGGER __sentinel_guard_%1$s ...

It only drops triggers for tables **it is about to create them for**. Removing a name from
the array does not un-guard the table — it orphans the trigger, which stays installed for
ever on any database that has run the harness once. Confirmed in `pg_trigger`:
`__sentinel_guard_read_positions` was still there after the name was gone.

**Chapter 3.13 recorded "being in the array is not the same as being watched." This is the
same law one turn further: being OUT of the array is not the same as being unwatched.**

So T024 was performed the only way it can mean anything — `DROP TRIGGER` explicitly, then
run:

    all three read_positions cases FAILED, 3 failed | 14 passed
    array restored, setup reinstalls the trigger, 17 passed

**And there is a live consequence beyond this task.** A table removed from that array keeps
its trigger on a developer's long-lived database and does not have one in CI, where the
database is fresh. The two environments would disagree about what is guarded, silently.
Nothing in this feature removes a table from the array, so nothing here trips it. Recorded
because the next person who does will not find out from a test.

## T024a — `read_positions`' bait is not claimable, by construction

`quota_notifications` had to be planted **already delivered** because
`drainQuotaNotifications` claims undelivered rows across every environment — the law that
cost thirteen failures in two unrelated files when it was got wrong.

Nothing in the platform drains read positions: no global sweep, no relay, no batch, no
statement anywhere that touches `read_positions` without an `environment_id`. There is no
state that makes the row claimable, so there is no state to get wrong. Bait 6 plants one
row and one channel — the sentinel had no channel, hence `readChannelId`, and the user is
the usage user already in that environment.

### T013 — drizzle-kit's journal is four migrations stale, and `generate` re-emits the backlog

`npx drizzle-kit generate` produced **`0008_activity_and_read_positions.sql`** — numbered
0008 because `migrations/meta/_journal.json` stops at 0007, while `0008_limit_policy.sql`,
`0009_quotas.sql` and `0010_connection_minutes.sql` already exist on disk. Nothing was
overwritten (the new file sat beside `0008_limit_policy.sql`), but the SQL contained the
whole 0008–0010 backlog — `quota_notifications`, `usage_periods`, the limit-policy columns —
plus this feature's three changes, 25 statements in total.

So the generated file was unusable as a migration and useful as a source of exact DDL. Its
statements for the three changes were lifted, the file and its snapshot deleted, and
`_journal.json` reverted, because `drizzle.config.ts` says its migrator and journal are
"deliberately unused (ADR-16)" — the runner in `src/db/migrate.ts` is the single ledger.
0011 and 0012 were then written by hand in the house style.

**A trap worth naming**: anyone running `drizzle-kit generate` on this repository gets four
migrations' worth of already-applied DDL in one file. The generator is a DDL reference, not
a migration author.
