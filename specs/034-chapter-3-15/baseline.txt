## T006 — two fix-forwards, neither of them this feature's work

**One: `packages/outsider` ran inside `pnpm coverage` and cannot.** The suite integrates
against a platform it does not start and throws on purpose when `RELAY_API_URL`,
`RELAY_WS_URL` and `RELAY_DEMO_CREDENTIAL` are absent, printing the five commands that
would satisfy it. `pnpm coverage` sets none. Chapter 3.12 split the lanes so
`pnpm test:integration` is `turbo run test:integration --filter=!@relay/outsider` — **and
put the exclusion in the script and not in `vitest.coverage.config.mts`.** One lane learned
it and the other did not. Now excluded there too, with the reason.

**Two: the api child's health deadline was 30 seconds and needed to be 120.**
`services/gateway/src/isolation.itest.ts` spawns an api child and waits for `/healthz`.
Measured both ways:

    the suite alone, coverage config      6 s,   19 passed
    the suite inside the full lane       90.9 s, 13 passed + 6 skipped, then
                                         afterAll timed out at 60 s

v8 instrumentation on a NestJS boot is most of that 90.9 s. The deadline was tight, not the
api broken — the same 30 s that chapter 3.12's battery blew at run 11 for a different
reason. A generous deadline costs nothing when the api is healthy: the loop polls every
100 ms and returns on the first success. It only changes how long a dead api takes to say
so.

Both fixes together took the coverage lane from **exit 1 / 399 s** to **exit 0 / 316 s** —
83 seconds faster, because the suite no longer spends 30 s timing out and 60 s in teardown.

## T022–T024 — the guard's tenth table, and a verification method that could not fail

`read_positions` is in `sentinel.sql`'s trigger array, `plant()` grows a sixth bait, and
`guard.itest.ts` drives three new cases: the refusal names the table, the message prints
the row (no `id` to interpolate), and a named exemption's write lands. **17 tests, up from
14.**

**T024 asked for the array entry to be removed and the tests to go red. They stayed green,
and the reason is a defect in the harness rather than in the tests.**

The DO block in `sentinel.sql` reads:

    DROP TRIGGER IF EXISTS __sentinel_guard_%1$s ON %1$I   -- for each table IN THE ARRAY
    CREATE TRIGGER __sentinel_guard_%1$s ...

It only drops triggers for tables **it is about to create them for**. Removing a name from
the array does not un-guard the table — it orphans the trigger, which stays installed for
ever on any database that has run the harness once. Confirmed in `pg_trigger`:
`__sentinel_guard_read_positions` was still there after the name was gone.

**Chapter 3.13 recorded "being in the array is not the same as being watched." This is the
same law one turn further: being OUT of the array is not the same as being unwatched.**

So T024 was performed the only way it can mean anything — `DROP TRIGGER` explicitly, then
run:

    all three read_positions cases FAILED, 3 failed | 14 passed
    array restored, setup reinstalls the trigger, 17 passed

**And there is a live consequence beyond this task.** A table removed from that array keeps
its trigger on a developer's long-lived database and does not have one in CI, where the
database is fresh. The two environments would disagree about what is guarded, silently.
Nothing in this feature removes a table from the array, so nothing here trips it. Recorded
because the next person who does will not find out from a test.

### T031a — the route a customer's client calls supplied no user, for twenty-three chapters

### T041 — the check had nowhere to go, and the first fix leaked

`listMessages(channelId, {beforeSeq, afterSeq, limit})` had no caller parameter, so the task
"add the same check to the history path" was asking for a check with nothing to check
against. Widening the signature was the easy half.

**The first attempt returned an empty page for a private channel a non-member reads**,
reasoning that `listMessages` answers an unknown channel id with `[]`. It does — at the
repository. The ROUTE answers 404, because `messages.service` calls `channelExists` first:

    a channel that does not exist   → channelExists false → 404
    a private channel, non-member   → channelExists TRUE  → 200 and an empty page

Two different answers, so the empty page announced that the channel was there. FR-003 says
every read answers identically to a channel that does not exist, and the only way to hold
that is for **one predicate to produce both refusals** — `channelVisibleTo(channelId,
userId)` replaces `channelExists` on the history path.

**Only pairing the two answers caught it.** A test asserting "200 and an empty page" would
have passed and shipped the leak.

### T044 — the oracle cannot see a symmetric change, and that is the property

First attempt: `notFound()` was changed to return a 403. **All 21 tests stayed green** —
because both halves of every pair call that one helper, so both moved together. That is
chapter 3.12's recorded lesson reproducing itself: *"a route-level 404→403 moves both halves
of the pair and the oracle cannot see it."*

Changing only the private-channel refusal put the pair out of step and the test went red:

    only the private half broken   1 failed | 20 passed
      × answers a non-member's read of a private channel as if it were absent

The oracle detects asymmetry, which is what it is for. A test that could see a symmetric
change would be a test asserting a status code, and a status code is the half that says
nothing.

### FR-047 superseded, and a shipped test rewritten rather than deleted

Chapter 3.12's `refuses type private, naming the field (FR-047)` asserted the enum rejects

test was rewritten to refuse a THIRD type — `secret` — which keeps the half of it that is
still true and still valuable: EIR-API-04 has carried `field` since chapter 1.3 and nothing
set it until chapter 3.14.

## Phase 7 — archiving, and the order that hides it

### FR-021a's order, with one slot deliberately empty

    ban            → not implemented here. `users.banned_at` has no reader until
                     chapter 3.16 (T155a), and the slot sits ahead of the channel
                     read so a banned user gets one answer for every channel id.
    membership     → phase 3
    archive        → this phase, BELOW membership

**Reversed, the archive refusal becomes an existence oracle**: a non-member of a private
archived channel would learn it exists from `channel_archived`. T072b tests that from
outside, with a control — a MEMBER of the same archived channel does get
`channel_archived`, so the check is live and the ORDER is what hides it from the

archive check simply did not work.

The empty slot is left visible in the code rather than filled with a comment elsewhere. A
reader who finds two checks where the requirement names three should be able to see which
one is missing.

### A typed domain error, not a `protocolError` from the repository

The first draft threw `protocolError("channel_archived", …, 403)` inside
`repository.sendMessage`. That puts an HTTP status in the layer whose job is to not know
about HTTP — and the repository has raised `ChannelNotFoundError` since chapter 2.2 and let
the service map it. So `ChannelArchivedError` joins it, and `messages.service` maps it to
403 with the code. The pattern was already there; the first draft ignored it.

### TWO TESTS FAILED ON THEIR CONTROLS BECAUSE AN EARLIER TEST MUTATED SHARED STATE

Both in the same shape, both caught by a control rather than by the assertion:

**T072b** used the suite's `privateChannelId`, and T057 above it removes `insider` from that
channel. By the time T072b ran, its "member" was not one — the control asked for 403 and got
404. Fixed by giving the test its own channel and member: `repo` is now suite-scoped for
exactly that.

**T078a** failed the same way in the gateway suite: T058's `removeSelf()` never put the
membership back, so two tests later the attacker was not a member of their own channel and
the accepted-cursor set was empty. Fixed by adding `rejoinSelf()` and having T058 restore
what it removed.

**A test that depends on the order it runs in is a test that will fail for a reason it does
not name.** Both of these failed on the control and not on the subject, which is the only
reason the cause was obvious rather than mysterious. A suite whose tests each assert one
thing and restore what they touched is the version of this that does not cost an hour.

### T078 — what "the count is still true" means

The spec's edge case is a channel archived while a user has unread messages in it.
Archiving writes ONE column on `channels` and touches no message and no read position, so
`last_sequence` is what it was, every read position is what it was, and the arithmetic
between them is unchanged. Asserted on the sequence rather than on a count, because the
count is phase 12's route — this is the invariant that makes the count safe, tested where it
can be.

### T078a — a no-op proved rather than assumed

FR-022's second clause had no task for eleven analysis passes. The answer: an archived
channel stays in the session and its resume cursor is still accepted, because archiving
touches no membership. Nothing new arrives because nothing new can be sent — the refusal is
at the write, not at the subscription.

"We changed nothing so nothing broke" is the sentence the test replaces. Archiving could
plausibly have been implemented by removing memberships, and then a member would have
silently lost the channel from their session.

### T116 — THE PLAN, AND THE LANE CANNOT SEE IT

The test lane's **largest membership set is five channels**, over 26,818 channels and
88,503 memberships. T116 predicted this — "the test lane is too small to notice" — so the
measurement was taken the way R4 took its own: a synthetic environment, one user, N
channels, membership in all, staggered activity, removed afterwards.

    N          first page              deep page (cursor at the Nth)
    1,000      0.46 ms  top-N heapsort  —
    5,000      2.22 ms  top-N heapsort  0.49 ms
    20,000    10.62 ms  top-N heapsort  0.03 ms
    50,000     9.06 ms  NO SORT         0.03 ms

**No sequential scan at any size.** Every access path is an index scan.

**THE FIRST PAGE IS THE MOST EXPENSIVE ONE, which is the reverse of an offset
paginator.** The keyset predicate cuts the input set down, so paging gets *cheaper* as
it goes: 10.62 ms for the first page of a 20,000-channel user, 0.03 ms for the last.
With `OFFSET` the same walk gets more expensive with every page, and that asymmetry is
the argument for a keyset stated as a number rather than as a principle.

**AND THE INDEX THIS PHASE ADDED IS NOT THE ONE THE PLANNER USES — until it is.** Up to
20,000 memberships the plan drives from `members_user_channel`, joins to `channels` by
id, and **sorts** — a top-N heapsort over the user's whole membership set, bounded at
28 kB because only 26 rows survive. `channels_environment_last_activity` goes unused.

At 50,000 the planner flips: a parallel ordered walk of
`channels_environment_last_activity` with a membership probe per row, **no Sort node at
all** — and it is *faster* than the 20,000 case (9.06 against 10.62). The index earns its
place at the scale where walking the environment's channels in activity order is cheaper
than sorting one user's memberships, and the planner finds the crossover without help.

So the cost of this listing scales with **memberships per user**, not with messages — and
that is the point of the column. R4 measured `max(messages.created_at)` at 159 ms with a
sequential scan over every message in the environment; this is 2.2 ms at 5,000 and never
touches `messages` at all.

### T113 — the tie moved suites, and no setter was added

Two channels sharing a `last_activity_at` cannot be produced through the API: the column
is written from the message's `created_at`, `now()` is the transaction timestamp, and
every send is its own transaction. Constructing the collision takes a raw `UPDATE`.

`repository.itest.ts` is on `eslint.config.mjs`'s driver-exempt list — the layer under
test IS the query layer — and `users.itest.ts` is not. So the tie tests live there, and
the alternative was rejected on purpose: adding `setLastActivityAt` to the repository so
the route suite could reach one would have put a method in production code **whose only
caller is a test**, in a feature whose subject is columns nothing reads.

Both tie tests fail without the `id` in the key, in the two different ways the predicate
can be wrong: `<` on the timestamp alone skips the second tied row, `<=` returns the
first for ever.

### T117 — THE TASK ASKED FOR 400 AND 400 IS THE LEAK

T117: "a cursor naming a channel in another environment **400** rather than 404 or an
empty page — anything that distinguishes 'exists elsewhere' from 'malformed' is the leak
the suite exists to catch."

The reason is right and the mechanism inverts it. To answer 400 for a **foreign** id, the
server has to look that id up in the global `channels` table and find it — and then a
uuid that exists in another tenant gets a different answer from a uuid that exists
nowhere. That is the distinction SC-002 forbids, implemented deliberately.

So the cursor is validated for **shape** and its id is never resolved. A keyset position
does not have to exist: `(last_activity_at, id) < (ts, id)` is a comparison, not a
lookup. The test asserts what the requirement wanted — a foreign cursor and an invented
one produce **byte-identical** responses — and the route answers 200 to both.

The lookup would also have broken a real client: a user removed from a channel between
pages would find their cursor rejected mid-pagination.

### T108 — the third write in the task does not exist

T108 asks that "a member joining, a rename or an archive" not move the activity column.
**This platform has no rename.** `POST /v1/channels` is idempotent on the external id and
its repeat branch returns the existing row without writing `name` or `metadata`; no other
route or repository function updates them. A rename cannot move the column because a
rename cannot happen.

Second task this feature has that named an operation the platform does not have — T087's
subscribe frame was the first, and both were found by looking for the thing rather than
by re-reading the task.

### T118 — the pagination drift, and it is the opposite of history's

Chapter 2.4 documented history's drift: a message arriving mid-pagination appears on a
page the client has not fetched yet, and never on one it has.

**This ordering drifts the other way.** The key is `last_activity_at desc`, so a channel
that takes a message moves toward the FRONT — toward pages already fetched. A client
paging through a busy tenant can therefore:

- **miss a channel entirely**: page 1 is fetched, channel X on page 3 takes a message and
  moves to position 2, and the client's page-2 cursor is already past it. X is in no page
  the client receives.
- **never see a channel twice**, which is the one guarantee that does hold. The cursor is
  strictly decreasing in `(last_activity_at, id)` and a moved channel moves to a position
  the client already passed, so it cannot be re-served.

So the listing is **at-most-once per page walk, not exactly-once**, and the direction is
worth stating: history's drift hides new rows, this one hides *moved* rows. A client that
needs a complete set takes the whole walk and accepts that a channel active during it may
be absent; the next walk starts at the front and finds it immediately, which is where an
active channel belongs.

Not fixed by ordering on an immutable key. `created_at desc` would page exactly once and
answer a different question — "your newest channels" is not "your most recently active
channels", and FR-014 asks for the second.
