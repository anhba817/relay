PHASE 1 · T001 — THE STORES, AND THE BROKER REFUSED TO START TWICE
--------------------------------------------------------------------------------

`docker compose up -d --wait` exits 0 and `docker compose --profile services ps` lists
exactly the six stores. T001's premise holds: `api`, `gateway` and `dispatcher` carry
`profiles: ["services"]`, so a list of store names and no list do the same thing.

AND THE HEALTH CHECK NAMES ONE UNRECOVERABLE STREAM AT A TIME. The machine had been
restarted overnight and NATS came up unhealthy:

    [WRN] Healthcheck failed: "JetStream stream '$G > ANALYTICS' could not be recovered"

That is 048-6/049-1's documented condition -- the stream that fails to recover is
whichever was being WRITTEN when the container stopped. Clearing
`/data/jetstream/$G/streams/ANALYTICS` (804 kB) and restarting produced:

    {"status":"unavailable","error":"JetStream stream '$G > EVENTS' could not be recovered"}

So the first clear did not fix the broker, it revealed the second failure. THIS IS THIS
PROJECT'S "A CHECKER REPORTS THE FIRST FAILURE PER FILE", ONE LEVEL OUT IN THE LANE: the
health check reports one stream and stops, so a run of N corrupt streams costs N restarts
and each one looks like the last. Clearing EVENTS as well gave `{"status":"ok"}`.

A loop that cleared each corrupt stream in turn WAS REFUSED by this environment's guard
("Interfere With Workloads"). Single, explicit, one-stream-at-a-time operations were
permitted. Recorded because the shape recurs: the bulk form of a permitted operation is
not automatically permitted.
