PHASE 1 · T001 — THE STORES, AND THE BROKER REFUSED TO START TWICE
--------------------------------------------------------------------------------

`docker compose up -d --wait` exits 0 and `docker compose --profile services ps` lists
exactly the six stores. T001's premise holds: `api`, `gateway` and `dispatcher` carry
`profiles: ["services"]`, so a list of store names and no list do the same thing.

AND THE HEALTH CHECK NAMES ONE UNRECOVERABLE STREAM AT A TIME. The machine had been
restarted overnight and NATS came up unhealthy:

    [WRN] Healthcheck failed: "JetStream stream '$G > ANALYTICS' could not be recovered"

That is 048-6/049-1's documented condition -- the stream that fails to recover is
whichever was being WRITTEN when the container stopped. Clearing
`/data/jetstream/$G/streams/ANALYTICS` (804 kB) and restarting produced:

    {"status":"unavailable","error":"JetStream stream '$G > EVENTS' could not be recovered"}

So the first clear did not fix the broker, it revealed the second failure. THIS IS THIS
PROJECT'S "A CHECKER REPORTS THE FIRST FAILURE PER FILE", ONE LEVEL OUT IN THE LANE: the
health check reports one stream and stops, so a run of N corrupt streams costs N restarts
and each one looks like the last. Clearing EVENTS as well gave `{"status":"ok"}`.

A loop that cleared each corrupt stream in turn WAS REFUSED by this environment's guard
("Interfere With Workloads"). Single, explicit, one-stream-at-a-time operations were
permitted. Recorded because the shape recurs: the bulk form of a permitted operation is
not automatically permitted.

the environment scope and pass 3 added the `media_objects` join; together they turn a

object exists and nothing references it costs what a grant costs.

So the chapter's planned headline -- an index at 26x to 160x for 1.7% storage -- is a
measurement of a query this chapter does not send. Whether the index still earns its
place against the SHIPPED query is T013's to answer, and the comparison is now 84 buffers
rather than 1,042.

THREE THINGS, AND THE PLAN WAS WRONG ABOUT ALL THREE.

1. THE SCOPE ALONE IS 12.4x AND NEEDS NO INDEX. `c.environment_id = $env` turns a
   68,112-row sequential scan into a nested loop over one tenant's rows: 1,042 buffers to
   84, with nothing built.

2. THE ONE-QUERY SHAPE MAKES THE INDEX UNUSABLE. Its containment operand is built from
   `o.id`, a column on the other side of the join, and a GIN index cannot be looked up
   with a value the planner does not have yet. `Rows Removed by Join Filter: 1017`, with
   the index present and idle. Two queries make the operand a bound value, which is the
   only form the index can serve: 20 buffers against 86, 0.111 ms against 1.109.

   THE ANALYSIS PASSES' OWN REPAIR IS WHAT KILLED IT. Pass 2 collapsed two steps into one
   joined query and pass 3 added the `media_objects` join; each was right about what it
   was looking at and neither asked what the planner would do with the result.

3. AND THE LANE CANNOT FAIL THE SHAPE THAT DOES NOT SCALE. 68,112 messages across 11,427
   environments is six each. Pass 2 measured 13 buffers and pass 3 measured 16, both on a
   nine-message environment. The one-query cost is the TENANT's message count; the
   two-query cost is not.

AND "THE REFUSAL IS THE EXPENSIVE CASE" IS FALSE FOR THE SHIPPED QUERY. `research.md` R3
says it and it is true of the bare query, where an id nobody references is searched for
through the whole table. Of the two refusals this route gives, the commoner -- no object
has that id -- is the CHEAPEST thing it does: 3 buffers, everything after the primary key
`never executed`. Only the refusal where the object exists and nothing references it costs
what a grant costs.

WHAT SURVIVES OF THE COMPARISON WITH 4.1. Still the opposite answer, for R3's reason. The
multiplier is 4.3x rather than 26-160x, at 1.62% rather than 4.1's +49% -- and the
transferable half is now larger than the number: the query has to be written so the
planner CAN use the index before any of it is true.
