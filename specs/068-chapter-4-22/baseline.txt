T001 (continued) · THE NATS RECOVERY, AND WHAT IT COST
--------------------------------------------------------------------------------
Asked rather than decided: every recovery deletes on-disk stream state. What the
measurement showed before the decision:

    ANALYTICS   63.8 MB   unrecoverable, named by /healthz
    EVENTS       3.9 MB   on disk and NOT LOADED — the live account held neither
    DELIVERIES    64 KB   59 messages, healthy
    jsz          streams: 1 of 3

THE HEALTH CHECK NAMES ONE UNRECOVERABLE STREAM AT A TIME (058), so ANALYTICS was
the only one reported while EVENTS was equally absent. **A health check that
names one fault is not a health check that found one fault** — `jsz` is what
said 1 of 3, and the two instruments disagreed about the size of the problem.

The loss was bounded before the question was asked: ClickHouse already holds
244,972 `api_requests` rows, so ANALYTICS was a drained transport buffer rather
than the only copy.

Decision: recreate the whole volume.

    docker compose stop nats && docker compose rm -f nats
    docker volume rm relay_nats-data          # NOT relay-platform_nats-data
    docker compose up -d --wait nats          EXIT 0, {"status":"ok"}
    jsz  streams: 0 consumers: 0 messages: 0

AND THE VOLUME IS NAMED FOR A PROJECT THIS DIRECTORY IS NOT CALLED. Compose
derives the prefix from the project name `relay`, not from the directory
`relay-platform`, so the obvious `relay-platform_nats-data` answers `no such
volume` and the real one is `relay_nats-data`. One wrong guess, recorded because
the error message is the only thing that distinguishes them.

Infra is green on all seven containers. The streams are 0 and stay 0 until the
api boots: nothing in the infra profile creates them.

PHASE 2 — THE DECISIONS

BEFORE THE DECISIONS: THE COMPOSED API HAD NEVER CREATED A STREAM
--------------------------------------------------------------------------------
With a clean volume the services came up green and `jsz` said **streams: 0**. One
request to `/healthz` and the log said why:

    {"level":"error","service":"consumer","msg":"consumer.poll_failed",
     "error":"NatsError: replicas > 1 not supported in non-clustered mode"}
    {"level":"error","service":"api","msg":"request_log.publish_failed",
     "error":"NatsError: replicas > 1 not supported in non-clustered mode"}

**049-2 REPRODUCING, AND IT WAS DIAGNOSED RATHER THAN FIXED.** That entry named
the cause exactly — `replicaCount()` returns ADR-02's R3 because the Dockerfile
sets `NODE_ENV=production` — and the escape hatch it describes, the
`RELAY_NATS_REPLICAS` override at `jetstream.publisher.ts:65`, **was set
nowhere**. The streams existed because they had been created once from outside
the container, and the volume carried them for nineteen features.

**A DEFECT HELD OFF BY A VOLUME IS NOT A FIXED DEFECT**, and nothing could have
noticed: every local run found the streams already there, and CI builds a fresh
volume but has a `nats` service the lanes drive the same way.

The repair is one line in `compose.yaml` — `RELAY_NATS_REPLICAS: "1"` on the api
— with the reason in the file beside it. Measured after:

    jsz  streams: 2    EVENTS msgs=0    ANALYTICS msgs=5
    publish failures in the following 60 s: 0

**This is a change outside the chapter's subject and FR-009 says there must not
be one.** It is recorded here rather than hidden: without it the composed api
cannot create a stream, so T058's quickstart — NFR-USE-03's whole verification —
cannot run at all, and neither can any later chapter's. T059 will show
`compose.yaml` in the diff and this paragraph is its answer.

T008 · THE COMPATIBILITY PATH — CONDITIONAL, AND THE DEFAULT IS NOTHING
--------------------------------------------------------------------------------
FR-007 applies only if something changes an opaque token. The cursor carries a
channel uuid every one of the thirteen routes accepts after this chapter, so
FR-006 does not reach it and the default is to leave it alone. **Changing nothing
is the only option with no silently-wrong-page risk**, and that is the whole of
the argument. Revisited only if T026's sweep produces a reason.

T009 · THE TIE-BREAK — ONE QUERY, AND THE OUTCOME IS A CLAUSE
--------------------------------------------------------------------------------
The outcome was settled at analysis pass 3: the IDENTITY wins a true tie. The
procedure was not. Measured against 41,772 channels, warm:

    where environment_id = $1 and (external_id = $2 or id = $2::uuid)
    order by (external_id = $2) desc limit 1

    Limit -> Sort -> Bitmap Heap Scan                 shared hit=11   0.068 ms
      BitmapOr
        Bitmap Index Scan …_environment_id_external_id_unique   Index Cond
        Bitmap Index Scan channels_pkey                         Index Cond

**Both arms are index scans with real conditions. 4.18's `OR`-lands-in-a-Filter
does not happen here**, which is the thing that had to be checked before choosing
and not after. Against ~3 buffers for a single lookup, eleven buffers buys one
round trip instead of two on all 173 uuid call sites.

DECISION: the one-query form, behind the shape test. A value that cannot parse as
a uuid takes the identity-only query and is never cast.

AND THE KEY ARM'S TENANCY IS A HEAP RECHECK, NOT AN INDEX CONDITION — a foreign
tenant's row enters the bitmap and is filtered on the heap. That reads as a leak
and is not: today's plain `channels_pkey` lookup does the same, `Filter:
(environment_id = …)`. Written down because the next person to read the plan will
reach for the alarm.

**The outcome is a clause.** Which identifier wins when both could match is
behaviour a customer can observe, so constitution VI's first bullet applies and
it joins FR-CHN-11 rather than living in a comment. T027 writes both.
