PHASE 2 — THE CORPUS. Recorded 2026-09-13.

The seeder was written against documents and then run. THE DOCUMENTS WERE WRONG
ABOUT THE SCHEMA IN THREE PLACES AND THE CODE WAS WRONG IN THREE MORE. Each is
recorded with what found it, because five of the six were invisible to reading.


WHAT THE SCHEMA SAID THAT NO DOCUMENT KNEW

  1. ONE APPLICATION CANNOT HOLD THREE ENVIRONMENTS.
     `unique (application_id, kind)` — and the schema's own comment names the
     clause: "FR-TEN-04 says exactly two environments per application."
     Every artifact said organisations 1, applications 1, environments 3.
     Found by: the first run, 23505, `Key (application_id, kind)=(…, development)
     already exists`. Corrected to one organisation, one application per
     environment — which is also what the product means.

  2. THE TABLE IS `members`, NOT `channel_members`.
     `memberships` exists and is a different table: humans in organisations.
     Every artifact named a table that does not exist.
     Found by: 42P01 on the first count.

  3. `addMember` WRITES AN OUTBOX ROW.
     The contract said "no outbox row, no event. The corpus is data, not
     history." The first floor run left 12,001 outbox rows — exactly one per
     membership, `channel.member_added` (FR-WHK-02). Nothing drains them against
     a scratch database, so they would sit as bait in a corpus claimed to hold
     none.
     Found by: counting, not reading. The seeder now clears them and REPORTS
     `created.outbox` rather than the contract asserting zero.


WHAT ONLY VOLUME FOUND

  4. A SMALL RANDOM FORMATS AS SCIENTIFIC NOTATION.
         invalid input syntax for type interval: "3.191957288484204e-05 days"
     `(random() * 90 || ' days')::interval` round-trips through text. A 2,000-row
     smoke test never produced a value small enough; 1.6 million rows did, on the
     first floor run. Replaced with `random() * 90 * interval '1 day'`, which
     stays numeric and has no text form to get wrong.

  5. A UNIFORM OFFSET CANNOT PUT AN EXACT COUNT IN THE WINDOW.
     First floor run: 999,786 in-window against a requested 1,000,000 — binomial
     noise around three quarters, 0.02% low, and still short of a floor stated as
     "≥1,000,000". The two segments are now placed separately: `inWindow` rows
     over 90 days and the rest over the remaining 30. Density is identical by
     construction — measured at 1,111 rows/day either side — and the count is
     exact. A design in which the tolerance cannot arise beats one that states a
     tolerance.

  6. THE REFUSAL REFUSED BY CRASHING.
     The "database already exists" path opened a second pool with
     `require("pg")`, which does not resolve from `scripts/` — `pg` belongs to
     `services/api`, not the root. It printed `Cannot find module 'pg'` instead
     of its message, and nothing reaches that path on a normal run because
     nothing seeds the same database twice.
     Found by: running it twice on purpose.

PHASE 3 — THE MEASUREMENTS. Recorded 2026-09-13.

THE CHAPTER'S HYPOTHESIS WAS FALSIFIED TWICE, AND THE RESULT IS BETTER THAN THE
ONE THAT WAS PLANNED.

Corpus: 1,000,000 messages in the subject environment's 90-day window, of
1,333,334 in the environment and 1,600,000 in the database. 2,000 channels,
5,000 people, 120 days ending at seed time. Environment as pinned in Phase 1.


THE FOUR NUMBERS

                        baseline      counterfactual      delta
    query, best of 3     585.9 ms         560.2 ms       -4.4%
    query runs         [611.2, 585.9,   [579.5, 560.6,
                         586.5]           560.2]
    send p95, quiet       20.5 ms          19.0 ms       mean of two control loops
    send p95, beside      13.7 ms          11.6 ms       102 queries alongside
    table                  179 MB           383 MB       +204 MB (the UPDATE rewrote
                                                          every row; no VACUUM)
    indexes                168 MB           275 MB       +107 MB


1. THE ANALYTICAL QUERY DOES NOT TAX THE WRITE PATH HERE. IT CORRELATES WITH THE
   WRITE PATH BEING FASTER.

   Beside 102 analytical queries over a 60-second window, the send path's p95 was
   13.7 ms against 20.5 ms alone — 6.8 ms FASTER, reproducibly, on both the
   baseline and the counterfactual database.

   THE MEASUREMENT WAS WRONG TWICE BEFORE IT WAS RIGHT, and both are worth more
   than the result:

   - The first version ran the query ONCE beside a sixty-second loop. At ~600 ms
     that is about 1% overlap: 6 of 599 sends had anything running beside them.
     It reported "no effect" from a measurement that could not have shown one.
   - The second ran it continuously and reported 7.9 ms faster — but quiet ran
     first on a cold cache and busy second on a warm one. The comparison
     confounded "beside a query" with "second".

   The third adds a discarded warm-up and a SECOND quiet loop after busy. The two
   quiet loops agree within 0.7 ms (20.9 and 20.2), so ordering is not carrying
   the result. The effect is real and its sign is the opposite of the hypothesis.

   WHAT THIS DOES NOT PROVE (FR-010): that an analytical query never taxes a write
   path. One backend on ten cores against a 179 MB table that fits in cache, at
   ten sends a second because `DEFAULT_LIMITS.send` is 600 a minute. It proves
   that at this volume, on this machine, the neighbour effect is not the argument.


2. THE INDEX THAT WOULD FIX IT BUYS 4.4%, AND THE PLANS SAY WHY.

   baseline        Seq Scan on messages        ~140 ms
                   Hash Join                    277 ms
                   Sort, external merge 33 MB   656 ms
                   GroupAggregate               698 ms

   counterfactual  the join is gone
                   Sort, external merge 33 MB   577 ms
                   GroupAggregate               619 ms

   Removing the join saved about 25 ms of 586. THE SORT IS THE COST AND NO INDEX
   REMOVES IT, because `count(DISTINCT user_id)` per day has to sort a million
   rows by (day, user_id) every time the question is asked. It spills 33 MB to
   disk on both sides.

   SO THE CHAPTER'S ARGUMENT IS SHARPER THAN THE ONE IT WAS PLANNED WITH. It is
   not "the index fixes it and taxes your writes". It is: you cannot index your
   way out of an analytical question when the cost is the aggregation. ClickHouse
   answers it with `uniqState` in an aggregating engine — the distinct count is
   maintained as rows arrive and never sorted at read time. That is the OLAP
   argument, and it survived the measurement that was supposed to make a
   different one.

   The column and index cost +107 MB of index and a full table rewrite for 25 ms.

A THIRD DEFECT THE SEEDER CARRIED, FOUND BY SENDING ONE MESSAGE

    `channels.last_sequence` is where the next message's sequence comes from. The
    corpus wrote sequences 1..N directly and left the counter at 0, so the api
    allocated 1 and collided on `(channel_id, sequence)`. EVERY SEND RETURNED 500
    `internal_error` AND THE LOG LINE CARRIED ONLY THE STATUS. `last_activity_at`
    was the same shape.

    Both are now advanced after the bulk write, and `created` reports
    `channels_with_last_sequence`. A counter maintained on the write path is cheap
    for the write and invisible to anything that writes around it — which is the
    chapter's own subject, one level down.
