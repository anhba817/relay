## Findings the plan did not anticipate

### 1. The interop worry did not materialise — the packaging one did

T004 existed because 2.6 lost time to an ESM/CJS import failure. Both NATS
candidates imported cleanly from CommonJS and published successfully, so the
decision fell to Principle VII instead: `nats@2.29.3` needs one package where
`@nats-io/jetstream` needs two (it carries no transport of its own, which the
first attempt discovered as `Cannot find module '@nats-io/transport-node'`).
Running the experiment was still right; it just answered a different question
than the one it was scheduled for.

### 2. A latent build race, hidden since 3.2

`turbo.json`'s `test:integration` depended on `^build` (dependencies' builds) but
not `build` (its own). Two suites now spawn a child from `services/api/dist` —
the gateway's socket cases from 3.2 and this chapter's crash test — and `nest
build` deletes its output directory before rebuilding. The api's build, pulled in
as `@relay/e2e`'s dependency, could run **while** the api's own integration tests
were reading `dist`, and the child died with `ERR_MODULE_NOT_FOUND`.

Fixed by depending on `build` as well. A second, related gap: the gateway's
`session.itest.ts` needs the api's build output but `@relay/gateway` never
declared `@relay/api`, so nothing ordered them. It passed in 3.2 only because
`dist` happened to be pre-built by hand. Declared now as a devDependency, the way
`@relay/e2e` has since 2.8.

### 3. Three tests assumed a table they do not own

The outbox is deliberately **not** tenant-scoped: one relay drains every
environment's events. That is the right design and it breaks the isolation
habit every other suite relies on — 2.1's per-suite environments cannot help
here. Three assertions had to be rewritten:

- "one `drainOnce()` clears my rows" — false when a batch of 100 is filled by
  another suite's events. Now a bounded loop until this environment is clear.
- "the second pass returns 0" — false for the same reason. Now asserted per
  environment.
- "our relay published the retry" — false while other processes ran relays. That
  one was first weakened to "ends up published, by whoever gets there first",
  then restored to the strong form once finding 4 removed the other relays. The
  weakened version is worth remembering as the fallback when a background daemon
  genuinely cannot be silenced.

The first two are permanent: the drain is global, so a per-environment assertion
loops by necessity.

### 4. A background daemon and a test lane do not share a table quietly

The hardest bug of the chapter was not in the outbox — it was in believing the
lane was quiet. Three suites failed intermittently (1 run in 3, then 1 in 5)
with assertions like `expected 2 to be greater than or equal to 3`: rows this
suite had just written were already published.

Three separate processes were draining the same table:

1. **The e2e journey's api children.** `packages/e2e` spawns real `dist/main.js`
   processes, and a real api runs a real relay.
2. **The gateway's socket suite's api child**, added in 3.2 for the same reason
   and equally real.
3. **The crash test's own child.** The walk pauses between commit and publish so
   the parent can `SIGKILL` it; at a 3-second pause, on a loaded lane, the signal
   sometimes arrived *after* the pause, and the surviving child drained the whole
   table on its way out.

Fixed by making the first two spawn with `RELAY_OUTBOX_RELAY=off` — they assert
message delivery and socket credentials, not events — and by widening the kill
window to 30 seconds, which is never actually spent because the parent kills on
the marker. Six consecutive clean lane runs afterwards.

The general lesson is worth keeping: **this table has no tenant column, so the
isolation that makes every other suite independent does not apply here.** Two
chapters' worth of test-isolation habits (2.1's per-suite environments, 2.6's
per-run subjects) do not transfer, and the replacement is explicit — either
nobody else runs a relay, or you assert only what is true regardless of who
drained.

### 5. Two fix-forwards to earlier chapters

- **3.1's signup suite** counted *all* organisations before and after a failed
  provisioning and asserted the totals matched. Concurrency-fragile from the day
  it was written; it survived two chapters and failed here (`expected 884 to be
  883`) because this chapter's crash tests spawn children that provision their
  own tenants. Removed — the assertion two lines below it, that no organisation
  named `doomed org` survived, was always the one carrying the weight.
- **3.2's gateway suite**, as above, via the build-order declaration.

Both are recorded in the chapter, which is the rule: a chapter that changes code
you copied and does not say so is how a tutorial starts lying.

### 6. The fence budget was wrong by four, and the reasons are the story

Budgeted 12–15, enumerated 15 in T032, shipped **19**. The four extra:
`messages.service.ts` and `internal.controller.ts` (threading the sender's
external id into the envelope, which R11 did not foresee), plus the two
fix-forwards above. Two of the four are Part 3's past rather than this chapter's
present. Recorded rather than absorbed, per T032.
