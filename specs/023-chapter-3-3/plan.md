# Implementation Plan: Tutorial Chapter 3.3 — The Outbox

**Branch**: `023-chapter-3-3` (no branch cut; work proceeds on `main` per the series' practice) | **Date**: 2026-08-08 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/023-chapter-3-3/spec.md`

## Summary

Write and publish chapter 3.3 in English, and advance the platform to the state
it documents: an `outbox` table that receives one event row inside the same
transaction as the message that caused it, and a relay that drains those rows to
JetStream and marks them published. The chapter's spine is a failure a reader can
reproduce — kill the process between the commit and the publish, watch the event
vanish, then watch it survive.

Phase 0 settled the design. The event row joins the transaction `sendMessage`
already opens for its sequence lock, so no call site changes and both doors
produce exactly one event (R1) — except a recognised idempotent retry, which must
produce none. The relay is `SELECT … FOR UPDATE SKIP LOCKED`, publish, mark (R2),
with at-least-once as an accepted consequence rather than a defect (R3). The
crash test uses a real `SIGKILL` from a parent process, because an exception
proves the error path and a kill proves durability (R4). The naive implementation
lives in a demonstration script and never in a service (R5). And the chapter
creates the minimum stream a publisher needs, leaving subjects, consumers and
sharding to 3.4 (R6).

## Technical Context

**Language/Version**: TypeScript 5.9 on Node 22.12+; api compiles as CommonJS
under NestJS 11 (ADR-15), the rest of the workspace is ESM.

**Primary Dependencies**: NestJS 11, Drizzle 0.45 (ADR-16), zod 4, pg 8, jose 6,
and **one addition** — a NATS client. `nats@2.29.3` (monolithic) and
`@nats-io/jetstream@3.4.0` (modular) are both current; the choice is made in
implementation on the basis of which imports cleanly into a CommonJS NestJS
service, **tested rather than assumed** (R11).

**Storage**: PostgreSQL via the compose stack; one forward-only migration
(`0004_outbox.sql`) generated by drizzle-kit and reviewed before it is applied.
NATS JetStream with file storage, already in `compose.yaml` since Part 1.

**Testing**: vitest in two lanes (Docker-free unit; `*.itest.ts` against compose
stores) plus the `@relay/e2e` journey suite, which must keep passing. The crash
test needs a child process and a real signal, which the 2.8 harness established.

**Target Platform**: Linux server (services), static site (tutorial).

**Project Type**: Documentation-first tutorial plus the canonical monorepo it
teaches. The chapter is the deliverable; the code is its answer key.

**Performance Goals**: one additional INSERT per message write, inside a
transaction that already exists. Event availability in seconds, against
FR-ANL-04's 60-second bound — two orders of magnitude of headroom, so the poll
interval is chosen for tidiness rather than latency (R2). No claim the chapter
does not measure.

**Constraints**: the unit lane stays Docker-free; the write path must not depend
on the broker (R9); the relay must be safe to run more than once (R2); no
credential and no message text in any log line; every existing suite keeps
passing; fences byte-match the tag with hunked-diff amendments.

**Scale/Scope**: one published English chapter, one migration, one new table, one
new module, one demonstration script, and twelve invariants. No public route
changes and no existing response changes — this chapter adds a path rather than
retiring a seam, which is why the fence budget is ~12–15 rather than 3.2's 41
(R11).

## Constitution Check

*GATE: evaluated before Phase 0 and re-evaluated after Phase 1 design.*

| Principle | Gate | Verdict |
|---|---|---|
| **I — Tenant isolation is a correctness property** | A new table below the boundary that deliberately has no `environment_id`. Does isolation weaken? | **PASS.** `outbox` is not tenant data — it is work the platform owes itself — and it is written by exactly one code path, which is already scoped: the row can only describe the message the scoped repository just wrote. The environment appears in the subject and the payload, so a consumer can filter, but nothing reads this table on a tenant's behalf. The exception is recorded in `data-model.md` beside the one 3.2 made for the key lookup, rather than left for a reviewer to notice. |
| **II — No acknowledged message is ever lost** | The write path gains an INSERT. | **PASS, with the trade stated.** The insert is inside the transaction that already guards the write, so it cannot half-happen. It does mean a broken outbox table breaks message writes — and the chapter says so out loud, because the alternative is a write that succeeds while silently owing an event, which is the failure being fixed. 2.8's journey suite re-runs to prove the guarantee is intact. |
| **III — Two data paths, never crossed** | This chapter *is* the bridge between them. | **PASS.** The outbox is the sanctioned crossing (SAD §5.1, ADR-06): the operational path writes a row, the relay moves it, and nothing on the analytical side ever reads Postgres. The chapter must be explicit that this is the ONLY crossing, since it is the first one built. |
| **IV — Single writer, single source of truth** | Who authors an event? | **PASS.** The envelope is written complete inside the transaction; the relay adds nothing at publish time (R7, data-model). A relay that authored fields would be a second writer of event data. |
| **V — API-first, developer-first** | The platform's first outward promise about what it emits. | **PASS.** `contracts/events.md` states the envelope, the semantics, and — unusually — what is explicitly *not* promised: ordering. The chapter states the same in prose, because an assumption of ordering is the most likely way a reader gets hurt in 3.5. |
| **VI — Requirement-driven, test-verified** | Twelve invariants. | **PASS on the invariants** — every one has a named test and a requirement to cite (contracts §Invariants). **Unmet on measurement**: the 100% branch-coverage bar for isolation- and durability-relevant code remains unmeasurable in this workspace. See Complexity Tracking; this would be the third chapter to defer it. |
| **VII — Boring by design — scope is a commitment** | The temptations: a dead-letter table, retry accounting, `LISTEN`/`NOTIFY`, emitting all eight FR-WHK-02 event types, promoting the relay to a service. | **PASS.** One dependency, spent on the broker client. One event type, because one public state change exists. No dead letter, no attempts column, no metrics export — each named with the chapter that owns it. `LISTEN`/`NOTIFY` rejected in R2 as an optimisation on a budget with 100× headroom. |

**Post-Phase-1 re-evaluation**: unchanged. The design adds one dependency, one
table and one module, introduces no new tenant column, and changes no public
route.

**Structure Decision**: a new `outbox/` module in the api, beside `auth/`,
`messages/`, `internal/` and `tenancy/`. It lives in the api because ADR-06 put it
there ("a small loop inside the API service initially, promotable to its own
deployment"), and the module keeps the publisher behind a port so that
"promotable" and "broker-swappable" are properties of the code rather than
claims in a document.

## Complexity Tracking

No constitution violations to justify. Three decisions a reviewer may reasonably
question, recorded with their alternatives:

| Decision | Why | What was rejected |
|---|---|---|
| The outbox insert is inside the message transaction, coupling the write path to a second table | it is the entire point: the event and the state change must share a fate (ADR-06) | best-effort insert after commit — the bug the chapter is about |
| A real `SIGKILL` in the test rather than a thrown exception | the property is "what survives when the process stops existing"; an exception proves the error path instead (R4) | fault-injection inside the service, which would ship a code path whose only job is to break |
| The chapter creates a JetStream stream, which is arguably 3.4's material | a relay publishing into a broker with no stream is fire-and-forget, and the chapter's claim would be false at the last hop (R6) | proving the relay against a stub, which would leave two of six success criteria untested |

**Constitution VI, deferred a third time by explicit decision (2026-08-08)**:
NFR-MNT-02's 100% branch coverage for ordering, idempotency and isolation code
cannot be measured — the workspace has no coverage tooling, and adding
`@vitest/coverage-v8` changes `services/api/package.json`, which three published
chapters fence. Principle VI's companion clause is equally unmet: no CI exists,
so "the quickstart MUST run unmodified, verified by automated execution in CI"
has been satisfied by hand every time.

The history is now three chapters long. 3.1 deferred the coverage task (021's
T037). 3.2 deferred it by explicit decision, recording that the remedy would run
**immediately after 3.2 and before 3.3**; it did not. **The owner has accepted
the third deferral and 3.3 proceeds**, with the tooling-and-CI feature moving to
**after 3.3**.

What that costs, stated rather than glossed: this chapter's central claim is
*no event is ever lost*, and it is exactly the kind of claim a coverage bar
exists to keep honest. The twelve invariants are named, tested and cited
(contracts §Invariants), and a real `SIGKILL` proves the durability property
rather than asserting it — so the claim is *evidenced*. What is missing is the
instrument that would show which branches of the relay and the transaction
those tests never reach. When the tooling feature runs, this chapter's outbox
path is the first thing it should measure.
