THE FIRST LANE RUN AFTER `docker compose down -v` IS RED, AND LATER RUNS ARE GREEN
---------------------------------------------------------------------------------
Diagnosed the long way during Phase 2, after `notifications.itest.ts` failed on a Mailpit
timeout. What was ruled out, in order, each by measurement:

    Mailpit's 149 accumulated messages              cleared it; still failed

Then `down -v` was run to reset, and the FIRST lane run after it failed **all 16 dispatcher
tests** — while the dispatcher passed 16/16 when run alone. The second and third full runs
were green, 591/591.

So the lane is not idempotent from cold volumes: the first run creates JetStream state that
the same run's later packages depend on. `ensureStream` lives in
`services/api/src/outbox/jetstream.publisher.ts` and is called from `consumer/runtime.ts`,
which the lane runs with `RELAY_EVENT_CONSUMER=off` — so nothing recreates it deliberately.
CI never sees this because its runner starts with no volumes and its first run IS the run.

**RUN THE LANE TWICE AFTER ANY `down -v`, AND BELIEVE THE SECOND.** Recorded in gaps.md.

FOUR PREMISES THE IMPLEMENTATION CORRECTED
------------------------------------------
1. THE TOKEN'S HOME IS A CYCLE. `MESSAGE_PUBLISHER` declared in `messages.module.ts`
   and imported by the controller closes a loop — the module imports the controller —
   and Nest reports it as a missing dependency, not a cycle: "Nest can't resolve
   dependencies of the MessagesController (MessagesService, Repository, ?)". The token
   moved beside the interface it names.

2. THE REQUEST ID WAS NOWHERE A HANDLER COULD READ IT. `RequestContextMiddleware`
   generated it, set `X-Request-Id`, logged it, and never put it on the request. NFR-OBS-01
   wants it in every structured line and the publish logs from inside the handler, so the
   middleware now attaches it. One line, and it was invisible until something needed it.

3. FR-009 CANNOT COMPARE SENDERS. The first version of that test compared a bot-sent
   REST payload with a person-sent socket payload and failed on `user`. An application
   credential may speak only as a bot (chapter 3.17) and the internal route speaks as the
   token's person, so demanding one `user` demands what the platform forbids. It now
   compares the key sets, the schema, the channel and the text, and names the two fields
   that differ by construction.

4. THE BUILT ARTIFACT IS WHAT THE TESTS RUN. `session.itest.ts` spawns
   `services/api/dist/main.js` and the outsider runs against docker IMAGES, so a change
   in `src` is invisible to both until `pnpm build` and `docker compose build`. T022
   failed once for that reason and the outsider failed once more. This is
   `check:errors reads dist` two levels up.

TWO PREMISES THE INVERSION GOT WRONG FIRST, both worth the chapter's attention
-----------------------------------------------------------------------------
1. A REST send must name a bot user. The first run failed `400` and the failure had
   nothing to do with delivery. Chapter 3.17 made an application credential speak only
   as a bot user of its tenant, so the body needs `user: "outside-bot"`. T003's own
   instruction was to "watch it time out" — it did not time out, it was refused, which
   is exactly the class of wrong-reason failure this feature keeps finding.

2. THE TWO ENTRANCES HAVE DIFFERENT IDEMPOTENCY CONTRACTS. Measured:

       REST body    idempotency_key: z.string().uuid()          messages.schema.ts:13
       socket frame idem_key:        z.string().min(1).max(255) frames.ts

   The second run failed `400 invalid_request` naming `idempotency_key`, because
   `outsider-${Date.now()}` is not a UUID. This matters to FR-006 and FR-007: the retry
   guard this chapter mirrors from the gateway is about idempotency, and the two paths
   do not accept the same keys. Recorded for the chapter and for gaps.md.
