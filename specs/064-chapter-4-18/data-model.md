# Data model — chapter 4.18

## 1. The entry — `audit_log`

One row per moderation action. Written inside the transaction that performs the action
(FR-005), and never written again.

| column | type | null | why |
|---|---|---|---|
| `id` | `uuid` | no | primary key, generated by the api as every other table's is |
| `environment_id` | `uuid` | no | constitution I. Foreign key to `environments`, so no entry can name an environment that does not exist. **No `ON DELETE`, decided at T014a** — which is the convention: all 40-odd tenant foreign keys in `schema.ts` are a plain `.references(() => environments.id)`, the one `onDelete("cascade")` in the file is `media_objects`' own parent/child key, and nothing in `services/api` deletes an environment. Postgres defaults to `NO ACTION`, so an environment holding moderation history cannot be dropped out from under it — for an audit log, the default is what you would choose on purpose. An earlier draft of this cell said entries *die with the tenant*, which is the opposite of what the schema does |
| `occurred_at` | **`timestamptz(3)`** | no | FR-MOD-03's *timestamp*. **Millisecond, not the default microsecond** — see below; it is what makes the cursor exact |
| `actor_kind` | `text` | no | `application`, `user` or `platform`, with a check constraint |
| `actor_id` | `text` | **yes** | the key id for an application credential, the external id for a user, and **NULL for a platform principal** — see §3 |
| `action` | `text` | no | a member of the published set (§2), stored as the set's own name |
| `target_kind` | `text` | no | `user`, `message`, `membership` or `channel`, with a check constraint |
| `target_id` | `text` | no | **the identifier a customer uses to name the thing**: the external id for a user, the uuid for a channel or a message, because those are what the routes take. See §3a — the write site does not always hold it |
| `request_id` | `uuid` | no | FR-MOD-03's *request ID*, joining an entry to the request log's row for the same request |

**`timestamptz(3)` AND NOT THE DEFAULT, BECAUSE THE CURSOR COMPARES THIS COLUMN TO A VALUE
THAT CAME BACK OVER THE WIRE.** Postgres defaults `timestamptz` to microsecond precision —
measured, `now()::timestamptz` is `2026-10-02 08:10:55.083489+00` — and the platform serialises
with `toIso`, which is `value.toISOString()` and emits milliseconds. A cursor minted from the
transmitted value and compared against the stored column loses the trailing microseconds, and
in DESC order **every row between `.083000` and `.083489` is excluded from the next page**. The
tiebreaker above does not save it: the pair's first element is already wrong.

**This is the first keyset cursor over a timestamp column in Postgres in this platform**, which
is why nothing has met it before. The request log's cursor is exact because its column is
`DateTime64(3, 'UTC')` and its wire format is millisecond — the same instant both ways. The
message history cursor pages on `seq`, an integer. Three cursors, three precision stories, and
only this one could lose rows.

**And the constitution's constraint says so in as many words** — *"All timestamps are stored and
transmitted in UTC, RFC 3339, millisecond precision"* — while **all 40 existing `timestamptz`
columns are precision 6**. The platform-wide deviation is not this chapter's to repair; this
column is declared `(3)` because it is the one place the deviation would cost a reader rows.

**`occurred_at`, not `created_at`, and the choice is deliberate rather than stylistic.** Every
other operational table in this schema uses `created_at` for *when the row was written*. Here
the two instants are identical by construction, because the row is written inside the action's
transaction — and that is exactly why the column should not be called `created_at`: a reader
who sees the familiar name will reasonably wonder whether the row could have been written
later than the action, and the answer is that it cannot. The name says which question it
answers. **If a later chapter ever writes an entry outside the action's transaction, this name
is the thing that will have to change, and that is the right place for the friction.**

**One index: `(environment_id, occurred_at DESC, id DESC)`.** It is the read route's only
access path (FR-006) and the tenancy predicate's.

**THE THIRD COLUMN IS THE CURSOR'S TIEBREAKER AND IT IS NOT OPTIONAL.** `occurred_at` is not
unique — two moderation actions in one instant is what a bulk script does — and a keyset cursor
on a non-unique column **skips or repeats rows at every page boundary**. The precedent this
chapter copies had already measured it. `request-log/reader.ts:183` compares the pair and says
why:

> THE PAIR, COMPARED AS A TUPLE… 42 `(environment_id, ts)` pairs in this lane hold more than
> one row; a `ts`-only comparison skips or repeats all 89 of them.

So the cursor is `(occurred_at, id)` compared as a row value, and the index carries `id` so the
planner can use it. **An earlier draft of this file specified the two-column index and the
contract said "keyset, as the request log's" — citing a precedent is not reading it.**

Chapter 4.15's rule applies at the point the index is added — *measure an index you add* — and
chapter 4.13's applies to how it is verified: ask for `Index Cond` per table under
`SET LOCAL enable_seqscan = off`, because on a freshly migrated database a sequential scan is
the planner making the right choice.

### What the table does not have

- **No `details` or `metadata` column.** FR-MOD-03 lists five fields and the chapter supplies
  five. A free-form blob is where a schema goes to stop being checkable, and chapter 4.16
  already paid for a column whose name read as its subject and held something else.
- **No `result` or `status`.** FR-008 was decided by reading all eight write methods:
  **a refused action earns no entry** — a refusal is a request and the request log already
  holds every one with its status — and **an action that changes no state earns no entry.**

  **The test is mechanical: did the write statement affect a row.** Uniform across the eight,
  and a choice at three of them, because `deleteUser`, `setMemberRole`, `archiveChannel` and
  `unarchiveChannel` all return a boolean meaning *the row was FOUND*. Each says so in its own
  comment, and phase 2's survey read `deleteUser`'s `false` as the no-op discriminator before
  reading what it meant — a second deletion changes nothing and still answers `true`, because
  `?? new Date()` keeps the original instant. The discriminator there is `alive.deletedAt`.
  Archiving an archived channel and setting a role a member already holds do write entries:
  the statement really did affect a row, and knowing whether the VALUE changed would need a
  SELECT inside the write transaction, which is the query `deleteMessage` argues against
  paying on every call.

  A column making both answers expressible would have made neither one true.
- **No soft delete, no `updated_at`, no version.** The trigger refuses both verbs; a column
  that only an `UPDATE` could fill would be a column nothing can fill.

## 2. The moderation set

Not a table — a **list checked against the derivation that already runs against the router**,
`services/api/src/audit/moderation-routes.ts`, with the both-directions pair whose property
FR-003 needs is the one `targets.ts`'s header states: *"A derived target matching no entry
fails the suite, and an entry matching no derived target fails it too."*

**A SIBLING RATHER THAN A FIELD ON `targets.ts`, DECIDED AT T011 BY MEASURING BOTH.** A field
required on all 47 entries — required, because *nothing may be exempt by omission* — is 16
hunks at `-U6` and 510 published lines at the width that collapses them to four, against a
591-line file: a change touching every entry of a list has no economical diff. The hunks could
not go in the chapter either, because the appendix already carries six `targets.ts` hunks whose
anchors the insertions fall inside. And the argument recorded for the field — *two lists can
fall out of step with the router independently* — is not true when both check against the
router. They can drift from each other, and neither is derived from the other, so that costs
nothing. The sibling also keeps a compliance classification out of the suite constitution VI
names as gating releases.

Each mutating, tenant-reachable route gets one of:

| value | meaning |
|---|---|
| `moderation` | the action owes an entry whoever made it |
| `moderation-when-application` | it owes an entry **only when an application credential made it** — the same route, the same verb, a different principal |
| `not-moderation` | it owes none, **with a reason recorded beside it** |

**THE THIRD VALUE EXISTS FOR EXACTLY ONE ROUTE AND THE MECHANISM ALREADY HAS THE VOCABULARY.**
`targets.ts` carries `accepts: "either"` on four routes, and
`DELETE /v1/channels/:channelId/messages/:messageId` is the one where the credential decides
whether the action is moderation. The repository says why in its own comment: *"FR-MOD-02
grants a tenant key deletion of any message and is silent on editing… So this route accepts
both credential classes."* An application credential deleting somebody else's message is
FR-MOD-02; a user deleting their own is FR-013 of chapter 3.23, and **a compliance log that
records ordinary user activity is a different and worse artifact**.

The other three `either` routes need nothing: `POST …/messages` and
`PUT …/channels/:channelId/read` are not moderation under either credential, and
`GET …/messages` is a read.

**And the condition is free at the write site.** `deleteMessage` already takes
`userId?: string` where *"`undefined` MEANS THE TENANT"*, and T022's context carries the
actor's kind. The entry is written when the actor is an application credential — one branch,
no lookup, and it is the same fact the authorship check already reads three lines up.

**Nothing may be exempt by omission**, which is the existing mechanism's rule and the reason
this classification rides on it rather than beside it. A route added later with no decision
fails the suite (SC-004).

**The population is 24 tenant-reachable mutating routes**, and that number came from a booted
application: `targets.itest.ts` printed `gauntlet targets: 47 derived, 39 attacked, 8 exempt`,
of which 33 are mutating and **9** are `/internal/`. The estimate this paragraph carried before
phase 1 said eight internal routes and therefore 25, and that 25 reached six documents — it came
from a regex that missed one. The derivation is the source; a count taken from the text is a
guess about it.

**The classification itself is in `specs/064-chapter-4-18/routes.md`**, a reason on every row:
7 `moderation`, 1 `moderation-when-application`, 16 `not-moderation`. The spec expected nine
inclusions and the rule yields eight, because the ninth — *edit another author's message* — is
**not a reachable action**: that route is `accepts: "user"`.

### What the `action` column holds

**`METHOD /path`, the derived route's own key** — `POST /v1/users/:externalId/ban`,
`DELETE /v1/channels/:channelId/archive` — and not a verb invented for the log. It is the
string `targetKey` builds, so one name serves three readers: the column, the `action` filter on
`GET /v1/audit-log`, and `moderation-routes.ts`'s both-directions check, which is then a set
comparison rather than a mapping somebody maintains. A reader joins an entry to a route by
reading it.

Chapter 4.16 lost a day to a field renamed between its producer and its reader. The defence is
not care; it is having one name a check compares in both directions.

## 3. The actor, and the two things it cannot say

`ApplicationPrincipal` carries `keyId`. `UserPrincipal` carries `userExternalId`.
`PlatformPrincipal` carries neither, and its `environmentId?: undefined` is deliberate
(chapter 4.4).

**An application credential names a key, not a person.** FR-MOD-03 says *actor*, and the
strongest thing this platform can say is which credential was presented. Who held it is not
knowable from here, and FR-007 requires that limit to be stated in the clause record rather
than discovered by whoever first reads an entry expecting a name.

**A platform principal has no tenant**, so an internal caller's action cannot be scoped to an
environment and cannot appear in a tenant's read. Every `/internal/` route is therefore outside
the set by construction rather than by decision — which is worth saying, because *outside by
construction* and *decided to be outside* are different claims and only one of them needs a
reason.

## 3a. The identifier the write site holds is not always the one to store

**`setBanned` resolves the user and hands the repository a uuid.** The route takes
`:externalId`, the service calls `requireUser(externalId)`, and then
`this.repo.banUser(user.id)` — so at the point FR-005 puts the entry, the external id is out
of scope. Storing the uuid instead would publish a value no customer has ever seen and would
need a join on every read, and *"well enough to find it a year later"* is not satisfied by a
key to a row that erasure may remove.

**So the external id is threaded, and the precedent is already in this repository.**
`deleteMessage` takes `userExternalId` for exactly this reason, and says so:

> The deleter as a CUSTOMER sees them, for `metadata.deleted_by` (FR-006a). Threaded rather
> than looked up, exactly as `sendMessage` threads its sender: a SELECT inside the write
> transaction is a query every deletion would pay to learn something the controller already
> holds.

**AND THE SURVEY WAS WRONG ABOUT THREE OF THE FIVE, WHICH T023a FOUND BY OPENING THEM.** This
section said `banUser` and `unbanUser` would gain the parameter. Neither did:

| method | the external id at the write site | so |
|---|---|---|
| `banUser` | `.returning({ externalId })`, read three lines above where the entry goes | no parameter |
| `removeMembers` | a `(SELECT external_id FROM users …)` inside its `RETURNING` | no parameter |
| `unbanUser` | none — and T026 gives it a `RETURNING` for FR-005 anyway | no parameter |
| `setMemberRole` | `.returning({ userId })`, a uuid | **threaded** |
| `deleteUser` | `.select({ id, deletedAt })` | **threaded** |

**A method that already emits a customer-visible event already holds customer-visible
identifiers**, and the two that needed threading are exactly the two that emit no event. A map
written to carry row ids to external ids into `removeMembers` was reverted before it shipped.

**Only the user and membership cases need it at all** — a channel and a message are named by
uuid on the routes that act on them, so for those the identifier the write site holds and the
one a customer uses are the same string.

**AND A MEMBERSHIP IS A PAIR.** `target_kind: "membership"` names a person's standing in one
channel, and the route carries both halves, so `target_id` is `<channel uuid>/<external id>`.
Unambiguous whatever the external id holds — the schema is `z.string().min(1).max(255)` and
permits a slash — because a uuid is 36 characters and cannot contain one, so the first slash is
always the separator.

**This is a signature change and not a behaviour change**, so FR-012's exception is not
engaged: the action does the same thing with the same answer, and one more argument arrives
already resolved.

## 4. State transitions

None. An entry has one state: written.

That is the whole of the model's immutability and it is enforced by a `BEFORE UPDATE OR DELETE`
trigger rather than by convention — measured in research R2, where the obvious alternative
(`REVOKE UPDATE, DELETE`) was found to do nothing at all, because the api connects as a
superuser and a superuser bypasses privilege checks.

**And the enforcement has a scope, which the chapter states rather than implies.** The trigger
refuses the application and refuses accident. It does not refuse `SET session_replication_role
= replica`, which is one line and disables every trigger in the session, nor `DROP TRIGGER`.
Both were measured. The log is immutable to everything short of the database password, and
this platform's api holds the database password.
