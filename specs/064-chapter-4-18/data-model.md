# Data model — chapter 4.18

## 1. The entry

One row per moderation action. Written inside the transaction that performs the action
(FR-005), and never written again.

| column | type | null | why |
|---|---|---|---|
| `id` | `uuid` | no | primary key, generated by the api as every other table's is |
| `environment_id` | `uuid` | no | constitution I. Foreign key to `environments`, so a tenant's entries die with the tenant and no entry can name an environment that does not exist |
| `occurred_at` | `timestamptz` | no | FR-MOD-03's *timestamp* |
| `actor_kind` | `text` | no | `application`, `user` or `platform`, with a check constraint |
| `actor_id` | `text` | **yes** | the key id for an application credential, the external id for a user, and **NULL for a platform principal** — see §3 |
| `action` | `text` | no | a member of the published set (§2), stored as the set's own name |
| `target_kind` | `text` | no | `user`, `message`, `membership` or `channel`, with a check constraint |
| `target_id` | `text` | no | identifies the thing acted on well enough to find it a year later |
| `request_id` | `uuid` | no | FR-MOD-03's *request ID*, joining an entry to the request log's row for the same request |

**`occurred_at`, not `created_at`, and the choice is deliberate rather than stylistic.** Every
other operational table in this schema uses `created_at` for *when the row was written*. Here
the two instants are identical by construction, because the row is written inside the action's
transaction — and that is exactly why the column should not be called `created_at`: a reader
who sees the familiar name will reasonably wonder whether the row could have been written
later than the action, and the answer is that it cannot. The name says which question it
answers. **If a later chapter ever writes an entry outside the action's transaction, this name
is the thing that will have to change, and that is the right place for the friction.**

**One index: `(environment_id, occurred_at DESC)`.** It is the read route's only access path
(FR-006) and the tenancy predicate's. Chapter 4.15's rule applies at the point it is added —
*measure an index you add* — and chapter 4.13's applies to how it is verified: ask for
`Index Cond` per table under `SET LOCAL enable_seqscan = off`, because on a freshly migrated
database a sequential scan is the planner making the right choice.

### What the table does not have

- **No `details` or `metadata` column.** FR-MOD-03 lists five fields and the chapter supplies
  five. A free-form blob is where a schema goes to stop being checkable, and chapter 4.16
  already paid for a column whose name read as its subject and held something else.
- **No `result` or `status`.** Whether a refused action earns an entry is FR-008's decision and
  it is taken in phase 2 by looking at each action, not by adding a column that makes both
  answers expressible and neither one true.
- **No soft delete, no `updated_at`, no version.** The trigger refuses both verbs; a column
  that only an `UPDATE` could fill would be a column nothing can fill.

## 2. The moderation set

Not a table — a **classification carried on the derivation that already runs against the
router**, `services/api/src/isolation/targets.ts`, whose own header states the property FR-003
needs: *"A derived target matching no entry fails the suite, and an entry matching no derived
target fails it too."*

Each mutating, tenant-reachable route gets one of:

| value | meaning |
|---|---|
| `moderation` | the action owes an entry, and the entry's `action` is this route's name |
| `not-moderation` | it does not, **with a reason recorded beside it** |

**Nothing may be exempt by omission**, which is the existing mechanism's rule and the reason
this classification rides on it rather than beside it. A route added later with no decision
fails the suite (SC-004).

**The population is 25 tenant-reachable mutating routes**, derived: the table parses to 33
mutating entries of which 8 are `/internal/`. That parse is an estimate — a regex over the
source found 47 entries where the file's own `method:` count is 51 — and **phase 1 replaces it
with the number a booted application prints.** The derivation is the source; a count taken from
the text is a guess about it.

## 3. The actor, and the two things it cannot say

`ApplicationPrincipal` carries `keyId`. `UserPrincipal` carries `userExternalId`.
`PlatformPrincipal` carries neither, and its `environmentId?: undefined` is deliberate
(chapter 4.4).

**An application credential names a key, not a person.** FR-MOD-03 says *actor*, and the
strongest thing this platform can say is which credential was presented. Who held it is not
knowable from here, and FR-007 requires that limit to be stated in the clause record rather
than discovered by whoever first reads an entry expecting a name.

**A platform principal has no tenant**, so an internal caller's action cannot be scoped to an
environment and cannot appear in a tenant's read. Every `/internal/` route is therefore outside
the set by construction rather than by decision — which is worth saying, because *outside by
construction* and *decided to be outside* are different claims and only one of them needs a
reason.

## 4. State transitions

None. An entry has one state: written.

That is the whole of the model's immutability and it is enforced by a `BEFORE UPDATE OR DELETE`
trigger rather than by convention — measured in research R2, where the obvious alternative
(`REVOKE UPDATE, DELETE`) was found to do nothing at all, because the api connects as a
superuser and a superuser bypasses privilege checks.

**And the enforcement has a scope, which the chapter states rather than implies.** The trigger
refuses the application and refuses accident. It does not refuse `SET session_replication_role
= replica`, which is one line and disables every trigger in the session, nor `DROP TRIGGER`.
Both were measured. The log is immutable to everything short of the database password, and
this platform's api holds the database password.
