T014  FR-008 PER ACTION, AND THE EIGHT DO NOT HAVE ONE SHAPE
-------------------------------------------------------------------------------------

      Read all eight write methods rather than generalising from `banUser`:

        method             transaction   reports a change        no-op guard
        banUser                yes       `.returning()`          inside the tx
        unbanUser              NO        **no — returns void**   none
        deleteUser             yes       boolean                 inside the tx
        removeMembers          yes       an outcome object       BEFORE the tx
        setMemberRole          NO        `.returning()`          --
        archiveChannel         NO        `.returning()`          --
        unarchiveChannel       NO        `.returning()`          --
        deleteMessage          yes       two-branch return       --

      **A REFUSED ACTION EARNS NO ENTRY.** A refusal is a request, and the request log
      (4.8) already holds every one with its status. An audit log that also holds
      refusals is a second request log with a worse retention policy, and FR-MOD-03's
      five fields — actor, action, target, timestamp, request id — describe something
      that happened.

      **AN ACTION THAT CHANGES NO STATE EARNS NO ENTRY**, and the four that can tell say
      so themselves: `banUser` returns `[]`, `deleteUser` returns `false`,
      `removeMembers` returns an outcome, `deleteMessage` branches. A re-ban writes
      nothing and is recorded as nothing. The entry goes after the guard, inside the
      transaction, where the method already knows the answer.

      **AND `unbanUser` CANNOT ANSWER THE QUESTION AT ALL** — `Promise<void>`, no
      `.returning()`, no transaction. It is half the chapter's opening demonstration and
      it is the one method of the eight that does not know whether it did anything. That
      is T014b's problem and T026's work.

T014a THE DRAFT'S CONSEQUENCE IS THE OPPOSITE OF THE SCHEMA'S CONVENTION
-------------------------------------------------------------------------------------

      `data-model.md` §1 said *"a tenant's entries die with the tenant"*, as a consequence
      of following the schema's usual foreign key. Checked:

        `.references(() => environments.id)` with no `onDelete`      every tenant FK
        `onDelete("cascade")` anywhere in `schema.ts`                1, and it is
                                                                     media_objects' own
                                                                     parent/child FK
        any code that deletes an environment                         none in services/api

      Postgres defaults to `NO ACTION`, so the convention **refuses** a delete that would
      orphan rows. **DECIDED: follow the convention — no `onDelete`.** For an audit log
      the default behaviour is the one you would choose on purpose: an environment with
      moderation history cannot be dropped out from under it, and nothing in the platform
      wants to drop one. §1 is amended, because it stated the consequence backwards.

      Row 22's user case is untouched and stays row 22's (research R8).

T014b FOUR ACTIONS TAKE FR-012's EXCEPTION, AND THREE OF THEM GAIN LESS THAN THE TASK
      SAID
-------------------------------------------------------------------------------------

      FR-005 (the entry is written atomically with the action) and FR-012 (this chapter
      adds no transaction) cannot both hold for `unbanUser`, `setMemberRole`,
      `archiveChannel` and `unarchiveChannel`. FR-005a permits the exception; these four
      take it.

      What each gains is not the same, and the task's own list was wrong about three of
      them. **`setMemberRole`, `archiveChannel` and `unarchiveChannel` already report

      atomicity and a new way to fail, and nothing else.

      **`unbanUser` gains all three**, because it has none: a transaction, a `.returning()`
      that lets it answer T014's question, and a failure mode it did not have. It changes
      signature from `Promise<void>`, which is a published contract — T026's bill.
