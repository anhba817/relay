T001 — THE STREAM HAS MESSAGES AND NO CONSUMER
-----------------------------------------------
    $ curl -s 'localhost:8222/jsz?streams=1&consumers=1'

    ANALYTICS    messages     31  bytes  15,139  consumers 0
    DELIVERIES   messages     46  bytes  14,490  consumers 0
    EVENTS       messages     56  bytes  23,582  consumers 0

**ALL THREE READ ZERO CONSUMERS, AND ONLY ONE OF THEM MEANS ANYTHING.** The compose stack
runs `clickhouse mailpit nats postgres redis`; the api, gateway and dispatcher run from the
lane or the CLI and were not up. So `EVENTS` and `DELIVERIES` show zero because their
consumers are not running, and `ANALYTICS` shows zero because none exists.

The planning probe read this table as evidence before noticing that. **A number that is
right for two different reasons is evidence for neither until you separate them** — which is
what T002 is for.

T004 — THE TEMPLATE THIS CONSUMER MAY NOT REUSE
-------------------------------------------------
`runtime.ts:195` calls `claimEvent(db, durable, parsed!.id, effect)`. The function itself,
read rather than cited:

    return db.transaction(async (tx) => {
      const claimed = await tx
        .insert(consumedEvents)
        .values({ consumer, eventId })
        .onConflictDoNothing({ target: [consumedEvents.consumer, consumedEvents.eventId] })
        .returning({ eventId: consumedEvents.eventId });
      if (claimed.length === 0) return "duplicate";
      await effect();
      return "handled";
    });

A **PostgreSQL transaction**. Constitution III forbids it on this path, and the runtime's own
header says it exists because *"a future consumer forgets to dedupe → double webhooks /
double metering"*. This is that consumer.


T005 — ReplacingMergeTree, WITH IDENTICAL SORTING KEYS
--------------------------------------------------------
    after 1 insert of 1,000 rows              count 1,000
    after an IDENTICAL redelivery             count 2,000   ·   FINAL 1,000

**The planning probe put `generateUUIDv4()` in the sorting key**, so its two batches were not
duplicates at all and it reported 2,000 after `OPTIMIZE FINAL` as though that were a fact
about ClickHouse. A duplicate test whose rows are not duplicates measures nothing and says
something. This run uses one fixed environment id.


T006 — THE DEDUPLICATION TOKEN, AND THE LINE THAT MATTERS
-----------------------------------------------------------
    1. plain MergeTree, same token twice          1,000 rows   the token did NOTHING
                                                               and reported no error
    2. non_replicated_deduplication_window = 100,
       first insert                                 500 rows
    3. same window, REDELIVERY, same token          500 rows   the block is refused

**Line 1 is the finding.** The token without the window deduplicates nothing and says
nothing. The mechanism is not used in this chapter anyway — R7 and R8 are why — but the
failure shape is worth carrying: **a setting that looks configured and does nothing.**
