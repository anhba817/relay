T018b — the promotion's cost, and the asymmetry nobody predicted

    messages rows on this machine                                    394,142
    "has this user ever sent?" — user HAS sent  (the refusal)          0.321 ms
    "has this user ever sent?" — user has NOT sent (the promotion)    14.120 ms

  THE SUCCESSFUL PROMOTION IS THE EXPENSIVE ONE, 44x over the refusal, and the reason is
  that `LIMIT 1` only helps the case that finds something. A user who has sent is
  answered by the first matching row; proving a user has NEVER sent requires reading all
  394,142 rows, because `messages.user_id` carries no index. Both are Seq Scans; only one
  can stop early.

  The task predicted "a filtered scan" and expected the cost to be one number. It is two,
  and the expensive one is the path a customer actually takes when registering a bot they
  just created. Still no index added: 14 ms once per promotion is not worth an index on a
  394k-row table that nothing else would use, and R4's 159 ms figure is a different query
  shape (an ordering join) rather than a scaling factor for this one.

T017 — the description rule was wrong on its first run, and a test found it

  The rule as written was `kind === "person" && description !== undefined`. The common
  shape is `kind` ABSENT, not `kind: "person"` — so `{external_id, description}` sailed
  through and gave a person a description. Corrected to
  `description !== undefined && kind !== "bot"`, which makes a description and
  `kind: "bot"` imply each other within an entry.

  CONSEQUENCE, STATED ON PURPOSE: editing a bot's description through the upsert means
  restating `kind: "bot"`. That is not a change and raises no conflict. Editing it alone
  is what `PATCH /v1/users/:externalId` is for.

T021a — the two exact-shape assertions broke, exactly as predicted

    users.itest.ts  "round-trips display name, avatar url and metadata"   toEqual, broke
    users.itest.ts  "reuses the row when the same external id ..."        toEqual, broke
    48 of 50 passed before the fix; 62 of 62 after the phase's new tests

  This is the argument for exact-shape assertions over `toMatchObject`: they are the only
  ones that notice a field ARRIVING. Both now pin `kind: "person", description: null`.

T023 — the constraint name is on the cause, not the message

  `rejects.toThrow(/users_bot_description_check/)` FAILED while the constraint was
  working. Drizzle wraps the driver error as "Failed query: ...", so the regex never saw
  the constraint name — and a `toThrow` that matches the wrapper would have passed for a
  typo in the SQL too. The assertion is now
  `rejects.toMatchObject({ cause: { constraint: "users_bot_description_check" } })`,
  which is about the constraint rather than about the statement failing.

PHASE 4: USER STORY 2 — A CREDENTIAL CANNOT POST AS A PERSON
------------------------------------------------------------

THE DOCUMENTED REFUSAL ORDER IS NOT ACHIEVABLE AS WRITTEN, and the reason is FR-007b

  `contracts/sending.md` numbers the five refusals 1..5 with sender resolution at 4:

    1 banned?   2 visible?   3 archived?   4 sender resolves?   5 may this credential?

  Step 1 reads the SENDER'S ROW — `UserBannedError` is thrown at `repository.ts:3740`
  and the channel is read three lines later at 3743 — because FR-007b says a ban applies
  to the sender named, not to the caller. So the sender must already be resolved before
  step 1 can run, and resolution cannot be step 4. The achievable order:

    0  resolve the named sender              400, field: "user"   (forced by step 1)
    1  is the sender banned?                 403 user_banned
    2  can the sender see the channel?       404 as if absent
    3  is the channel archived?              403 channel_archived
    4  may this credential send as it?       403 sender_not_permitted

  The contract's load-bearing claim survives: **resolution before the kind check**, so a
  refusal naming a fact about a user cannot be provoked for a channel the caller could
  not otherwise reach. What moved is that the two are no longer adjacent — one is first
  and one is last.

  CONSEQUENCE FOR R5. The kind check could not live in the service: the service runs
  before the repository, so enforcing it there would put it FIRST, ahead of the ban, the
  visibility and the archive, and leak exactly what the ordering protects. It is in the
  repository, which is told `senderMustBeBot` — a CONSTRAINT and not a credential class.
  R5's rule is that the repository must not learn what a credential is, and it does not.

T051 — FR-013's decision, and where the requirement's wording does not fit

  FR-013 asks that the answer be "the same on all four paths". Measured, the four are:

    history      listMessages       user: null            readable
    listing      last_message       user: null            readable
    webhook      MessageCreatedData user: null            readable
    resume       toFrame            row DROPPED           not renderable

  THEY CANNOT BE THE SAME, and the reason is the contracts rather than the code.
  `messageSchema.user` is `z.string().min(1)` in three places in `frames.ts`, so a frame
  cannot carry a null at all; the other three contracts can. Changing the frame contract
  is what `contracts/sending.md` says this chapter does not do, and chapter 3.16's
  frame-shape assertion (T056) is what holds it still.

  THE DECISION THAT IS THE SAME ON ALL FOUR: **never invent a sender.** Where a contract
  can express "nobody", it says null; where it cannot, the row is not delivered. FR-013 is
  satisfied at the level of the decision and not of the wire shape, and the clause reads as
  though the four contracts were alike when they are not.

T054b — `MessageCreatedData.user` stays `string | null`

  Nothing can create a new null: FR-MSG-15 requires a sender and the compiler enforces it.
  The type does not describe what the platform emits — it describes what a subscriber may
  still RECEIVE, because FR-WHK-03 retries for up to two hours and the queue was already
  full when the rule changed. Narrowing it to `string` would be a type asserting that
  something in flight cannot happen.
