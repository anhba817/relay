T002b — FR-MSG-13 is MET, not introduced

  The clause predates chapter 2.2's route. Chapter 3.3 satisfied it by sending
  unattributed, and messages.controller.ts has recorded that reading ever since:
  "A tenant's own server sending on a customer's behalf is FR-MSG-13, not a mistake."
  Thirteen analysis passes read this feature's claim that the SRS had no such requirement.
  A requirement satisfied by doing the opposite of what it says is harder to see than one
  nobody wrote.

  A bot's send is not rejected at exhaustion. In the blockquote, so it reads as a decision.

T004 — FR-USR-01 still holds

  "Relay shall not generate end-user identifiers." A bot's identifier is customer-supplied
  like any other. The rejected alternative is a synthetic sender the platform mints, which
  is what chapter 3.10 argued against and still argues against. A bot is DECLARED, not
  synthetic — the customer creates it, names it and describes it. That distinction is what
  T086d writes into 3.10's Trap.

T011 — the migration, measured rather than assumed

    users rows on this machine                                      134,067
    ADD COLUMN kind NOT NULL DEFAULT 'person', ADD COLUMN description  4.721 ms
    ADD CONSTRAINT users_kind_check                                   14.427 ms
    ADD CONSTRAINT users_bot_description_check                        13.972 ms
    (DROP of both columns, for the rolled-back measurement)           16.235 ms

  THE ANSWER SPLITS, AND THE TASK ASKED ONE QUESTION. "No backfill" is true of the
  column add — 4.7 ms against 134,067 rows is metadata-only, exactly as chapter 3.16
  measured for `last_activity_at`. It is NOT true of the two CHECK constraints: each
  validates every existing row and each took ~14 ms here. At this size that is nothing;
  the shape is O(n) and a customer with 10^8 users would notice the constraints and not
  the columns. Recorded because "the migration needs no backfill" is the sentence
  somebody will quote.

  Whole `pnpm migrate` wall clock was 3.39 s, of which almost all is `nest build`.

T013 — the compiler named 28, not 27, and the 28th is the one that mattered

    predicted (analysis pass 8)                                           27
    actual, first run                                                     28
    after narrowing the sender at the service                             27

  The eight test files matched the prediction EXACTLY: idempotency 11, repository.itest
  6, history-drift 3, history 2, channels 2, and one each in quotas, outbox, backfill.
  The 28th was `src/messages/messages.service.ts` — the only production caller.

  Pass 8 counted call sites that OMIT `userId`. The service does not omit it; it passes
  `string | undefined`, which `exactOptionalPropertyTypes` refuses just as firmly. So the
  counting method could not see the one call site the count was really about. Three
  numbers describe this file's send calls — 100 by naive grep, 46 HTTP sites in R1, 27
  omitting the property — and the true answer to "what breaks" was a fourth.

T013a — SC-003a's evidence

    pnpm typecheck  ->  0 errors, after 27 call sites and one service narrowing

T014a — TWO tests plant a senderless row, not one

  T014a named `repository.itest.ts`'s `last_message.user` arm. The compiler found a

  `repository.itest.ts:204` was a third surprise of the same family: the repository-level

  opposite. `createUser` cannot set `kind` (that is `upsertUser`, Phase 3), so the bot is
  promoted by a raw UPDATE.

PHASE BOUNDARY: TWO TASKS WERE MIS-PHASED, AND THE COMPILER SAID SO

  T012c and T012d test HTTP behaviour with a bot named in the send body.
  `sendMessageBodySchema` is a `strictObject` with no `user` field until T028, so at
  Phase 2 a key send cannot name anybody. Both moved to Phase 4 and annotated in place;
  the numbering stays where it is, because ids are stable labels (pass 11).

  The same boundary showed up inside `messages.service.ts`. T014's list of callers held
  only test files, so Phase 2 had no task for the production one — and Phase 2 cannot
  close with a red build. The service now narrows the sender and throws until T029 gives
  the refusal its code and field. Every key-authenticated send in the integration lane
  fails there until Phase 4, which is the boundary showing through rather than a
  regression.
