=============================================

*Every measurement this feature takes, and every thing that went wrong taking it.
Written as it happens, not at close-out.*

TASK LIST — WHAT THE CHECKER CAUGHT
------------------------------------------------------------

`check-refs.py`, carried forward from chapter 3.20 with `FOREIGN` reset, on its
first run against a finished `tasks.md`:

    27 problems — 26 tasks naming no file path, and a missing traceability.md

A quarter of the task list did not say where the work goes. Every one is an
integration test, and the reason they were vague is that the file they belong in
was an open question until R9's constraint was read properly.

R9 SAYS "NO TENTH INTEGRATION FILE" AND THAT IS NOT WHAT IT MEANS
    grep -c "spawn(" services/gateway/src/resume.itest.ts    0
    grep -c "spawn(" services/gateway/src/session.itest.ts   1

`resume.itest.ts` stubs the `ApiClient` and boots gateways in process — it spawns
no api at all. **The constraint that costs battery runs is the spawn count, not
the file count**: seven of nine files spawn an api and five of chapter 3.20's
seven failures across forty runs were a fixture failing to come up.

Typing writes nothing and reads nothing, so it needs no api either.
`typing.itest.ts` follows `resume.itest.ts`'s pattern and the spawn count stays
at seven.

THE PLAN'S PHASE ORDER WAS WRONG
------------------------------------------------------------

`plan.md` puts US1 (Mai sees Tuan typing) before US2 (the inbound seam). **US1
cannot be delivered without US2** — no frame lets a client say it is typing, so
the delivery path has no trigger. The stories keep their spec numbering and the
phases run US2 first.

Found while writing the task list rather than while executing it, which is the
cheap place to find it. Chapter 3.15/3.16 had five wrong premises and 3.17 had
five more; three of 3.17's surfaced only during implementation.

ANALYSIS PASS 1 — TWO CRITICALS, AND BOTH WERE UNASKED QUESTIONS
------------------------------------------------------------

Nine findings: 2 CRITICAL, 3 HIGH, 3 MEDIUM, 1 LOW. All eight above LOW fixed.

**C1 — THE CLAUSE THIS CHAPTER EXISTS TO CLOSE HAD NO TASK.**
FR-009 says the indicator expires with no frame sent to end it. Twenty-one
requirements, 108 tasks, and `grep -niE "expire" tasks.md` returned one line —
T064, about reconnect replay, which is FR-018.

It slipped because "the client holds the timer" reads like an answer, and an
answer feels like coverage. **The server's half is testable and was untested**:
FR-009a now asserts that no frame of any kind follows a signal, on the watcher's
whole frame list rather than on the absence of one type — a server that sends
nothing ever would satisfy the weaker version.

**C2 — THE PLANNED RATE LIMIT COULD NOT WORK, AND THE FIX MADE THE DESIGN
SMALLER.**
Research R5 said a third `"typing"` operation on the existing limiter needs "no
schema change and no new Redis shape". True of the grammar. Two more lines of the
same file:

    limits.ts:89   const WINDOW_MS = 60_000
    limits.ts:115  `rl:${environmentId}:${operation}:${windowStartFor(now, WINDOW_MS)}`

    scope    per tenant   vs  per connection — 10,000 users would share one budget
                              and one chatty user would silence the rest
    window   60 s         vs  2 s — "N per minute" cannot express "one per 2 s"
    subject  no channel   vs  per channel

Three mismatches, each fatal alone. **The replacement is a `Map` on the
connection** — no Redis, no third operation, `limits.ts` not edited.

**And the per-environment ceiling was dropped rather than kept alongside.** It
would bound a rate the debounce already bounds: the gateway enforces the interval
itself, so a hostile client cannot exceed it by trying. What stays unbounded is the
number of connections, and that is FR-RTM-09's cap — chapter 3.22.

**The design got smaller because a premise was checked, not because somebody
wanted a smaller design.** Constitution VII passed the third bucket as a small
addition; it was an addition that could not do the job.

ANALYSIS PASS 2 — TWO MORE CRITICALS, AND ONE OF THEM WAS INVISIBLE FROM HERE
------------------------------------------------------------

Pass 1 asked whether the tasks' premises held. Pass 2 asked two different
questions: **does pass 1's own fix hold up, and do the artifacts agree with each
other?** Five findings, all fixed.

**C3 — TWO TASKS IN ONE FILE ASSERTED OPPOSITE BEHAVIOURS.**

    T047  a second signal within the renewal window still delivers a frame
    T057  repeated signals inside the interval produce at most one publish

Both would have been written before anyone noticed. US1's scenario 2 was true
when there was no interval and became false when US3 added one; **pass 1 walked
past it while fixing the very requirement that contradicts it.** Pure document
drift, visible without opening a single source file.

**C4 — CHAPTER 3.20's TWO BRANCHES ARE INCOMPLETE AND NOTHING HERE COULD SEE IT.**

    session.ts:367   the `added` branch subscribes fanout, presence, membership
    session.ts:425   the revocation branch releases the same three

A fourth grammar makes both wrong. **A user added mid-connection would receive
messages and presence but no typing** — FR-004 silently false for exactly the case
chapter 3.20 built, and the obvious test (a member who was in the channel at
connect) passes against it.

**This is the finding that would have shipped.** Every artifact in this feature
was internally consistent; the defect lives in the interaction with the chapter
before it, and it is only visible by opening `session.ts` and noticing that the
previous chapter left two branches that enumerate subscriptions. Now FR-004a,
T043a, T043b and T048c.

**H4 — THE DEBOUNCE WAS ABOUT TO EDIT A TYPE FOUR CHAPTERS FENCE.**
T054 said "a `Map` on the connection". `Connection` lives in `registry.ts`, fenced
by chapters 3.7, 3.8, 3.11 and 3.19. A `Map` in `attachSessions`'s closure keyed
by connection id needs no fenced type and has a clearer lifetime. No task
mentioned `registry.ts` at all.

**M4** — nothing cleared a channel's debounce entry when a revocation dropped the
channel. Folded into T043b, which is the act that drops it.

**M5** — "renewal window" and "renewal interval" were one thing under two names,
in the file where C3's contradiction lived.

**AND A CLAUSE READ RATHER THAN ASSUMED, WHICH CONFIRMED PASS 1's FIX.**

    FR-RTL-01  "per-tenant rate limits on REST requests, message sends, and
                connection establishment"

Three operations, and typing is not one of them. So removing the typing bucket
does not merely avoid a mechanism that could not work — **it aligns with the
clause, and the third bucket would have added a counted operation the SRS does not
name.** The fix was more right than the argument given for it in pass 1.
