# Implementation Plan: Tutorial Chapter 3.1 — Tenants All the Way Down

**Branch**: `021-chapter-3-1` (no branch cut; work proceeds on `main` per the series' practice) | **Date**: 2026-08-04 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/021-chapter-3-1/spec.md`

## Summary

Write and publish tutorial chapter 3.1 in English, and advance the canonical
platform to the state the chapter documents: the organisation → application →
environment hierarchy, the human-identity and membership tables that sit above
the tenant boundary, and an OAuth signup that provisions all three atomically
from a single authentication (FR-TEN-01/02). The chapter pays chapter 2.1's
recorded debt — the stub `applications` table — and states plainly which
dev-mode seams remain and who retires them.

The technical approach comes from Phase 0: grow the repository layer's existing
admin surface rather than opening a second door onto tenant creation (R1);
keep platform humans and tenant end users in separate tables and record that as
ADR-18 (R2, R10); enforce FR-TEN-04's two-environment rule with a unique index
rather than a guard (R3); make signup idempotent through a unique constraint
rather than a read-then-write check (R5); implement the authorization-code flow
by hand with zod-validated provider responses (R6); and bind `state` to the
browser with a short-lived cookie, which is where the chapter's TRAP lives (R7).

## Technical Context

**Language/Version**: TypeScript 5.9 on Node 22.12+; the api service compiles
as CommonJS under NestJS 11 (ADR-15), the rest of the workspace is ESM.

**Primary Dependencies**: NestJS 11, Drizzle 0.45 (ADR-16), zod 4, pg 8. **No
new runtime dependency** — the OAuth exchange uses Node's built-in `fetch` and
a five-line cookie parse (R6, R7).

**Storage**: PostgreSQL via the compose stack; forward-only SQL migrations
generated by drizzle-kit and applied by the repo's own runner (`0002_tenancy.sql`).

**Testing**: vitest in two lanes — Docker-free unit tests, and `*.itest.ts`
integration tests against compose Postgres; plus the `@relay/e2e` journey lane
from 2.8, which must keep passing untouched.

**Target Platform**: Linux server (services), static site (tutorial).

**Project Type**: Documentation-first tutorial + the canonical monorepo it
teaches. The chapter is the deliverable; the code is its answer key.

**Performance Goals**: None specific to this chapter. Provisioning is a
once-per-signup write; the chapter makes no latency claim it does not measure.

**Constraints**: Unit lane stays Docker-free (2.1's gate); every persisted
operational record keeps a non-null tenant identifier (FR-TEN-06); no existing
Part 1/Part 2 suite may weaken; fences byte-match the tag with hunked-diff
amendments (docs/07 §2, convention adopted 2.7).

**Scale/Scope**: One published English chapter (2,000–4,000 canonical words,
2–4 figures), one migration, ~4 new tables, two HTTP routes, one ADR plus deep
dive, and the tests that hold seven invariants.

## Constitution Check

*GATE: evaluated before Phase 0 and re-evaluated after Phase 1 design.*

| Principle | Gate | Verdict |
|---|---|---|
| **I — Tenant isolation is a correctness property** | New tables sit *above* the environment boundary, so the repository's mandatory `environment_id` scoping cannot apply to them by construction. Does the design keep isolation designed-in rather than reviewed-in? | **PASS.** The admin surface stays the single home for tenant creation (R1); every table below the boundary keeps its non-null tenant column untouched; membership queries are scoped by organisation the way tenant queries are scoped by environment; and the chapter's tests attack the boundary with a second organisation's identifiers. The one shape that would have violated this — a nullable `environment_id` on the identity table — is explicitly rejected in R2 and becomes the chapter's TRAP. |
| **II — No acknowledged message is ever lost** | Untouched by this chapter. | **PASS** (no change to the write or delivery paths; Part 2 suites re-run to prove it). |
| **III — Two data paths, never crossed** | Untouched. | **PASS** (no analytical surface here). |
| **IV — Single writer, single source of truth** | Provisioning writes tenant containers. | **PASS.** It writes through the repository layer in one transaction (R4); no second component gains database access. |
| **V — API-first, developer-first** | Two new HTTP routes face humans, not developers. | **PASS**, with a stated limit: the chapter opens no management API, and says which chapter does (R9). Error shapes reuse 1.4's envelope. |
| **VI — Requirement-driven, test-verified** | Seven invariants: atomicity, idempotency, the environment cap, isolation between organisations, the CSRF binding, the provider-contract failure mode, and the admin surface staying out of request handlers. | **PASS.** Each has a named test and a requirement to cite (contracts §Invariants), and the constitution's 100% branch-coverage bar for isolation code is measured as its own task. |
| **VII — Boring by design — scope is a commitment** | The temptation here is to build a session, a console, and role management. | **PASS.** Zero new runtime dependencies; no session (R9); roles created but not managed; deletion deferred — each named with its owning chapter rather than silently skipped. |

**Post-Phase-1 re-evaluation**: unchanged. The design added one ADR (R10) and
no dependencies; the data model introduced no nullable tenant column; contracts
expose two unauthenticated routes and nothing else.

## Phase 2 preview — how tasks will be shaped

`/speckit-tasks` will sequence roughly: schema + migration **together with the
`createEnvironment` amendment they break** → prove Part 2 still passes → tests
per invariant, written first → provisioning in the admin surface → OAuth module
→ walk script → capture real output → write the chapter against captured output
→ ADR-18 + deep dive → publish English + manifest → run every gate, plus a
traceability check and a coverage check. Chapter prose is written
**after** the code runs, because the series' chapters quote measured output, and
several of the last four chapters changed their claims once the code was real.
