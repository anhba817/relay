T044-2  **THE VIEW'S EXPRESSION WAS WRONG AND A TEST IS WHAT SAID SO.**
      `sumMap(map(kind, toUInt64(if(event = 'reserved', 1, 0))))` gives EVERY event's kind
      a key and non-uploads a value of zero. Measured on a day holding one image
      reservation, one audio REJECTION and one image rendition:

        the first version    {'audio':0,'image':1}
        `sumMapIf`           {'image':1}
        no matching row      {}

      An `audio` key in a column called `uploads_by_kind`, on a day nobody uploaded any
      audio. The damage is to the KEY SET, not the values: it stops meaning *"the kinds
      this tenant uploaded"* and starts meaning *"the kinds that had any media event"*,
      and a caller iterating the map reports a kind belonging to a different question.
      `dailyUsage`'s own rule one level down — *"a day with no activity is a missing row,
      never a row of zeros."*

      **AND THE ZEROS WERE STABLE, WHICH IS THE KIND THAT SURVIVES.** `SummingMergeTree`
      drops a row whose summed columns are all zero and does **not** drop a zero-valued
      key inside a map: `{'audio':0,'image':1,'video':0}` before `OPTIMIZE … FINAL` and
      the same after. So this was not a 4.9-style moment-versus-state artefact that a
      merge would have cleaned up.

      `0018` IS AMENDED IN PLACE RATHER THAN FIXED BY AN `0019`. The migration is this
      chapter's own and has shipped nowhere; a `0019` that repairs `0018` publishes a
      mistake as history, which is the argument 4.13 made when it rewrote the MinIO image
      in all 25 commits. **A lane that already applied the old file must drop the view and
      delete its ledger row** — the checksum refusal is doing its job, and the two
