    13 tests, 31 files and 287 tests in the api's unit lane, all green
    lint GREEN · typecheck GREEN · test GREEN

  The verdict is decided from PRESENCE before any arithmetic, so only a comparison with both
  sides present reaches a division.

T014 — `0 / 0` WAS NOT IN THE DESIGN, AND IT IS REACHABLE
  `data-model.md` gave the formula `abs(a - o) / max(a, o)` and the verdict ordering, and
  never said what two present zeroes mean. They are reachable: `usage_periods` holds 288 rows
  for 2026-08 with `messages_sent = 0`, and a rollup row can hold 0 for the same quantity.
  **They agree** — the guard returns 0 rather than NaN, and a test drives it.

T018 — AND THE `max(a, o)` DENOMINATOR MAKES THE THRESHOLD ASYMMETRIC
  The first boundary test asserted 100,000 against 100,100 as *"exactly 0.1%"* — the
  arithmetic anybody does in their head, 0.1% of 100,000 being 100. **It measures 0.0999%**,
  because the divisor is the larger side:

      100 / 100,100 = 0.000999000999…      just INSIDE the bound
      100 / 100,000 = 0.001                exactly ON it

  So a 0.1% shortfall and a 0.1% excess are different absolute amounts, and **a drift computed
  off the smaller side lands inside the threshold and does not fire**. That is the mistake
  phase 4's planted drift will make if nobody says so, which is why the test asserts both the
  correct pair (99,900 / 100,000) and the trap.

  Neither of these was visible in the design; both came from running the arithmetic.

T028-T030 — THE SUITE, AND A FACT 4.6 USED TO DELETE A BRANCH
  Two of seven failed on the first run, both the same cause:

    expected 'breach' to be 'no-data'
    expected +0 to be null

  **A bare aggregate with no GROUP BY always returns exactly one row.** Chapter 4.6 asked the
  server that question and used the answer to delete an unreachable guard; here the same fact
  means an **empty result set is not reachable**, so a tenant with no rollup rows came back as
  `0` rather than as nothing — and "holds nothing" and "holds zero" became the same answer, in
  a report whose whole point is that they are not.

  The fix is `count()` as the first column of both reads, and the count decides absence rather
  than the sum. **7 passed (7)** after it.

T032/T033 — THE QUANTITY WAS CHOSEN BY WHAT THE REPOSITORY CAN PLANT
  `usage_periods.messages_sent` is incremented ONE AT A TIME by `sendMessage`, inside the
  transaction that writes the message, so an operational total of 100,000 messages costs
  100,000 sends. `creditConnectionMinutes` takes the number as an argument — the gateway
  reports a TOTAL rather than a tick — so the same figure costs one call.

  That is why the planted drift is in connection-minutes, and it is also why this suite needs
  no driver exemption: nothing here is a raw `INSERT`, so `reconcile.itest.ts` stays off
  `eslint.config.mjs`'s list where `period.itest.ts`, `quotas.itest.ts` and
  `connections.itest.ts` all sit.

    planted   operational 100,000  ·  analytical 99,000        1.0000%   breach
    removed   operational 100,000  ·  analytical 100,000       0.0000%   pass

  AND THE OTHER THREE QUANTITIES DO NOT RAISE IN THE SAME REPORT, which is the half that makes
  the first one mean anything: `messages` and `activeUsers` are two present zeroes — agreement
  — and `storedMessages` is `not-comparable`.

T034 — THE BOUNDARY, AND **BOTH OBVIOUS PLANTINGS PASS**
  Against an operational 100,000, measured:

    analytical    difference       pct      verdict
        99,900          -100   0.100000%    pass      "0.1% under" — the naive shortfall
        99,899          -101   0.101000%    breach
       100,100          +100   0.099900%    pass      "0.1% over"  — the naive excess
       100,101          +101   0.100898%    breach

  Phase 2 predicted the excess half from arithmetic alone; the shortfall half is the same trap
  from the other side, and it is the comparison being `<=` that makes it one. **Anyone planting
  `operational * 1.001` to make the job fire gets a pass and concludes the job is broken, and
  `operational * 0.999` does it too.** The smallest breaching drift is 101 in BOTH directions —
  the asymmetry is in the percentage, not in the absolute, and only because `max(a, o)` is the
  denominator.

  A FALSIFICATION PROBE, BOTH HALVES. Changing `pct <= threshold` to `pct < threshold` turned
  exactly one test red — `analytical 99900 … expected 'breach' to be 'pass'` — and nothing
  else. The boundary cases sit ON the bound rather than near it.

T035 — THE CLEANUP IS ASSERTED, NOT POLLED
  4.6's suite read three creations where it had planted two, because `ALTER TABLE … DELETE` is
  a queued mutation; its repair was to poll `system.mutations`. This suite keeps the poll and
  then **reads `count()` for the tenant and asserts 0** — checking the outcome instead of the
  queue.

  AND ONLY ONE SIDE IS DELETED, WHICH IS DELIBERATE. The analytical rows must go: the target is
  a `SummingMergeTree` and the read is `sum()`, so a second plant on the same day ADDS to the
  first. The operational rows stay — `reset-lane.mjs` purges lane debris and not data by design
  (Postgres held 31,215 environments at 045's close-out), they belong to an environment id
  nothing else in the lane can name, and deleting them would mean a raw `DELETE` in the one
  file that currently needs no exemption.

T036 — THE LINE THAT DECIDES WHETHER THE ALERT FIRES LIVED IN A FILE NOTHING TESTS
  `scripts/reconcile-usage.mjs` closed with `process.exit(breached.length > 0 ? 1 : 0)`. One
  expression, no test, and the whole of FR-008's observable behaviour. It is `exitCodeFor` in
  `metering/reconcile.ts` now, with four unit tests, and the script calls it.

  Run against a real environment, both halves, through the script:

    analytical 99,000 vs operational 100,000   connectionMinutes  1.0000%  breach   exit=1
    analytical 100,000 vs operational 100,000  connectionMinutes  0.0000%  pass     exit=0

T037 — WHAT "RAISES AN ALERT" CANNOT MEAN HERE
  There is no alerting integration in these three repositories. What exists is **two** mail
  paths — `quotas/quota-email.ts` for a quota crossing and `notifications/notification-relay.ts`
  for a disabled webhook endpoint — and they share one transport, `notifications/mailer.ts`,
  whose default is `smtp://localhost:1025`: **Mailpit, the catcher `compose.yaml` runs for the
  lane.** So the platform's existing notion of "alert" is an email to a development mail
  catcher, addressed to organisation members, and its own failure mode is already in the lane
  as `quotas.unaddressable` / `notifications.unaddressable` — *no member has an email address*.

  A notification with no recipient is not an alert, and neither is an exit code. What a real
  one costs, named rather than hand-waved: a delivery target that is not a person's inbox
  (a pager or a webhook), a deduplication key so a daily job breaching for thirty days sends
  one alert rather than thirty, and a severity that distinguishes 0.2% from 100% — none of
  which this platform has anywhere.

  CAUSE TWO, AND IT IS NEW: **the rollup and its source have disjoint tenant sets.** The

T044 — THE TTL BOUNDARY IS A FUNCTION OF THE CLOCK, AND THE MODEL PREDICTS 047's NUMBER
  A probe table with `TTL toDateTime(ts) + INTERVAL 90 DAY`, 92,000 rows, 1,000 per calendar
  day, midnight-aligned, oldest = today − 91.

    straight after the insert     0 deleted · 92 days present
    after OPTIMIZE ... FINAL  1,053 deleted · 2026-06-17 gone whole (1,000)
                                             2026-06-18 short by 53 of 1,000

  **THE TTL IS A SCHEDULE, NOT AN EVENT** — 047's finding, reproduced as the control: every
  expired row was still there until a merge was forced.

  AND THE 53 ARE EXACTLY THE ROWS BEFORE THE WALL CLOCK. The server's clock at the cut read
  **01:16:07**; the rows are 86 seconds apart, and 53 x 86 s = 4,558 s = 1 h 16 m. So a rollup
  computed before the cut carries 1,000 for that day where the source holds 947 — **53 / 90,947
  = 0.0583%** — and that percentage climbs through the day to a ceiling of one whole day's share
  of the window, **1,000 / 91,000 = 1.0989%**, then resets at midnight.

  047 published 0.49% as *the* figure. It is one point on this curve: 4,941 of a day's ~11,000
  rows is 45% of a day, which is a run at about 10:48. **The obstacle is not "0.49%" — it is a
  discrepancy that is zero at midnight and 1.1% just before it, on the same data.**
