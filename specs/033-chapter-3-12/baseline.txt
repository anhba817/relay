right and each covered less — or more — than intended. Filtering at capture time
destroys the evidence; filtering at read time keeps it. That is the rule the fence
checker, the guard and the lint rule all embody, applied to a shell pipeline.

## T023-T031b — the four shapes, the control, and the two routes that name an environment

`attack.ts` is four functions, one per shape, and each returns the pair rather
than a boolean: `readAttack`, `listAttack`, `writeAttack`, `credentialAttack`.
`writeAttack` also reads the victim's state before and after, because a write
that leaks nothing and changes something is still a breach.

`gauntlet.itest.ts` — **19 tests**, in four groups:

  the control                3      read 2, list 1, write 7, credential 1  = 11
  internal user token        3      platform routes (T031)                 = 2
                                                                     TOTAL 19

**The control is the finding of this block.** Fourteen tests passed the first time
the file ran, and that number was not evidence of anything. Every assertion in the
suite compares two refusals for sameness — so an expired credential, a lane
missing a variable, or a route that answers 401 to everything produces two
identical refusals and passes the whole file while attacking nothing at all. The
suite now proves its own premise first: the attacker's credential reaches the
attacker's own webhook endpoint (200), its own channel history containing its own
message (200, and the id is in the body), and writes to its own channel (201).
Green means something only with those three above it.

Two attempts to check this from outside the suite failed and are worth recording,
because both failures were about the harness and not the platform. A scratch
script could not resolve `reflect-metadata` outside the workspace; run under
`tsx` inside it, `AppModule` threw `UndefinedDependencyException`, because tsx
emits no decorator metadata — which is exactly why the vitest configs use the SWC
plugin. A permanent test in the suite was the cheaper answer as well as the
better one.

T031, T031b — the platform routes, where isolation means something different.
Only **two of the five** name an environment alongside an identifier:
`dispatch/expand` (`environment_id` beside `event_id`) and `usage/connections`
(an environment per connection). Those two can be told to act on environment A
while carrying something from B, and both are attacked — expand here, connections
by `usage.itest.ts`'s `connection_environment_conflict` assertion.

The other three — `material`, `outcome`, `replay` — take one opaque identifier
and derive the environment from the row they find. There is no cross-environment
request to make, because the caller never says which environment it means. That
is not a hole the suite declines to test; it is the absence of the parameter that
would make the attack expressible. What guards them is FR-044 and nothing else,
which is why `material` — the one response in the platform that returns a
decrypted customer secret — is the route to watch first if a platform credential
ever leaks.

Expand's two assertions, and the first is what makes the second mean anything:
naming the attacker's environment creates deliveries (`created > 0`, its own
endpoint subscribes to `message.created`) and leaves the victim's delivery count
unchanged; naming an environment that exists nowhere creates zero and also leaves
it unchanged. Without the first, "the victim's count did not move" is what a
no-op looks like.

## T037-T043 — every table's tenant path, and the two things writing it found

`db/catalogue.ts` classifies from `information_schema`, not from `schema.ts`: a
table a migration added and nobody modelled in Drizzle is invisible to a check
that reads the model, and that is the table this exists to catch. It lives in
`db/` because that is the only directory the lint ban permits `drizzle-orm` in,
and T069a is about to restore that ban for integration tests (R23).

    tenant paths: 22 base tables — 12 direct, 2 hop, 8 spine
    hop: members  → channels, users
    hop: messages → channels, users

12 direct includes `__sentinel_environments`, which the harness creates — 11 on a
database the lane has never run against, which is why T038 records these and
asserts totality instead.

**The `hop` rule in data-model.md was wrong, and writing the query is what showed
it.** It said "exactly one foreign key reaches a table that has it". Both hop
tables reach **two** — `channels` and `users` are each `direct` — so the uniqueness
reading would have classified neither and failed totality on the two tables it
was written to describe. The rule is existence. Corrected in data-model.md §4.

**`::text` is load-bearing, and the failure was legible only by accident.**
`information_schema` columns are `sql_identifier`; node-pg has no parser for an
array of them, so `array_agg(DISTINCT ccu.table_name)` arrives as the literal
string `{channels,users}`. Iterating it yields `{`, and the assertion read
`members hops through {, which is not direct` — which named the bug precisely
because the message interpolates the value. A boolean assertion would have said
`false is not true`.

One self-inflicted stop worth recording: the comment explaining that cast, written
inside the SQL, used backticks around `information_schema` — inside a template
literal, which ended the string. `tsc` was not re-run after that edit, so it
surfaced as a vite parse error during the test run instead. Typecheck after every
edit, not after every batch.

## T044-T051 — the socket surface, 19 attacks and one lost handshake

`services/gateway/src/isolation.itest.ts` — gateway in process, api as a child,
the arrangement chapter 3.2 established. **19 tests**:

  control                       2     the four verbs (T045-T048)      4
  the union, classified         4     a client uttering each of the
                                      nine outbound frames            9

**T045 named a field that does not exist**, and the code said so before the test
did. The task said "`channel_ids` contains nothing belonging to B" of the
`connection.ack`; the ack carries `user`, `cursor`, `resume_ok` and `truncated`
and nothing else. `channel_ids` is the api's `/internal/session` response
(`session.controller.ts:103`), which the gateway reads at connect
(`auth.ts:81`) and turns into the subscription set — so that IS where a leak
would start, and the assertion moved there. Task corrected.

**The direction of a frame cannot be derived, but the member list can**, and the
split matters. `frameSchema.options` yields all ten discriminator values at
runtime, so a frame added to the union shows up here with no edit and fails
totality until somebody classifies it — the property `targets.itest.ts` gives the
route list. The DIRECTION has no metadata anywhere in the union: no inbound/
outbound split, no client/server marker. An earlier draft of T049 and of
`contracts/gauntlet.md` §4 both said "derive the inbound ones", which is not
implementable.

The classification is **1 inbound, 9 outbound**, and `session.ts:552` is the
authority rather than taste — it compares against the single literal
`message.send` and answers everything else with `unknown_frame_type` and close
4002. The suite checks the classification against that behaviour frame by frame,
so a second inbound entry would fail rather than sit in a list being wrong.

**The lost handshake, which cost twelve failing tests.** Await `open`, then attach
a `message` listener, then read: `connection.ack` is sent the instant the upgrade
completes, awaiting `open` yields to the event loop first, and the frame arrives
with no listener attached and is gone. Every test that waited for a SECOND frame
timed out at exactly 5000ms — twelve of nineteen, all with the same symptom and
none of it about tenancy. The fix is to collect from the moment the socket exists
and let `waitFor` read the buffer before it waits, which is also what made the
timeout message useful: it now names the frames that did arrive.

One preventive edit, from the fixed-port lesson this lane already learned twice:
the file starts TWO api children, and two draws from one 200-port range collide
about once in two hundred runs. The second child takes the neighbouring port
rather than another draw.

## T064-T068 — three reintroductions, and the first one did not fire

**T064, take one: the gauntlet stayed green, 21 passed.** `environment_id` dropped
from `listMessages`' `scoped()` helper — a repository SELECT on the history read
path — and every assertion passed.

The reason is layering, and it is worth more than the reintroduction was.
`GET /v1/channels/:channelId/messages` calls `channelExists(channelId)` first
(chapter 2.8's fix for the two doors disagreeing), and that read IS scoped. A
foreign id is refused there and `listMessages` is never reached. **The suite is
sensitive to the OUTERMOST scoping check on a path and blind to an inner one that
a live outer check masks.** Nothing in the suite says otherwise, and nothing in
the plan had noticed.

**T066: breaking indistinguishability takes an unscoped read, and that is the
finding.** The task said "change one endpoint's 404 to a 403". Doing that at the
route level moves BOTH halves of the pair to 403 and the oracle cannot see it —
the pair compares foreign against absent, so a change that treats them alike is
invisible by construction. To make them differ, the code has to learn something
the tenant scope hides. So the reintroduction is the realistic version: an
unscoped `anyEndpointExists(id)` and a "helpful" 403.

    × read: a foreign resource answers as an absent one > GET /v1/webhooks/:id

**WHAT THIS MEASURES, AND WHAT IT DOES NOT.** Three faults chosen by the author of
the suite that catches them measure sensitivity to three faults. They are not
coverage of the class, and the first attempt is the proof of that: it was chosen
as an obvious leak, and it was not one, for a reason nobody had written down.

What the three do establish, precisely:

  - a dropped scope on the outermost read of a path is caught, by the pair
  - a dropped scope on a write is caught by the STATE comparison alone, with the
    responses still identical
  - a leak of existence is caught by the pair, and requires an unscoped read to
    create

## T107a — what twenty green runs establishes, and what it does not

The chapter states the range of every other defence it builds. This is the one
defence that had no range written down, and the counterexample was four commits
back in this repository.

**The arithmetic.** Twenty consecutive green runs reject, at 95% confidence, only
a per-run failure probability of **13.91% or worse** — `(1−p)²⁰ ≤ 0.05` solves at
`p ≥ 0.1391`. Everything gentler survives, often comfortably:

    per-run failure rate    probability it survives 20 green runs
             1%                          81.8%
             2%                          66.8%
             5%                          35.8%
            10%                          12.2%
          13.9%                           5.0%
            20%                           1.2%

So a flake that fails one run in twenty — the kind that ruins an afternoon once a
month — passes this battery **more than a third of the time**. Rejecting a 5%
flake at the same confidence would take **59 runs**; a 1% flake, **299**. At
roughly 195 seconds a run, that is 3.2 hours and 16.2 hours.

**AND THE COUNTEREXAMPLE IS NOT HYPOTHETICAL.** Chapter 3.11 ran twenty green and
an eleven-chapter-old flake surfaced on **run twenty-one**. Its own battery is the
evidence that twenty is a floor rather than a proof — recorded in this repository's
git history, at `part3-ch11`.

**What twenty runs does buy**, and it is worth having: it catches the defect class
that fails often. Chapter 3.11's battery found a timeout-shaped fault on run one —
six Mailpit tests waiting through a 10-second helper inside a 5-second budget —
and chapter 3.12 found three of its own on the first attempt. Those are not rare
events; they are near-certainties that a single run happens to miss because of
ordering or a warm cache.

**What it does not buy**, stated so nobody reads a green battery as a guarantee:

- a flake below about 14% per run is not excluded by it;
- a defect that needs a specific interleaving of two suites is not excluded, since
  the lane runs one package at a time and the ordering within a package is stable;
- a defect that needs a cold cache, a slower machine or a different CPU count is
  not excluded, because twenty runs on one machine vary in almost nothing;
- and nothing about correctness is excluded — twenty green runs of a suite that
  asserts the wrong thing is twenty green runs.

**The budget a run may not exceed**, stated because a mean that moves is a defect:
**240 seconds**. The lane measured 191.72 s at chapter 3.11's close and 192–195 s
through this chapter with thirty-odd suites added, so 240 leaves room for a slower
machine and none for a timeout-shaped fault. A run over the budget is investigated
rather than averaged.
