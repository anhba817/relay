`@relay/test-harness:test:integration`, with

  Serialized Error: { errno: -111, code: 'ECONNREFUSED', address: '127.0.0.1', port: 15432 }

The compose stack had exited nine hours earlier. Bringing it back up failed too:

  Error response from daemon: ... endpoint relay-postgres-1 ...
  listen tcp4 0.0.0.0:5432: bind: address already in use

**`compose.yaml` defaults Postgres to 5432 and the code defaults to 15432.**
Line 22 is `"${RELAY_POSTGRES_PORT:-5432}:5432"`; `packages/test-harness/src/db-url.ts`
and `services/api/src/db/client.ts` both default to **15432**. So the stack has to
be started as

  RELAY_POSTGRES_PORT=15432 docker compose up -d --wait

or Postgres alone fails to bind while the other four containers come up healthy —
which is the confusing shape, because `docker compose ps` then shows four of five
fine. An unrelated `facet-pg` container sits on 55432 and is not the collision;
this machine's own Postgres holds 5432.

Recorded because it cost four wasted lane invocations, and because the README
documents `docker compose up -d --wait` without the variable.

## T004 — three runs, and every failure

Three consecutive runs, all green, four packages captured per run:

  run 1   8 / 268 / 28 / 16     195s
  run 2   8 / 268 / 28 / 16     193s
  run 3   8 / 268 / 28 / 16     193s

A 2-second spread against 3.11's recorded 193.30s mean. Nothing intermittent
surfaced, which is what T004 exists to establish and is not the same as proving the
lane cannot flake — SC-019 and T107a carry that argument, and 3.11's own battery
went twenty green before a flake appeared on run twenty-one.

**Four mistakes of mine cost about twenty minutes here, and they are one mistake.**
Each was a check whose range I had not verified before trusting it:

  1. a background command with a relative `cd` that did not exist from the cwd it
     inherited — the site baseline "failed" and the failure was mine
  2. a capture filter, `^@relay/[a-z-]+:test:integration:`, that silently excluded
     `@relay/e2e` because the character class has no digits, and could not match
     `ELIFECYCLE` at all. So the three-run record above is four packages, not five,
     and could not have shown a package-level abort. The fifth number comes from a
     fourth run captured whole and filtered at read time
  3. a gate, `until ! pgrep -f "vitest"`, whose own command line contains the word
     it greps for, so it matched itself and never exited
  4. a `pkill` meant for that gate, which took down two lane runs including one
     started in the same command

The class is the chapter's own subject: a filter, a gate and a pattern each looked
right and each covered less — or more — than intended. Filtering at capture time
destroys the evidence; filtering at read time keeps it. That is the rule the fence
checker, the guard and the lint rule all embody, applied to a shell pipeline.

**What they are, sampled rather than assumed**, because "25 arms" says nothing about
whether the clause can close:

  151   if (!environment) {                                    a precondition guard
  255   return row ?? null;                                    the `??` default arm
  1710  if (result.disabled) disabled++;                       a counting branch
  2240  value instanceof Date ? value.toISOString() : String(value)   a ternary's other side
  2894  if (organisationId) {                                  a nullable-column path
  3139  if (!row) {                                            a not-found guard

So the 25 split into two kinds. Some — 1710, 2894, 2240 — are ordinary paths a test
can reach. Others — 151, 3139, and most of the `??` arms — are guards whose false
branch means a caller violated a precondition the types nearly forbid, and closing
them means constructing a state the repository layer exists to make unconstructable.
FR-040 asks for the number and the names; whether 100% is reachable is a question
this list makes answerable rather than one it answers.
