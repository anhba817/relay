THE ONE THAT MATTERED: EVERY MEMBERSHIP EVENT WOULD HAVE BEEN DESTROYED
------------------------------------------------------------

`services/api/src/outbox/event.ts:167` — the schema the **consumer** parses with:

    export const outboxEventSchema = z.strictObject({
      id: ..., type: z.literal("message.created"), ...
    });

A `channel.member_added` payload fails that parse. `consumer/runtime.ts:163` answers a
failed parse with `message.term()` — **redelivery stopped for good** — and logs
`consumer.unparseable`, under a comment that says "nothing catches what lands here". So
every membership event reaching the spine would have been silently destroyed at the
consumer, in production, with the row correctly written and the relay correctly
publishing it.

**Three things hid it.**

1. **The lane runs `RELAY_EVENT_CONSUMER=off`.** The api suite went green through 505
   tests with the defect in place.
2. **Analysis cleared it by reading the wrong file.** Pass 1 checked
   `packages/protocol/src/internal.ts:276`, whose `type` is `z.string().min(1)`, and
   reported the hazard closed. There are two envelope schemas and a grep finds the
   permissive one first.
3. **It is invisible to every gate this repository has.** Not a typecheck failure — the
   producer and the consumer never meet in one type. Not a lint failure. Not a lane
   failure. The only thing that finds it is handing a produced event to the consuming
   schema, which is what T027 said to do in the words *"run the consumer against one
   membership event rather than reasoning about it."*

The fix is a `z.discriminatedUnion("type", …)` over the same three names, so a fourth
type added to `OUTBOX_EVENT_TYPES` without a branch below is now a typecheck failure
rather than a terminated message. Three tests carry it: every producible type parses,
what `membershipEvent` builds round-trips, and an unknown type or a mismatched `data`
is still refused — the union widened without becoming permissive.

T054a — NO TASK OWNED THE OPEN PATH'S SUBSCRIPTION
T054 covers the release on a revocation and T079 covers the user's own subject at

T061 — THE ORDERING ASSERTION WAS UNFALSIFIABLE, AND THE PROOF SAID SO
This is the phase's most expensive finding and it cost nothing but the discipline
of running T065 as written.

T061 asked for the frames in arrival order, asserting `membership.changed`
precedes the last `message.created`, on the stated grounds that "both orders end
with the notice delivered and the channel quiet; only arrival order separates
send-then-cut from cut-then-send". T065 then asks for the proof: remove the
send-before-delete and watch it fail.

It did not fail. The implementation was edited to cut first —
`connection.channelIds.delete()` moved above `send()` — and all 22 tests stayed
green. **Swapping those two statements changes nothing any client can observe**,
because the notice goes to a socket reference the function already holds, and the
cut only affects future fabric routing.

What FR-008 actually forbids is one line further out. `registry.subscribersOf()`
is how the removed user is found; deriving the audience AFTER the mutation
removes them from their own notice's audience — revoked and never told. That
implementation was built too:

    audience-after-cut  ->  "tells the removed user…" FAILED in 5 s, no notice

So the requirement's content is audience-then-mutate, the first test in the file
carries it, and the ordering test was rewritten to assert that directly. **Two
implementations were run to find out which line the requirement was about.**
Reading the code would have suggested both were fine.

T056 — THE FR-029 TEST PASSED WITH THE THING IT TESTS DELETED
Twice, for two different reasons, and neither was visible from the assertion.

**First: the cursor and the frame had the same sequence.** The test presented
`channel:1` and then buffered that channel's FIRST message, whose seq is also 1.
`flushable(buffer, marks)` filters `frame.seq > marks[channel]`, so the frame was
dropped as at-or-below the mark. Green with the FR-029 filter deleted — a test
about the resume, under a title about revocation. The buffered frame has to sit
ABOVE the cursor or nothing in the test is about membership.

**Second: the connection was not buffering.** A connection is `buffering` from
the upgrade until `api.backfill` returns, which on this lane is one local HTTP
round trip — about twenty milliseconds. The removal always landed after the flush,
so the delivery under assertion was ordinary live delivery of a message posted
while the user was still a member, which is correct behaviour.

Slowing the FABRIC does not widen the window: `withDeadline(subscribing,
resumeDeadlineMs)` failing calls `degrade()`, and `degrade()` empties the buffer
itself. The seam that works is the `ApiClient`, which `attachSessions` already
takes as a parameter — a decorator whose `backfill` sleeps 2,000 ms first. The
code path under test is the real one; only the clock moved.

With both fixed, deleting the filter turns the test red in 3.7 s.

TWO TEARDOWNS IN THE WRONG ORDER, AND NEITHER FAILURE NAMED ITSELF
`server.close()` does not resolve while a connection is open, and vitest runs
`afterEach` hooks in REVERSE registration order — so a describe-level teardown
closing instances runs BEFORE the file-level one that closes sockets.

    7 tests, 83 s, all reporting `Hook timed out in 10000ms` at a teardown

The same trap then appeared inside a single test's `finally`, which closed its
instance before its socket: one 20 s timeout, reported as a test timeout. Fixed
by sharing instances per describe (fresh USERS and CHANNELS per test is the
isolation this file needs, and `seed()` gives that for a few inserts) and by
closing the socket before the server.

THE SENDER MUST BE A BOT, AND A BOT MUST HAVE A DESCRIPTION
`postMessage` named a seeded person and got 403 `sender_not_permitted`: "an
application credential may send only as a bot user". `createUser` cannot make one
— chapter 3.17 refused that deliberately — so the sender goes through
`upsertUser({ kind: "bot" })`. That then hit `users_bot_description_check`, a
database CHECK rather than a validator: `kind <> 'bot' OR description IS NOT
NULL`. Its own comment is the rule — "a description is what turns an opaque
sender into an answerable one, so a bot without one is not a bot" — and it
refuses a seed as readily as a route.

PHASE 6 — THE ADDITION
============================================================

T080/T086 — THE SECOND ORDERING REQUIREMENT WHOSE FAILURE MODE DOES NOT EXIST
T080 asked for subscribe, then insert into `channelIds`, then send, because the
reverse "opens a window where `registry.subscribersOf` returns a connection for a
channel this instance is not yet receiving — a silently lost message rather than
an error". T086 asked for the proof: swap the two lines, watch a test fail.

All 36 tests stayed green. So the window was widened to 1.5 s with a delayed
`fanout.subscribe` and a message published inside it, under both orders:

    subscribe-then-insert   [["presence.changed",null],["membership.changed","added"]]
    insert-then-subscribe   [["presence.changed",null],["membership.changed","added"]]

Byte-identical. `subscribersOf` returning the connection changes nothing while
the INSTANCE is not subscribed: the frame never reaches this process, so there is
no delivery for the registry to be consulted about. **Both orders lose the
message**, which makes the ordering unobservable rather than merely hard to test.

**This is the second time in this feature** — T061 was the first, and the shape
is identical: a task named two adjacent statements, asserted that their order was
the requirement, and the requirement turned out to live somewhere else. Both were
found by running the proof the task itself asked for, and neither would have been
found by reading. The generalisation worth keeping: **a task that says "the
ordering is the requirement" is making a claim about an observable difference,
and that claim needs its own falsification before the test is written, not
after.**

The shipped order is subscribe-then-insert regardless. It cannot produce a
connection claiming a subscription it does not hold, which is worth having for
whoever reads the code next even though no test can see it.

THE REAL WINDOW IS A GAP, AND IT IS NOW A TEST
A message published between the add committing and the gateway's subscribe
landing reaches the new member through history and not through the socket. The
test asserts the loss rather than the ordering, so a future change that closes
the gap turns it red and has to say so. `gaps.md` item 5.

THE ADDITION'S AUDIENCE IS A DIFFERENT LOOKUP, AND THE FIRST VERSION USED ONE
`deliverMembership` found its audience with `registry.subscribersOf(channel)` for
both directions. That is right for a removal — the removed user is still in
`channelIds` at that instant, which is why one publish reaches both audiences —
and **wrong for an addition**, where the new member is not in the channel yet.
`subscribersOf` returns every member except the one the frame is about, so the
person being added is the only one not told. Additions now also walk
`connectionsFor(user)`, which is the reason a principal-addressed subject has to
exist at all.

Caught by T081 failing on the first run rather than by reading, which is worth
noting: R1 states the asymmetry in the research document, this file's own module
comment restates it, and the audience lookup was still written once for both.

PHASE 7 — THE BAN
============================================================

T089 — THE CONTRACT'S OPEN QUESTION HAD A THIRD ANSWER
`contracts/membership-fabric.md` offered two: `channel: "*"` on the fabric (one
schema, one parse, one code path) or a separate payload shape (no sentinel, two
of everything). **Both leak the sentinel to somebody** — the first to a log
reader and, worse, to a client, because the wire frame's `channel` is
`z.string().min(1)` and a client would receive a channel id of `"*"`.

The answer taken keeps `"*"` on the fabric and **expands it in the gateway**, one
wire frame per channel that connection holds. A client sees what N individual
removals would have produced. `change` stays `removed`; the enum needs no third
member and `frames.ts` is not edited.

The api cannot do this expansion: it knows which channels the ban revoked, not
which of them a given connection on a given instance holds — and that per-
connection set is what a client's frames have to match.

    for (const channelId of [...connection.channelIds])

**The copy is load-bearing.** The recursion deletes from `channelIds`, and
iterating a Set while deleting from it skips entries — a ban that revoked every
other channel. Written as a copy from the start because the deletion is two
frames away in the same function, but it is the kind of thing that reads as
defensive until it isn't.

T041 asked for one shared window and T092 repeated it — *"if the fixtures allow,
set the ban up inside that wait rather than opening a third"* — and the ban test

THE UNBAN PUBLISHES NOTHING, AND ONE EDGE READS AS "NO CHANGE" WITHOUT BEING ONE
`banUser` returns `[]` both for a repeated ban — `isNull(users.banned_at)` makes

is lost: a connection with no channels receives nothing whether or not it is
told, and distinguishing the two would mean widening the repository's return for

T097 — THE INTERVAL, AND ITS ARITHMETIC
    DEFAULT_REREAD_INTERVAL_MS = 60_000

NFR-SCL-01 budgets 10,000 connections per instance, and the re-read is per
connection because the api answers for the token that connection presented:

    60 s   10,000 / 60   =   167 requests per second per instance
     5 s   10,000 / 5    = 2,000 requests per second per instance

Two thousand a second for a backstop is not a backstop, it is a poll — and the
mechanism it backs up already meets FR-RTM-10 in 34-88 ms. Sixty seconds bounds
the damage of a DROPPED publish, which is a rarer event with a different budget;
reading the two as one number is how a backstop turns into a poll.

Every test injects a short interval (200-300 ms) the way chapter 3.19's tests
inject a hundred-millisecond grace. Waiting out sixty seconds once would be a
quarter of the whole lane's budget.
