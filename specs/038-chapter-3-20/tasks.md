## Dependencies and execution order

    Phase 1 ──> Phase 2 ──> Phase 3 ──> Phase 4 (US1) ──> Phase 5 (US2)
                                              │                 │
                                              └──> Phase 6 (US3) ──> Phase 7 (US4)
                                                              │
                                        Phase 8 (backstop) <──┘
                                                              │
                              Phase 9 ──> Phase 10 ──> Phase 11

- **Phase 2 blocks Phase 3, and that ordering is constitutional rather than technical.**
  Constitution II forbids publish-after-commit without the outbox. A task list that built the
  fabric first would ship a violation and then repair it, and the repair would look like a
  refactor rather than like the fix it is.
- **Phase 3 blocks every story.** No story can start without the subject grammar, both modules and
  the two-instance harness.
- **US2 depends on US1**, because the frame both deliver is carried by the same publish. US3
  depends on Phase 3 only. US4 depends on US1's act, which it reuses per channel.
- **Phase 8 depends on US1 and US3** — the backstop applies a diff through the code path those two
  build, so it cannot be written before there is a path to reuse.
- **T008 gates T095.** The route's revival depends on reading a fixture's assertion, and a task
  list that ordered them the other way round has already chosen.
- **T065 and T086 are the same technique on two orderings.** Both remove the ordering under test
  and watch a test fail. Neither is a test; both are checks that a test bites.
- **No task id carries a letter suffix**, because `check-refs.py` forbids them and chapter 3.19
  used none. Chapter 3.18 used twenty-three. The cost of 3.19's convention is real and worth
  knowing before an analysis pass needs it: **inserting a task means renumbering the tail**, and
  the first attempt at that during analysis pass 1 silently broke seven in-file references —
  `T086 -> T065`, `T087 -> T045`, `T096 -> T095` and four in the sections below. The two additions
  that pass wanted were merged into T027 and T041 instead. Widen an existing task; do not insert
  one without re-auditing every `T\d{3}` in this file.

## Implementation strategy

**MVP is Phase 1 + Phase 2 + Phase 3 + Phase 4 — US1 less its failure-path scenario.** At that
point FR-RTM-10 is met on the removal path and the test that has asserted the violation since
chapter 3.18 asserts the clause instead. FR-RTM-05's event kind is only half-produced — additions
publish nothing yet — so the MVP is a demonstrable increment rather than a shippable chapter.

**US1.6 is the exception and it is stated rather than implied.** *"With the fabric unreachable, the
route still answers, the row is still written, and one structured failure event is logged"* is
T101, in Phase 8, and it carries no `[US1]` label because Phase 8 is not a story phase. Its
mechanism ships in Phase 3 with the publisher's error handling; only the end-to-end assertion
waits. **So a label-based reading of this file shows US1 at five of six, and that is accurate** —
analysis pass 3 counted 20 of 20 by mapping scenarios to tasks by content, which is a different
question from what any one phase delivers.

**Do not stop analysing on falling yield.** Chapter 3.17 ran sixteen analyse passes for 20
CRITICALs; 3.16 ran fifteen for 8, and its pass 12 recommended stopping while passes 13, 14 and 15
each found one. Yield measures the questions asked, not the defects present.
