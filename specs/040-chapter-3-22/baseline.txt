T027–T035 — THE MODULE, AND TWO DEFECTS THE ARMS LIST DID NOT PREVENT
------------------------------------------------------------

    connections.test.ts    14 passed (14)    606 ms

**DEFECT ONE: `null` FROM A REPLY AND `null` FROM A THROW WERE THE SAME VALUE.**

`failable` returned `T | null` and read `null` as failure. But `SET … NX` returns
**nil on a miss**, which is the ordinary case when a slot is taken — so every claim
past the first reported `unenforced`:

    6 failed | 8 passed (14)
    AssertionError: expected { kind: 'unenforced' } to deeply equal
                    { kind: 'claimed', slot: 1, held: 1 }

**Arm 1 and arm 5 of T026's list produce the same wire value**, and listing them
separately did not stop me writing code that cannot tell them apart. The module's
own comment claimed the distinction — *"`null` means COULD NOT ASK; it is never
conflated with nothing held"* — while the code conflated them. Fixed with a
wrapper: `{ asked: true, reply } | { asked: false }`.

`presence.ts:232` gets away with `T | null` because its `SET` uses `NX`/`XX` where
nil and failure lead to the same branch. This module has to distinguish them, and
copying its signature was the mistake.

**DEFECT TWO: AN UNREACHABLE REDIS DID NOT FAIL, IT HUNG.**

    × returns unenforced rather than zero when Redis is unreachable   20003 ms

ioredis' defaults queue a command and retry, so `claim` waited out the test's own
timeout. **Against NFR-PRF-04's p95 < 1 s from handshake to `connection.ack`, a cap
that fails open must fail open QUICKLY** — otherwise FR-016's "accept the
connection" is indistinguishable from refusing it. `limits.ts:95` and
`presence.ts:133` both already use the three options that bound it:

    lazyConnect: true, maxRetriesPerRequest: 0, connectTimeout: 1_000

Now 606 ms for the whole file. **Neither defect was in the arms list, the plan, or
fifteen analysis passes** — both surfaced from running the tests against a real
Redis, which is the reason T034 insists on one.

`Promise.race` WAS THE FIRST FIX AND IT WAS WRONG. `untilAcked` rejects at its own

an unhandled rejection, which in this package ends the process. Polling both
conditions has no second promise to abandon.

THE CRASH IS SIMULATED AT THE REGISTRY, NOT AT THE SOCKET, and the fixture says so

In process there is no way to stop a gateway's own `close` handlers running:
destroying the socket is what triggers them. So `crash()` quits the instance's
Redis client and nothing else. From Redis's side — the only side that can see any
of this — that is exactly a `kill -9`: no release lands, no renewal lands, and the
five keys sit until their bound elapses. Teardown then runs the ordinary path,
where every release and every `releaseAll` throws inside the module's own
`failable` and is logged rather than thrown, so the timers still get cleared. It
does not reproduce a half-written command or a torn connection, and the comment
does not claim it does.

ONE MODULE PER INSTANCE, MOVED INTO `boot()` (T050a)

Phase 5's three tests built a registry in the test body and handed it in. Two
gateways sharing one module would have the crashed instance's `releaseAll()` free
the SURVIVING instance's places, and T052 would have passed for the wrong reason.
`boot({ cap: {} })` now builds one per instance and closes it after
`sessions.close()`, which is also the ordering the release needs.

FR-011a NEEDED A THIRD DOOR ON THE FIXTURE. `sessions.close()` frees the places
and then calls `wss.close()`, which does not close established sockets — and the
fixture's own `close()` waits on `server.close()`, which does not return while a
socket is open. So the deploy path can only be observed by a call that stops the
sessions and leaves the rest to teardown: `instance.shutdown()`. The test uses the
DEFAULT bound, sixty seconds, so expiry cannot explain the acceptance, and the
default twenty-second heartbeat, so a renewal cannot re-claim what `releaseAll`
just freed.

PHASE 7 — THE RACE, AND A REAL DEFECT FOUND BY FALSIFYING SOMETHING ELSE

T058 ran two mechanisms, not one.

    the claim's SET drops its NX          8 of 16 red
    the claim becomes GET-then-SET        0 of 16 red

The first is what the task asked for and it proves less than it looks: dropping
`NX` destroys mutual exclusion even when the calls are strictly sequential, so of
course the cap stops capping. The second is the mechanism that isolates ATOMICITY —
check-then-act is exclusive when nothing else is in flight and racy in the window
between the two commands — and it left every existing test green.

"NOTHING WENT RED, THEREFORE THE ORDERING IS NOT OBSERVABLE" IS A STATEMENT ABOUT
THE SUITE

T058's own instruction says that if nothing goes red the race is not observable
from the application and T059 changes shape. Following it would have produced the
wrong answer. Nothing went red because no test in the file put more than one claim
in flight at a time. T059's test does, and under check-then-act it admits ALL
TWELVE attempts, six runs out of six — every one of them reads slot 0 as free
before any of them writes it.

    expected [ …(12) ] to have a length of 5 but got 12

So the race is observable, deterministically, and the ordering is what carries
FR-013 after all. The test had to be written to find that out, which is the part
the procedure did not allow for. Chapter 3.20's rule — a claim about an observable
difference needs falsifying before the test is written — holds; what needs adding
is that a falsification can only see the tests that exist.

T059's fixture is the two instances Phase 6 built, and it has to be. `Promise.all`
of twelve connects against one gateway is not a race: they reach Redis through one
client on one socket and the commands serialise there.

THE FLAKE THAT WAS A PRODUCT DEFECT

The check-then-act run showed one red — the clean-shutdown test, at
`no connection.ack within 5s`. It passed alone. Under the SHIPPED code it failed
2 runs in 6, so it was never about check-then-act at all: the new test was flaky
and about to go into a twenty-run battery.

The message threw the evidence away. `untilAcked` reported only that no ack
arrived; the socket had been refused half a second earlier. Rewritten to carry
what it saw, the next failure said:

    no connection.ack within 5s — frames: error (connection_limit_reached);
    close: 4004

which named the defect. `release` retires a slot by writing a one-millisecond
tombstone, and the walk's `SET NX` refuses any key that exists — so a claim
arriving inside that millisecond stepped over the slot. The module's comment said
so and called it safe: "one slot briefly skipped, never an over-admit". True of one
slot. **`releaseAll` tombstones ALL FIVE AT ONCE**, and then the walk finds nothing
free and returns `full`:

    expected { kind: 'full', held: 5 } to deeply equal { kind: 'claimed', slot: 0 }

A client reconnecting to the new instance after a deploy is refused with
`connection_limit_reached`, whose documented remedy is to close one of the
connections it already holds. Those went with the old instance. FR-011a exists to
make a deployment cost one reconnection cycle; this made it cost a refusal with
impossible advice.

THE FIX IS THAT A TOMBSTONE MEANS FREE

The walk now tries `SET NX` and then, on the same slot, `SET … IFEQ - PX bound`.
Two commands per contested slot; one for the common case where the first slot is
free; ten for a genuinely full user, against NFR-PRF-04's one-second budget. The
race stays inside the command: two connections both finding the tombstone both
attempt it, the first wins, the second's comparison fails against the winner's id
and it walks on. No connection id can equal `-`.

`tombstoneMs` IS NOW A NAMED, INJECTABLE NUMBER, and that is what turns the flake
into a test. At one millisecond the broken walk passes about half the time; at 500
ms it fails every time. Three unit tests, all deterministic:

    frees a slot it holds, and the slot is reusable at once      slot 0, no sleep
    claims a slot whose tombstone has NOT expired                tombstoneMs: 500
    accepts a claim immediately after releaseAll frees all five  tombstoneMs: 500

Removing the second command turns all three red. The first of them USED TO SLEEP
20 ms and accept any slot, with a comment saying either outcome was correct — the
sleep is what hid this for two phases, and the clean-shutdown test now reconnects
with no wait at all for the same reason.

CONSTITUTION IV, PASSED NON-VACUOUSLY (T066)

Chapter 3.21 recorded that this principle can pass for the wrong reason, so the
reason is written down. No row is written anywhere in this chapter: the api
remains the single writer of persisted state and the cap never touches Postgres.

What is not vacuous is the second bullet: *"Nothing in Redis is a source of truth:
total Redis loss must cause no data loss."* The connection registry is named in
