T011 — THE FAILING STATE, OBSERVED, AND A PREMISE THIS TASK GOT WRONG
------------------------------------------------------------

    × refuses a sixth connection for one user (FR-RTM-09 (3.22))   5094 ms
    Error: no close within 5s

**Red for exactly the stated reason.** The five acks succeeded — the loop asserts
each one's identity — and the sixth stayed open, which is the failing state this
phase exists to observe. Not `fetch failed`, not a timeout on the api, not a port
collision: the connection was accepted.

**AND WRITING IT FOUND A HOLE IN THE TASK.** T011 as planned put the test in
`session.itest.ts` and said nothing about which describe or which modules. But
T006b had just established that every gateway module is optional and that this file
calls `attachSessions` with none — **so a red test here could never go green.** A
red test that cannot pass is worse than no test: it trains a reader to ignore the
lane.

The resolution keeps the test where the task put it and adds what the task missed.
It lives in the describe named **"the cap at the door"**, which already holds the
other two door refusals — chapter 3.8's rate limit and chapter 3.11's quota, the
second needing no module because the api decides it — and **T042d passes the module
into that block in Phase 5.** The connection cap is the third refusal at that door
and belongs beside them.

**Research R11b is amended rather than left standing.** It said the new integration
file would be the only fixture enforcing the cap. Two will: the new file and this
block. That is a deliberate second, not a leak.
