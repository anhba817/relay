T011 — THE FAILING STATE, OBSERVED, AND A PREMISE THIS TASK GOT WRONG
------------------------------------------------------------

    × refuses a sixth connection for one user (FR-RTM-09 (3.22))   5094 ms
    Error: no close within 5s

**Red for exactly the stated reason.** The five acks succeeded — the loop asserts

**AND WRITING IT FOUND A HOLE IN THE TASK.** T011 as planned put the test in

and belongs beside them.

**Research R11b is amended rather than left standing.** It said the new integration
file would be the only fixture enforcing the cap. Two will: the new file and this

T017 — THE FALSIFICATION RUN, AND TWO OF THREE TESTS FAILED IT

Re-applying T013's break turned **one** of the three red, not three. That is a
finding about my own tests, not about the code:

    T014  message, exactly once     RED under the break            falsifiable
    T015  membership to both        green — the break was in the
                                    WRONG PATH; a second
                                    falsification, de-duplicating the
                                    membership audience by user
                                    instead of by connection id,
                                    turns it red                   falsifiable
    T016  a live connection after
          an earlier one is gone    NOT FALSIFIABLE — see below

**T016 could not be falsified and the test's claim was corrected rather than the
test kept.** FR-014's second half says one connection's delivery failure must not
prevent another's. `send` is a bare `socket.send(...)` with no try/catch, so the
falsification is to make it throw on a socket that is not OPEN — and **all three
tests stayed green**, because `registry.remove` runs from the terminated socket's
own close handler before any publish arrives. There is no failing send to survive:
a dead connection is *gone from the registry*, not *present and broken*.

So the property is real and **unobservable through this fixture**. Chapter 3.20's
lesson in its own words: a claim about an observable difference needs falsifying
before the test is written. The test stays, retitled to what it does assert — a
surviving connection keeps receiving after an earlier one is gone — and its comment
records why the stronger claim is not made.

**And the first draft of T016 terminated the WRONG socket.** `subscribersOf`
returns `[...byId.values()]` — a `Map`, so insertion order — so terminating the
second connection would leave a delivery loop that dies on its first failure
looking correct, having already reached the first. It now terminates the first.

PHASE 3 — THE PROTOCOL, AND A THIRD PINNED COUNT NO TASK OWNED
------------------------------------------------------------

T019 — THE TWO NAMES, DECIDED ONCE

    close code   4004  "connection limit reached"
    error code   connection_limit_reached

`4004` is the next free number after chapter 3.15's `4003`, from the space 1.3 and
3.15 drew from. **The error code's name was chosen against a collision rather than
for its sound**: `rate_limited` is one word away in the register and means the
opposite thing — it throttles a tenant's establishments per window and its own
message reads *"too many connections; retry after the window resets"*. Retrying is
what this code must not suggest, so it cannot borrow that phrasing.

T020, T021 — WHY NO REUSE WORKS, WRITTEN WHERE THE CODE IS

Every one of the five fails `codes.ts`'s standing test — *a client that cannot tell
them apart retries the wrong one for ever*:

    4001  sends the client to re-authenticate. The token is valid, so minting a new
          one succeeds and connecting fails again: 3.15's loop against a wall.
    4002  blames a client that did nothing wrong.
    4003  tells a person they are barred while four of their connections work.
    4008  tells a client to wait for a quota window. The slot may free a second
          later, and waiting never causes it.
